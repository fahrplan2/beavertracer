# Kada se paketi izgube

:::goal
**Ishod učenja:** U alatu Tracer možeš promatrati i objasniti kako TCP uočava izgubljene podatke, ponovno ih šalje i uspostavlja ispravan redoslijed.
:::

U ovoj simulaciji kabel je namješten: **drugi paket s podacima** od Client-PC-a prema Serveru se gubi. (Postavku pronalaziš kada u načinu izvođenja klikneš na kabel: **Ciljano gubitak paketa**.)

## Eksperiment

1. Prijeđi u :fa-play: način izvođenja (**Pokreni**), otvori na **Client-PC** **Jednostavni TCP klijent** i poveži ga na `192.168.0.20`, port `5000`.
2. Pošalji jednu za drugom tri poruke: `Hallo`, zatim `Welt`, zatim `!`.
3. Promatraj prozor za chat: odjek poruke `Hallo` stiže odmah. A druge dvije?
4. Pričekaj nekoliko sekundi. Zatim u načinu :fa-magnifying-glass: **Praćenje** otvori trace za **Server** (primatelj), sučelje `eth0`.

:::quiz mc
Što se događa s odjecima poruka `Welt` i `!`?
- [ ] Odjek poruke `!` stiže odmah, a `Welt` nedostaje zauvijek
- [x] Oba stižu tek nakon nekoliko sekundi — zajedno i ispravnim redoslijedom
- [ ] Nijedan od njih nikada ne stiže
:::

## Što prikazuje Tracer

Na serveru nedostaje paket s porukom `Welt` — on je ipak izgubljen. Umjesto toga u stupcu **Info** pronalaziš tri napomene u uglatim zagradama:

| Napomena | Što se dogodilo |
|---|---|
| `[TCP Previous segment not captured]` | Paket s `!` stiže, ali prije njega nedostaju bajtovi — **praznina**. |
| `[TCP Dup ACK …]` | Server ponovno potvrđuje isti broj kao i prije (*duplicate ACK*): „Još uvijek čekam bajt 8.” |
| `[TCP Retransmission]` | Klijent **još jednom** šalje `Welt`. |

:::quiz short
Koji redni broj (`Seq`) ima paket označen s `[TCP Retransmission]`?
= 8
:::

:::quiz short
Koji broj potvrde (`Ack`) server šalje odmah nakon ponovnog slanja?
= 17
:::

:::quiz mc
Zašto server nakon ponovnog slanja odmah potvrđuje sve do bajta 17 — a ne samo do kraja poruke `Welt`?
- [x] `!` je već primio i zadržao — s porukom `Welt` praznina je zatvorena, sada je sve do bajta 16 stiglo
- [ ] Klijent je `Welt` i `!` ponovno poslao zajedno
- [ ] Brojevi potvrde uvijek se zaokružuju
:::

:::evaluate
Provjeri odgovore
:::

Na dijagramu slijeda to izgleda ovako — isprekidana strelica s oznakom ✕ je izgubljeni paket:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Što se krije iza toga

Klijent čuva svaki poslani paket dok ne bude potvrđen i za to pokreće **timer**. Ako potvrda predugo izostane, ponovno šalje podatke — **ponovno slanje** (*retransmission*).

Server uvijek potvrđuje samo do **prve praznine**. Podatke koji stignu nakon nje (ovdje `!`) zadržava dok se praznina ne popuni. Tek tada sve prosljeđuje programu ispravnim redoslijedom — zato su odjeci poruka `Welt` i `!` stigli zajedno.

:::tip Zapamti
TCP uočava gubitke po **izostalim potvrdama**: primatelj uvijek potvrđuje samo do prve praznine. Ako potvrda izostane, pošiljatelj nakon isteka timera podatke šalje **ponovno** (*retransmission*). Ono što stigne nakon praznine primatelj zadržava — tako podaci do programa stižu **potpuni i ispravnim redoslijedom**.
:::

:::tip Produbljivanje: Fast Retransmit
Nakon `Hallo` brzo jednu za drugom pošalji četiri ili više poruka. Nakon izgubljenog paketa klijent tada dobiva tri *Dup ACK*-a zaredom — i odmah ponovno šalje, bez čekanja na svoj timer. Taj se postupak zove **Fast Retransmit**.
:::

:::note
Stvarne TCP implementacije osim toga prilagođavaju i brzinu slanja: ako se paketi gube, mreža je vjerojatno preopterećena i pošiljatelj usporava (*kontrola zagušenja*). To nadilazi okvire ovog tečaja.
:::
