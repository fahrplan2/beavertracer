# 数据包丢失时会发生什么

:::goal
**学习目标：** 你能在追踪中观察并解释 TCP 如何发现丢失的数据、重新发送，并恢复数据的顺序。
:::

在这个模拟中，线缆被做了手脚：从 Client-PC 发往 Server 的**第二个带数据的数据包**会丢失。（在运行模式下点击线缆即可找到该设置：**目标丢包**。）

## 实验

1. 切换到 :fa-play: **运行**模式，在 **Client-PC** 上打开**简单 TCP 客户端**，并连接到 `192.168.0.20`，端口 `5000`。
2. 依次发送三条消息：`Hallo`，然后是 `Welt`，最后是 `!`。
3. 观察聊天窗口：`Hallo` 的回显立即出现。另外两条呢？
4. 等待几秒钟。然后在 :fa-magnifying-glass: **追踪**模式下，为 **Server**（接收方）的接口 `eth0` 打开一个追踪。

:::quiz mc
`Welt` 和 `!` 的回显会怎样？
- [ ] `!` 的回显立即出现，`Welt` 永远丢失
- [x] 两者都要几秒钟后才出现——一起出现，并且顺序正确
- [ ] 两者都永远不会到达
:::

## 追踪显示了什么

在 Server 处缺少带有 `Welt` 的数据包——它确实丢失了。取而代之的是，你会在 **Info** 列中找到三个用方括号标出的提示：

| 提示 | 发生了什么 |
|---|---|
| `[TCP Previous segment not captured]` | 带有 `!` 的数据包到达了，但在它之前缺少一些字节——出现了**空缺**。 |
| `[TCP Dup ACK …]` | 服务器再次确认与之前相同的编号（*重复 ACK*）：“我仍在等待第 8 个字节。” |
| `[TCP Retransmission]` | 客户端**再次**发送 `Welt`。 |

:::quiz short
标有 `[TCP Retransmission]` 的数据包的序列号（`Seq`）是多少？
= 8
:::

:::quiz short
服务器在重传之后立即发送的确认号（`Ack`）是多少？
= 17
:::

:::quiz mc
为什么服务器在重传之后会一下子确认到第 17 个字节——而不是只确认到 `Welt` 的末尾？
- [x] 它之前已经收到了 `!` 并暂存起来——有了 `Welt`，空缺被补上了，现在直到第 16 个字节的数据都齐了
- [ ] 客户端把 `Welt` 和 `!` 一起重新发送了一次
- [ ] 确认号总是会被取整
:::

:::evaluate
检查答案
:::

## 背后的原理

客户端会保存每个已发送的数据包，直到它被确认，并为此启动一个**定时器**。如果确认迟迟没有到来，它就会重新发送数据——这就是**重传**（*Retransmission*）。

服务器始终只确认到**第一个空缺**为止。在空缺之后到达的数据（这里是 `!`），它会先暂存起来，直到空缺被补上。然后它才按正确的顺序把全部数据交给程序——所以 `Welt` 和 `!` 的回显是一起出现的。

:::tip 要点
TCP 通过**缺失的确认**来发现丢失：接收方始终只确认到第一个空缺为止。如果确认没有到来，发送方会在定时器超时后**重新**发送数据（*Retransmission*）。空缺之后到达的数据会被接收方暂存——这样数据就能**完整且按正确顺序**到达程序。
:::

:::tip 拓展：快速重传
在 `Hallo` 之后，快速连续发送四条或更多消息。在丢失的数据包之后，客户端会连续收到三个*重复 ACK*——并立即重新发送，而无需等待定时器。这种机制称为**快速重传**（Fast Retransmit）。
:::

:::note
真实的 TCP 实现还会调整发送速度：如果数据包丢失，网络很可能已经拥塞，发送方就会放慢速度（*拥塞控制*）。这超出了本课程的范围。
:::
