# パケットが失われるとき

:::goal
**学習目標:** TCPが失われたデータにどのように気づき、再送し、順序を復元するのかを、トレースで観察して説明できるようになる。
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

このシミュレーションではケーブルに細工がしてあります。クライアントPCからサーバーへの**2番目のデータ付きパケット**が失われます。(この設定は、実行モードでケーブルをクリックすると見つかります: **ターゲット化されたパケットロス**。)

## 実験

1. :fa-play: **実行**モードに切り替え、**Client-PC**で**シンプル TCP クライアント**を開き、`192.168.0.20`、ポート `5000` に接続します。
2. 3つのメッセージを順に送ります: `Hallo`、次に `Welt`、最後に `!`。
3. チャットウィンドウを見てみましょう。`Hallo` のエコーはすぐに返ってきます。では、残りの2つは?
4. 数秒待ちます。そのあと :fa-magnifying-glass: **トレース**モードで、**サーバー**(受信者)のポート `eth0` のトレースを開きます。

:::quiz mc
`Welt` と `!` のエコーはどうなりますか?
- [ ] `!` のエコーはすぐに返り、`Welt` は永遠に届かない
- [x] どちらも数秒後に届く — まとめて、正しい順序で
- [ ] どちらも一切届かない
:::

## トレースが示すもの

サーバー側には `Welt` のパケットがありません。失われてしまったからです。その代わりに、**Info**列に角括弧付きの3つのヒントが見つかります:

| ヒント | 何が起きたか |
|---|---|
| `[TCP Previous segment not captured]` | `!` のパケットは届いたが、その前のバイトが欠けている — **ギャップ**がある。 |
| `[TCP Dup ACK …]` | サーバーが前回と同じ番号をもう一度確認応答する(*duplicate ACK*): 「まだバイト8を待っています。」 |
| `[TCP Retransmission]` | クライアントが `Welt` を**もう一度**送る。 |

:::quiz short
`[TCP Retransmission]` と表示されているパケットのシーケンス番号(`Seq`)はいくつですか?
= 8
:::

:::quiz short
再送の直後にサーバーが送る確認応答番号(`Ack`)はいくつですか?
= 17
:::

:::quiz mc
なぜサーバーは再送のあと、`Welt` の終わりまでではなく、バイト17までまとめて確認応答するのでしょうか?
- [x] `!` はすでに受信して保留していた — `Welt` でギャップが埋まり、バイト16までがすべてそろったから
- [ ] クライアントが `Welt` と `!` をもう一度まとめて送ったから
- [ ] 確認応答番号は常に丸められるから
:::

:::evaluate
回答を確認
:::

シーケンス図ではこのように見えます。✕が付いた破線の矢印が、失われたパケットです:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## 背景にある仕組み

クライアントは、送信したパケットを確認応答が来るまで保持し、そのために**タイマー**を開始します。確認応答がなかなか来ないと、データをもう一度送ります。これが**再送**(*Retransmission*)です。

サーバーが確認応答するのは、常に**最初のギャップ**までです。その後に届いたデータ(ここでは `!`)は、ギャップが埋まるまで保留します。ギャップが埋まって初めて、すべてを正しい順序でプログラムに渡します。だから `Welt` と `!` のエコーがまとめて届いたのです。

:::tip ポイント
TCPは**確認応答の欠落**によって損失を検知します。受信側は常に最初のギャップまでしか確認応答しません。確認応答が来なければ、送信側はタイマーが切れたあとにデータを**もう一度**送ります(*再送*、Retransmission)。ギャップの後に届いたデータは受信側が保留するので、データは**欠けることなく、正しい順序で**プログラムに届きます。
:::

:::tip 発展: Fast Retransmit
`Hallo` のあとに、4つ以上のメッセージを素早く続けて送ってみましょう。失われたパケットのあと、クライアントは *Dup ACK* を3回連続で受け取り、タイマーを待たずにすぐ再送します。この方式を**Fast Retransmit**と呼びます。
:::

:::note
実際のTCP実装は、送信速度も調整します。パケットが失われるのは、ネットワークが混雑しているからだと考えられるため、送信側は速度を落とします(*輻輳制御*)。これはこのコースの範囲を超えます。
:::
