# 証明書: この鍵は誰のものか?

非対称暗号と署名があれば、すべて解決したように見えます。あなたの銀行のWebサーバーが公開鍵を送ってくれれば、それで準備完了です。でも、その公開鍵が**本当に銀行のものである**と、どうやって分かるのでしょうか?

通信経路を迂回させる攻撃者は、**自分自身の**公開鍵を送りつけて、銀行だと名乗ることができてしまいます。するとブラウザは素直に攻撃者の鍵で暗号化してしまい、攻撃者はすべてを読み取れます。このように通信の途中に入り込む攻撃者を**中間者(Man-in-the-Middle)**と呼びます。

## 証明書: 鍵のための身分証明書

実生活では、自分が誰であるかを証明するために**身分証明書**を見せます。身分証明書が信用されるのは、**信頼できる機関**(市役所など)が発行したものであり、偽造が難しいからです。

ネットワークでは、この役割を**証明書**が担います。証明書には、たとえば次の情報が含まれています。

| フィールド | 意味 | 身分証明書では |
|---|---|---|
| **サブジェクト**(*Subject*、多くは `CN=…`) | 誰のための証明書か。Webサーバーの場合はその名前、例: `CN=www.biberbank.de` | 所有者の氏名 |
| **公開鍵** | 所有者の鍵 | 顔写真 |
| **発行者**(*Issuer*) | 誰がこの証明書を発行したか | 発行機関 |
| **有効期間** | …から…まで | 有効期限 |
| 発行者の**署名** | 発行者がこの内容で本当に証明書を発行したことの証明 | 印章、ホログラム |

`CN` は *Common Name* の略です。

証明書を発行する機関は**認証局**(*Certificate Authority*、略して **CA**)と呼ばれます。認証局は `www.biberbank.de` の証明書に署名する前に、申請者が本当にそのドメインを所有していることを確認します。

## ブラウザは誰を信頼するのか?

ブラウザは、どの証明書に対しても次の点を確認します。

1. CAの**署名**は本物か?(そのためにCAの公開鍵が必要です。)
2. 証明書はまだ**有効**か?
3. 証明書内の**名前**はアクセスしたアドレスと一致しているか?

では、ブラウザはどうやってCAを知っているのでしょうか? どのOSやブラウザにも、約150の**ルートCA**(*Root-CA*)のリストが**あらかじめインストール**されています。これらの証明書は**自己署名**されています。つまり自分で自分を証明しているのです。ソフトウェアに同梱されているからこそ、信頼されています。

ルートCAが直接署名せず、**中間CA**を経由して署名することもよくあります。こうして**信頼の連鎖**ができあがります。

```
Root-CA (vorinstalliert, vertraut)
  └─ signiert → Zwischen-CA
                  └─ signiert → www.biberbank.de
```

ブラウザは連鎖を下から上へたどり、信頼しているルートCAに行き着くまで確認します。これがうまくいかない場合や、有効期間または名前が一致しない場合には、**警告**を表示します。

:::quiz match
サブジェクト (CN) -> 証明書がどの名前に対して有効か
発行者 -> どのCAがその証明書に署名したか
公開鍵 -> サーバーの署名を検証するために必要
ルートCA -> ブラウザにあらかじめインストールされており、信頼の連鎖の出発点となる
:::

:::tip ポイント
**証明書**は、**公開鍵**が特定の**名前**に属していることを証明します。証明書は**認証局(CA)**によって署名されます。ブラウザは、**信頼の連鎖**をたどってあらかじめインストールされた**ルートCA**に行き着き、証明書が**有効**で、**名前**がアドレスと一致している場合に、その証明書を信頼します。
:::
