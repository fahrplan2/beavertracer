# Cuando los paquetes se pierden

:::goal
**Objetivo de aprendizaje:** Puedes observar en el Tracer y explicar cómo TCP detecta datos perdidos, los reenvía y restablece el orden.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

En esta simulación el cable está preparado: el **segundo paquete con datos** del Client-PC al Server se pierde. (Encuentras el ajuste al hacer clic en el cable en el modo de ejecución: **Pérdida de paquetes dirigida**.)

## El experimento

1. Cambia al modo :fa-play: **Ejecutar**, abre en el **Client-PC** el **Cliente TCP Simple** y conéctalo con `192.168.0.20`, puerto `5000`.
2. Envía tres mensajes uno tras otro: `Hallo`, luego `Welt` y después `!`.
3. Observa la ventana de chat: el eco de `Hallo` llega enseguida. ¿Y los otros dos?
4. Espera unos segundos. Después, en el modo :fa-magnifying-glass: **Rastreo**, abre un trace para el **Server** (el destinatario), puerto `eth0`.

:::quiz mc
¿Qué ocurre con los ecos de `Welt` y `!`?
- [ ] El eco de `!` llega enseguida, `Welt` falta para siempre
- [x] Ambos llegan solo después de unos segundos, juntos y en el orden correcto
- [ ] Ninguno de los dos llega nunca
:::

## Qué muestra el Tracer

En el servidor falta el paquete con `Welt`, pues se ha perdido. En cambio, en la columna **Info** encuentras tres indicaciones entre corchetes:

| Indicación | Qué ha ocurrido |
|---|---|
| `[TCP Previous segment not captured]` | Llega el paquete con `!`, pero antes faltan bytes: hay un **hueco**. |
| `[TCP Dup ACK …]` | El servidor confirma otra vez el mismo número que antes (*duplicate ACK*): «Sigo esperando el byte 8». |
| `[TCP Retransmission]` | El cliente envía `Welt` **una vez más**. |

:::quiz short
¿Qué número de secuencia (`Seq`) tiene el paquete marcado con `[TCP Retransmission]`?
= 8
:::

:::quiz short
¿Qué número de confirmación (`Ack`) envía el servidor justo después de la retransmisión?
= 17
:::

:::quiz mc
¿Por qué el servidor confirma después de la retransmisión directamente hasta el byte 17, y no solo hasta el final de `Welt`?
- [x] Ya había recibido `!` y lo había retenido: con `Welt` el hueco se cierra y ahora está todo hasta el byte 16
- [ ] El cliente ha vuelto a enviar `Welt` y `!` juntos
- [ ] Los números de confirmación siempre se redondean
:::

:::evaluate
Comprobar respuestas
:::

En el diagrama de secuencia se ve así; la flecha discontinua con la ✕ es el paquete perdido:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Qué hay detrás

El cliente conserva cada paquete enviado hasta que se confirma e inicia para ello un **temporizador**. Si la confirmación tarda demasiado, vuelve a enviar los datos: una **retransmisión** (*Retransmission*).

El servidor solo confirma hasta el **primer hueco**. Los datos que llegan después (aquí `!`) los retiene hasta que se rellena el hueco. Solo entonces los entrega todos al programa en el orden correcto; por eso los ecos de `Welt` y `!` llegaron juntos.

:::tip Recuerda
TCP detecta las pérdidas por las **confirmaciones que faltan**: el destinatario solo confirma hasta el primer hueco. Si la confirmación no llega, el remitente envía los datos **de nuevo** cuando expira un temporizador (*Retransmission*). Lo que llega después de un hueco, el destinatario lo retiene, de modo que los datos llegan al programa **completos y en el orden correcto**.
:::

:::tip Profundización: Fast Retransmit
Después de `Hallo`, envía cuatro o más mensajes rápidamente uno tras otro. Tras el paquete perdido, el cliente recibe tres *Dup ACKs* seguidos y reenvía de inmediato, sin esperar a su temporizador. Este procedimiento se llama **Fast Retransmit**.
:::

:::note
Las implementaciones reales de TCP también adaptan su ritmo de envío: si se pierden paquetes, probablemente la red está sobrecargada y el remitente se vuelve más lento (*control de congestión*). Esto va más allá de este curso.
:::
