# El handshake TLS

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Antes de enviar la primera petición cifrada, el cliente y el servidor tienen que ponerse de acuerdo: sobre un método, sobre una clave de sesión — y el cliente debe comprobar con quién está hablando. Este establecimiento de conexión se llama **handshake TLS**.

## Observar

Abre en el **Client-PC** `https://www.beaver-schule.de/` (si aún no lo has hecho), abre un trace para el **Client-PC** y filtra con `tls`.

## El desarrollo en el diagrama

Sin las confirmaciones TCP (`ACK`), el handshake tiene este aspecto:

:::seq
mode: text
Client -> Server: Client Hello | Número aleatorio, métodos posibles
Server -> Client: Server Hello | Método elegido, número aleatorio
Server -> Client: Certificate | Certificado del servidor
Server -> Client: Server Key Exchange | Parte DH, firmada
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | Parte DH del cliente
Client -> Server: Change Cipher Spec | A partir de ahora, cifrado
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | A partir de ahora, cifrado
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (cifrado)
Server -> Client: Application Data | Página web (cifrada)
:::

Qué ocurre en cada paso — y qué elemento de la sección 8.1 hay detrás:

1. **Client Hello / Server Hello:** el cliente y el servidor se saludan, intercambian números aleatorios y acuerdan los métodos (en BeaverTracer: intercambio de claves con **ECDHE**, firma con **ECDSA**, cifrado con **AES**).
2. **Certificate:** el servidor envía su **certificado**. El cliente comprueba la firma de la CA, la validez y el nombre. Si esto falla, cancela aquí — y el navegador muestra una advertencia.
3. **Server Key Exchange:** el servidor envía su **parte de Diffie-Hellman** — y la **firma** con su clave privada. El cliente verifica la firma con la clave pública del certificado. Así sabe que esta parte procede realmente del titular del certificado y no de un Man-in-the-Middle.
4. **Client Key Exchange:** el cliente envía su parte de Diffie-Hellman. Ahora ambos pueden calcular la misma **clave de sesión** — sin que se haya transmitido nunca.
5. **Change Cipher Spec:** «A partir de ahora cifro».
6. **Encrypted Handshake Message (Finished):** ambas partes envían — ya cifrada — una suma de verificación de todos los mensajes del handshake anteriores. Si un atacante ha modificado algo por el camino, las sumas de verificación no coinciden y la conexión se cancela.
7. **Application Data:** a partir de aquí fluyen los datos HTTP — cifrados simétricamente con AES.

:::quiz match
Certificate -> El servidor se identifica con su certificado
Server Key Exchange -> Parte de Diffie-Hellman firmada del servidor
Client Key Exchange -> Parte de Diffie-Hellman del cliente
Change Cipher Spec -> A partir de ahora se cifra
Application Data -> Datos HTTP cifrados
:::

:::note
En el trace ves **dos** conexiones TLS consecutivas: el navegador primero obtiene la página y después establece una nueva conexión para la hoja de estilos `style.css`. Cada conexión tiene su propio handshake y su propia clave de sesión. Los navegadores reales mantienen las conexiones abiertas y se ahorran así parte de este esfuerzo. Además, la versión más reciente, **TLS 1.3**, necesita menos mensajes que el TLS 1.2 mostrado aquí.
:::

:::tip Recuerda
En el **handshake TLS**, el servidor se identifica con su **certificado**, ambas partes acuerdan una **clave de sesión** mediante **Diffie-Hellman** (el servidor **firma** su parte) y con **Finished** ambas comprueban que nadie ha modificado el handshake. Después, los datos se transmiten como **Application Data** cifrados simétricamente.
:::
