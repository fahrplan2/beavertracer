# L'handshake TLS

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Prima che venga inviata la prima richiesta cifrata, client e server devono mettersi d'accordo su un metodo e su una chiave di sessione. Inoltre il client deve verificare con chi sta parlando. Questa instaurazione della connessione si chiama **handshake TLS**.

## Osserva

Sul **Client-PC** apri `https://www.beaver-schule.de/` (se non l'hai già fatto), apri una traccia per il **Client-PC** e filtra con `tls`.

## Il flusso nel diagramma

Senza i riscontri TCP (`ACK`), l'handshake si presenta così:

:::seq
mode: text
Client -> Server: Client Hello | numero casuale, metodi possibili
Server -> Client: Server Hello | metodo scelto, numero casuale
Server -> Client: Certificate | certificato del server
Server -> Client: Server Key Exchange | parte DH, firmata
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | parte DH del client
Client -> Server: Change Cipher Spec | da ora in poi cifrato
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | da ora in poi cifrato
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (cifrato)
Server -> Client: Application Data | pagina web (cifrata)
:::

Ecco cosa succede e quale elemento della sezione 8.1 c'è dietro:

1. **Client Hello / Server Hello:** client e server si salutano, si scambiano numeri casuali e si accordano sui metodi (in BeaverTracer: scambio di chiavi con **ECDHE**, firma con **ECDSA**, cifratura con **AES**).
2. **Certificate:** il server invia il suo **certificato**. Il client verifica la firma della CA, la validità e il nome. Se la verifica fallisce, il client interrompe qui e il browser mostra un avviso.
3. **Server Key Exchange:** il server invia la sua **parte Diffie-Hellman** e la **firma** con la sua chiave privata. Il client verifica la firma con la chiave pubblica contenuta nel certificato. Così sa che questa parte proviene davvero dal titolare del certificato e non da un man-in-the-middle.
4. **Client Key Exchange:** il client invia la sua parte Diffie-Hellman. Ora entrambi possono calcolare la stessa **chiave di sessione**, senza che sia mai stata trasmessa.
5. **Change Cipher Spec:** „Da ora in poi cifro.“
6. **Encrypted Handshake Message (Finished):** entrambe le parti inviano, già in forma cifrata, un checksum calcolato su tutti i messaggi di handshake precedenti. Se un attaccante ha modificato qualcosa lungo il percorso, i checksum non corrispondono e la connessione viene interrotta.
7. **Application Data:** da qui in poi passano i dati HTTP, cifrati in modo simmetrico con AES.

:::quiz match
Certificate -> Il server si identifica con il suo certificato
Server Key Exchange -> Parte Diffie-Hellman firmata del server
Client Key Exchange -> Parte Diffie-Hellman del client
Change Cipher Spec -> Da ora in poi si cifra
Application Data -> Dati HTTP cifrati
:::

:::note
Nella traccia vedi **due** connessioni TLS una dopo l'altra: il browser prima scarica la pagina e poi apre una nuova connessione per il foglio di stile `style.css`. Ogni connessione ha un proprio handshake e una propria chiave di sessione. I browser reali tengono aperte le connessioni e si risparmiano così una parte di questo lavoro. La versione più recente, **TLS 1.3**, richiede inoltre meno messaggi rispetto al TLS 1.2 mostrato qui.
:::

:::tip Punto chiave
Durante l'**handshake TLS** il server si identifica con il suo **certificato**. Le due parti negoziano una **chiave di sessione** tramite **Diffie-Hellman**, e il server **firma** la propria parte. Con **Finished** entrambe verificano che nessuno abbia modificato l'handshake. Dopodiché i dati vengono trasmessi come **Application Data**, cifrati in modo simmetrico.
:::
