# Quando i pacchetti vanno persi

:::goal
**Obiettivo di apprendimento:** Sai osservare nel tracer e spiegare come TCP si accorge dei dati persi, li rinvia e ripristina l'ordine corretto.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

In questa simulazione il cavo è stato preparato: il **secondo pacchetto con dati** dal Client-PC al Server va perso. (Trovi l'impostazione cliccando sul cavo nella modalità di esecuzione: **Perdita di pacchetti mirata**.)

## L'esperimento

1. Passa alla modalità :fa-play: **Esegui**, apri sul **Client-PC** il **Client TCP Semplice** e connettilo a `192.168.0.20`, porta `5000`.
2. Invia tre messaggi uno dopo l'altro: `Hallo`, poi `Welt`, poi `!`.
3. Osserva la finestra della chat: l'eco di `Hallo` arriva subito. E gli altri due?
4. Aspetta qualche secondo. Poi, nella modalità :fa-magnifying-glass: **Traccia**, apri una traccia per il **Server** (il destinatario), interfaccia `eth0`.

:::quiz mc
Che cosa succede agli echi di `Welt` e `!`?
- [ ] L'eco di `!` arriva subito, `Welt` manca per sempre
- [x] Arrivano entrambi solo dopo qualche secondo — insieme e nell'ordine corretto
- [ ] Nessuno dei due arriva mai
:::

## Che cosa mostra il tracer

Sul server manca il pacchetto con `Welt` — dopotutto è andato perso. In compenso, nella colonna **Info** trovi tre indicazioni tra parentesi quadre:

| Indicazione | Che cosa è successo |
|---|---|
| `[TCP Previous segment not captured]` | Il pacchetto con `!` arriva, ma prima mancano dei byte — un **buco**. |
| `[TCP Dup ACK …]` | Il server conferma ancora una volta lo stesso numero di prima (*duplicate ACK*): "Sto ancora aspettando il byte 8." |
| `[TCP Retransmission]` | Il client invia `Welt` **un'altra volta**. |

:::quiz short
Quale numero di sequenza (`Seq`) ha il pacchetto contrassegnato con `[TCP Retransmission]`?
= 8
:::

:::quiz short
Quale numero di riscontro (`Ack`) invia il server subito dopo la ritrasmissione?
= 17
:::

:::quiz mc
Perché dopo la ritrasmissione il server conferma direttamente fino al byte 17 — e non solo fino alla fine di `Welt`?
- [x] Aveva già ricevuto e trattenuto `!` — con `Welt` il buco è colmato, ora c'è tutto fino al byte 16
- [ ] Il client ha inviato di nuovo `Welt` e `!` insieme
- [ ] I numeri di riscontro vengono sempre arrotondati
:::

:::evaluate
Controlla le risposte
:::

Nel diagramma di sequenza appare così — la freccia tratteggiata con la ✕ è il pacchetto perso:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Che cosa c'è dietro

Il client conserva ogni pacchetto inviato finché non viene confermato e per ciascuno avvia un **timer**. Se la conferma tarda troppo, invia di nuovo i dati — una **ritrasmissione** (*Retransmission*).

Il server conferma sempre e solo fino al **primo buco**. I dati che arrivano dopo (qui `!`) li trattiene finché il buco non viene colmato. Solo allora passa tutto al programma nell'ordine corretto — ecco perché gli echi di `Welt` e `!` sono arrivati insieme.

:::tip Punto chiave
TCP riconosce le perdite dalle **conferme mancanti**: il destinatario conferma sempre e solo fino al primo buco. Se la conferma non arriva, allo scadere di un timer il mittente invia i dati **di nuovo** (*Retransmission*). Ciò che arriva dopo un buco viene trattenuto dal destinatario — così i dati raggiungono il programma **completi e nell'ordine corretto**.
:::

:::tip Approfondimento: Fast Retransmit
Dopo `Hallo`, invia quattro o più messaggi in rapida successione. Dopo il pacchetto perso, il client riceve allora tre *Dup ACK* di fila — e ritrasmette subito, senza aspettare il suo timer. Questo procedimento si chiama **Fast Retransmit**.
:::

:::note
Le implementazioni reali di TCP adattano inoltre la loro velocità di invio: se i pacchetti vanno persi, probabilmente la rete è sovraccarica e il mittente rallenta (*controllo della congestione*). Questo va oltre gli obiettivi di questo corso.
:::
