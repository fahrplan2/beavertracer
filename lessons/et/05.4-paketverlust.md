# Kui paketid lähevad kaduma

:::goal
**Õpieesmärk:** Sa oskad Tracer'is jälgida ja selgitada, kuidas TCP märkab kadunud andmeid, saadab need uuesti ja taastab õige järjekorra.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

Selles simulatsioonis on kaabel ette valmistatud: **teine andmetega pakett** klient-arvutilt serverile läheb kaduma. (Selle seadistuse leiad, kui klõpsad Käivitusrežiimis kaablil: **Sihtotstarbeliste pakettide kaotus**.)

## Katse

1. Lülitu :fa-play: **Käivita**-režiimi, ava **Client-PC** peal **Lihtne TCP klient** ja ühenda see aadressiga `192.168.0.20`, port `5000`.
2. Saada üksteise järel kolm sõnumit: `Hallo`, siis `Welt`, siis `!`.
3. Jälgi vestlusakent: `Hallo` kaja tuleb kohe. Aga ülejäänud kaks?
4. Oota paar sekundit. Seejärel ava :fa-magnifying-glass: **Jälgi**-režiimis **Serveri** (vastuvõtja) jälg, liides `eth0`.

:::quiz mc
Mis juhtub `Welt` ja `!` kajadega?
- [ ] `!` kaja tuleb kohe, `Welt` puudub igaveseks
- [x] Mõlemad tulevad alles mõne sekundi pärast — koos ja õiges järjekorras
- [ ] Ükski neist ei jõua kunagi kohale
:::

## Mida Tracer näitab

Serveri juures puudub `Welt`-iga pakett — see ju läks kaduma. Selle asemel leiad veerust **Info** kolm märget nurksulgudes:

| Märge | Mis juhtus |
|---|---|
| `[TCP Previous segment not captured]` | `!`-ga pakett jõuab kohale, aga enne seda puuduvad baidid — tekkis **lünk**. |
| `[TCP Dup ACK …]` | Server kinnitab uuesti sama numbrit nagu enne (*duplicate ACK*): „Ootan endiselt baiti 8.“ |
| `[TCP Retransmission]` | Klient saadab `Welt` **veel kord**. |

:::quiz short
Mis järjenumber (`Seq`) on paketil, mis on märgitud `[TCP Retransmission]`?
= 8
:::

:::quiz short
Mis kinnitusnumbri (`Ack`) saadab server vahetult pärast uuesti edastamist?
= 17
:::

:::quiz mc
Miks kinnitab server pärast uuesti edastamist kohe kuni baidini 17 — ja mitte ainult `Welt` lõpuni?
- [x] Ta oli `!` juba kätte saanud ja hoidis selle tagasi — `Welt`-iga sai lünk täidetud, nüüd on kõik kuni baidini 16 olemas
- [ ] Klient saatis `Welt` ja `!` uuesti koos
- [ ] Kinnitusnumbreid ümardatakse alati
:::

:::evaluate
Kontrolli vastuseid
:::

Järjestusdiagrammil näeb see välja nii — katkendlik nool ✕-ga on kadunud pakett:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Mis selle taga on

Klient hoiab iga saadetud paketti alles, kuni see on kinnitatud, ja käivitab selleks **taimeri**. Kui kinnitus viibib liiga kaua, saadab ta andmed uuesti — see on **uuesti edastamine** (*retransmission*).

Server kinnitab alati ainult kuni **esimese lüngani**. Andmeid, mis jõuavad kohale pärast seda (siin `!`), hoiab ta tagasi, kuni lünk on täidetud. Alles siis annab ta kõik õiges järjekorras edasi programmile — seepärast tulid `Welt` ja `!` kajad koos.

:::tip Pea meeles
TCP tuvastab kaotused **puuduvate kinnituste** järgi: vastuvõtja kinnitab alati ainult kuni esimese lüngani. Kui kinnitus jääb tulemata, saadab saatja andmed pärast taimeri aegumist **uuesti** (*retransmission*). Mis jõuab kohale pärast lünka, seda vastuvõtja hoiab tagasi — nii jõuavad andmed programmini **täielikult ja õiges järjekorras**.
:::

:::tip Süvendus: Fast Retransmit
Saada pärast `Hallo` kiiresti üksteise järel neli või rohkem sõnumit. Pärast kadunud paketti saab klient siis kolm *Dup ACK*-i järjest — ja saadab kohe uuesti, ootamata oma taimerit. Seda meetodit nimetatakse **Fast Retransmit**.
:::

:::note
Päris TCP-realisatsioonid kohandavad lisaks oma saatmiskiirust: kui paketid lähevad kaduma, on võrk tõenäoliselt ülekoormatud ja saatja aeglustab (*ummikjuhtimine*). See ületab selle kursuse raamid.
:::
