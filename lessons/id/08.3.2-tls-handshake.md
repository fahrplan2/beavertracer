# Handshake TLS

:::sim
url=/sims/lesson-8.2.1.btsim

Sebelum permintaan terenkripsi pertama dikirim, klien dan server harus bersepakat: tentang suatu metode, tentang kunci sesi — dan klien harus memeriksa dengan siapa ia berbicara. Pembentukan koneksi ini disebut **handshake TLS**.

## Alur dalam diagram

Tanpa konfirmasi TCP (`ACK`), handshake terlihat seperti ini:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Apa yang terjadi di sini — dan komponen dari bagian 8.1 mana yang berperan:

1. **Client Hello / Server Hello:** Klien dan server saling menyapa, bertukar bilangan acak, dan menyepakati metode yang dipakai (di BeaverTracer: pertukaran kunci dengan **ECDHE**, tanda tangan dengan **ECDSA**, enkripsi dengan **AES**).
2. **Certificate:** Server mengirim **sertifikat**-nya. Klien memeriksa tanda tangan CA, masa berlaku, dan nama. Jika pemeriksaan ini gagal, klien menghentikan proses di sini — dan peramban menampilkan peringatan.
3. **Server Key Exchange:** Server mengirim **bagian Diffie-Hellman**-nya — dan **menandatanganinya** dengan kunci privatnya. Klien memeriksa tanda tangan itu dengan kunci publik dari sertifikat. Dengan begitu klien tahu: bagian ini benar-benar berasal dari pemilik sertifikat, bukan dari Man-in-the-Middle.
4. **Client Key Exchange:** Klien mengirim bagian Diffie-Hellman-nya. Sekarang keduanya dapat menghitung **kunci sesi** yang sama — tanpa kunci itu pernah dikirim.
5. **Change Cipher Spec:** "Mulai sekarang aku mengenkripsi."
6. **Encrypted Handshake Message (Finished):** Kedua pihak mengirim — yang sudah terenkripsi — sebuah checksum atas semua pesan handshake sebelumnya. Jika penyerang mengubah sesuatu di tengah jalan, checksum tidak akan cocok, dan koneksi diputus.
7. **Application Data:** Mulai dari sini data HTTP mengalir — dienkripsi secara simetris dengan AES.

:::quiz match
Certificate -> Server membuktikan identitasnya dengan sertifikat
Server Key Exchange -> Bagian Diffie-Hellman server yang ditandatangani
Client Key Exchange -> Bagian Diffie-Hellman klien
Change Cipher Spec -> Mulai sekarang data dienkripsi
Application Data -> Data HTTP terenkripsi
:::

:::note
Di trace kamu melihat **dua** koneksi TLS berurutan: Peramban lebih dulu mengambil halaman, lalu membuat koneksi baru untuk stylesheet `style.css`. Setiap koneksi mendapat handshake sendiri dan kunci sesi sendiri. Peramban sungguhan menjaga koneksi tetap terbuka sehingga menghemat sebagian dari beban ini. Versi yang lebih baru, **TLS 1.3**, juga membutuhkan lebih sedikit pesan dibandingkan TLS 1.2 yang ditampilkan di sini.
:::

:::tip Poin penting
Pada **handshake TLS**, server membuktikan identitasnya dengan **sertifikat**, kedua pihak menyepakati **kunci sesi** lewat **Diffie-Hellman** (server **menandatangani** bagiannya), dan dengan **Finished** keduanya memeriksa bahwa tidak ada yang mengubah handshake. Setelah itu data dikirim sebagai **Application Data** yang dienkripsi secara simetris.
:::
