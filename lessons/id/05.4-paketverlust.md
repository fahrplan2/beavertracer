# Ketika paket hilang

:::goal
**Tujuan pembelajaran:** Kamu dapat mengamati di Tracer dan menjelaskan bagaimana TCP menyadari data yang hilang, mengirimkannya kembali, dan memulihkan urutannya.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

Dalam simulasi ini kabelnya sudah disiapkan: **paket kedua yang berisi data** dari Client-PC ke Server akan hilang. (Pengaturannya bisa kamu temukan jika kamu mengeklik kabel di Mode Jalankan: **Kehilangan paket yang ditargetkan**.)

## Eksperimen

1. Beralihlah ke mode :fa-play: **Jalankan**, buka **Klien TCP Sederhana** di **Client-PC**, lalu hubungkan ke `192.168.0.20`, port `5000`.
2. Kirim tiga pesan secara berurutan: `Hallo`, lalu `Welt`, lalu `!`.
3. Perhatikan jendela chat: Echo dari `Hallo` langsung muncul. Bagaimana dengan dua pesan lainnya?
4. Tunggu beberapa detik. Lalu di mode :fa-magnifying-glass: **Jejak**, buka trace untuk **Server** (penerima), antarmuka `eth0`.

:::quiz mc
Apa yang terjadi pada echo dari `Welt` dan `!`?
- [ ] Echo dari `!` langsung muncul, `Welt` hilang selamanya
- [x] Keduanya baru muncul setelah beberapa detik — bersamaan dan dalam urutan yang benar
- [ ] Tidak satu pun dari keduanya pernah sampai
:::

## Apa yang ditunjukkan Tracer

Pada server, paket dengan `Welt` tidak ada — memang paket itu hilang. Sebagai gantinya, kamu menemukan tiga petunjuk dalam tanda kurung siku di kolom **Info**:

| Petunjuk | Apa yang terjadi |
|---|---|
| `[TCP Previous segment not captured]` | Paket dengan `!` tiba, tetapi byte sebelumnya tidak ada — sebuah **celah**. |
| `[TCP Dup ACK …]` | Server mengonfirmasi sekali lagi nomor yang sama seperti sebelumnya (*duplicate ACK*): "Aku masih menunggu byte 8." |
| `[TCP Retransmission]` | Klien mengirim `Welt` **sekali lagi**. |

:::quiz short
Berapa nomor urut (`Seq`) dari paket yang ditandai dengan `[TCP Retransmission]`?
= 8
:::

:::quiz short
Berapa nomor konfirmasi (`Ack`) yang dikirim server langsung setelah pengiriman ulang?
= 17
:::

:::quiz mc
Mengapa server setelah pengiriman ulang langsung mengonfirmasi sampai byte 17 — dan bukan hanya sampai akhir `Welt`?
- [x] Server sudah menerima `!` dan menahannya — dengan `Welt` celahnya tertutup, sekarang semuanya sampai byte 16 sudah ada
- [ ] Klien mengirim `Welt` dan `!` sekali lagi secara bersamaan
- [ ] Nomor konfirmasi selalu dibulatkan
:::

Pada diagram urutan, tampilannya seperti ini — panah putus-putus dengan tanda ✕ adalah paket yang hilang:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Apa yang ada di baliknya

Klien menyimpan setiap paket yang dikirim sampai paket itu dikonfirmasi, dan untuk itu ia memulai sebuah **timer**. Jika konfirmasi terlalu lama tidak datang, klien mengirim data itu lagi — sebuah **pengiriman ulang** (*retransmission*).

Server selalu hanya mengonfirmasi sampai **celah pertama**. Data yang tiba setelahnya (di sini `!`) ditahan sampai celah itu terisi. Baru setelah itu server meneruskan semuanya ke program dalam urutan yang benar — itulah sebabnya echo dari `Welt` dan `!` datang bersamaan.

:::tip Poin penting
TCP mengenali kehilangan dari **konfirmasi yang tidak datang**: Penerima selalu hanya mengonfirmasi sampai celah pertama. Jika konfirmasi tidak datang, pengirim mengirim data **sekali lagi** setelah timer habis (*retransmission*). Apa pun yang tiba setelah sebuah celah ditahan oleh penerima — sehingga data sampai ke program **secara lengkap dan dalam urutan yang benar**.
:::

:::tip Pendalaman: Fast Retransmit
Setelah `Hallo`, kirim empat pesan atau lebih dengan cepat secara berurutan. Setelah paket yang hilang, klien akan menerima tiga *Dup ACK* berturut-turut — dan langsung mengirim ulang, tanpa menunggu timernya. Metode ini disebut **Fast Retransmit**.
:::

:::note
Implementasi TCP yang sesungguhnya juga menyesuaikan kecepatan pengirimannya: Jika paket hilang, jaringan kemungkinan sedang kelebihan beban, dan pengirim menjadi lebih lambat (*pengendalian kemacetan*). Hal itu melampaui cakupan kursus ini.
:::
