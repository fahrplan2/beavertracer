في هذه المحاكاة تم تجهيز الكابل بشكل خاص: **الحزمة الثانية التي تحمل بيانات** من الكمبيوتر العميل إلى الخادم تضيع. (تجد هذا الإعداد عندما تنقر على الكابل في وضع التشغيل: **فقدان حزم موجه**.)

## التجربة

1. انتقل إلى وضع :fa-play: **تشغيل**، وافتح **عميل TCP البسيط** على **Client-PC** واتصل بالعنوان `192.168.0.20` والمنفذ `5000`.
2. أرسل ثلاث رسائل واحدة تلو الأخرى: `Hallo`، ثم `Welt`، ثم `!`.
3. راقب نافذة الدردشة: صدى `Hallo` يصل فورًا. وماذا عن الرسالتين الأخريين؟
4. انتظر بضع ثوانٍ. ثم افتح في وضع :fa-magnifying-glass: **التتبع** تتبعًا لـ **Server** (المستقبِل)، على المنفذ `eth0`.

:::quiz mc
ماذا يحدث لصدى `Welt` و`!`؟
- [ ] صدى `!` يصل فورًا، أما `Welt` فيضيع إلى الأبد
- [x] كلاهما يصل بعد بضع ثوانٍ فقط — معًا وبالترتيب الصحيح
- [ ] لا يصل أي منهما أبدًا
:::

## ما الذي يعرضه Tracer

في الخادم تغيب الحزمة التي تحمل `Welt` — فقد ضاعت بالفعل. وبدلًا من ذلك تجد في عمود **Info** ثلاث إشارات بين أقواس مربعة:

| الإشارة | ما الذي حدث |
|---|---|
| `[TCP Previous segment not captured]` | تصل الحزمة التي تحمل `!`، لكن تنقص قبلها بايتات — **فجوة**. |
| `[TCP Dup ACK …]` | يؤكد الخادم مرة أخرى الرقم نفسه كما في السابق (*duplicate ACK*): «ما زلت أنتظر البايت 8.» |
| `[TCP Retransmission]` | يرسل العميل `Welt` **مرة أخرى**. |

:::quiz short
ما رقم التسلسل (`Seq`) للحزمة المعلَّمة بـ `[TCP Retransmission]`؟
= 8
:::

:::quiz short
ما رقم التأكيد (`Ack`) الذي يرسله الخادم مباشرة بعد إعادة الإرسال؟
= 17
:::

:::quiz mc
لماذا يؤكد الخادم بعد إعادة الإرسال حتى البايت 17 مباشرة — وليس فقط حتى نهاية `Welt`؟
- [x] لقد كان قد استقبل `!` وأبقاه محتجزًا — ومع وصول `Welt` أُغلقت الفجوة، والآن أصبح كل شيء حتى البايت 16 موجودًا
- [ ] أرسل العميل `Welt` و`!` معًا مرة أخرى
- [ ] أرقام التأكيد تُقرَّب دائمًا
:::

:::evaluate
التحقق من الإجابات
:::

في مخطط التراسل يبدو الأمر هكذا — السهم المتقطع مع علامة ✕ هو الحزمة المفقودة:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## ما الذي يكمن وراء ذلك

يحتفظ العميل بكل حزمة مرسلة إلى أن يتم تأكيدها، ويبدأ لذلك **مؤقتًا**. إذا تأخر التأكيد أكثر من اللازم، يرسل البيانات مرة أخرى — وهذه هي **إعادة الإرسال** (*Retransmission*).

لا يؤكد الخادم إلا حتى **أول فجوة**. أما البيانات التي تصل بعدها (هنا `!`) فيحتجزها إلى أن تُملأ الفجوة. وعندها فقط يسلّم كل شيء إلى البرنامج بالترتيب الصحيح — ولهذا وصل صدى `Welt` و`!` معًا.

:::tip تذكّر
يكتشف TCP الفقدان من خلال **غياب التأكيدات**: فالمستقبِل لا يؤكد إلا حتى أول فجوة. وإذا غاب التأكيد، يرسل المرسِل البيانات **مرة أخرى** بعد انتهاء المؤقت (*Retransmission*). وما يصل بعد الفجوة يحتجزه المستقبِل — وهكذا تصل البيانات إلى البرنامج **كاملة وبالترتيب الصحيح**.
:::

:::tip تعمّق: Fast Retransmit
أرسل بعد `Hallo` أربع رسائل أو أكثر بسرعة متتالية. بعد الحزمة المفقودة يتلقى العميل ثلاثة *Dup ACKs* متتالية — ويعيد الإرسال فورًا دون انتظار مؤقته. تُسمّى هذه الآلية **Fast Retransmit**.
:::

:::note
تقوم تطبيقات TCP الحقيقية أيضًا بتكييف سرعة إرسالها: إذا ضاعت الحزم، فالأرجح أن الشبكة مزدحمة، فيبطئ المرسِل (*التحكم في الازدحام*). وهذا يتجاوز نطاق هذه الدورة.
:::
