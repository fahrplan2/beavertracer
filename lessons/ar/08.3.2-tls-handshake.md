قبل إرسال أول طلب مشفَّر، يجب أن يتفق العميل والخادم: على طريقة التشفير، وعلى مفتاح الجلسة — وعلى العميل أن يتحقق من هوية الطرف الذي يتحدث معه. يُسمّى إنشاء الاتصال هذا **مصافحة TLS** (TLS-Handshake).

## الملاحظة

افتح على **Client-PC** العنوان `https://www.beaver-schule.de/` (إن لم تكن قد فعلت ذلك بعد)، ثم افتح تتبعًا (Trace) لـ **Client-PC** وصفِّ النتائج باستخدام `tls`.

## سير العملية في المخطط

من دون إشعارات التأكيد في TCP (`ACK`) تبدو المصافحة على النحو التالي:

:::seq
mode: text
Client -> Server: Client Hello | رقم عشوائي، الطرق الممكنة
Server -> Client: Server Hello | الطريقة المختارة، رقم عشوائي
Server -> Client: Certificate | شهادة الخادم الرقمية
Server -> Client: Server Key Exchange | حصة DH، موقَّعة
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | حصة DH الخاصة بالعميل
Client -> Server: Change Cipher Spec | مشفَّر من الآن فصاعدًا
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | مشفَّر من الآن فصاعدًا
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (مشفَّر)
Server -> Client: Application Data | صفحة الويب (مشفَّرة)
:::

ما الذي يحدث هنا — وأي لبنة من القسم 8.1 تقف وراءه:

1. **Client Hello / Server Hello:** يحيّي العميل والخادم أحدهما الآخر، ويتبادلان أرقامًا عشوائية، ويتفقان على الطرق المستخدمة (في BeaverTracer: تبادل المفاتيح باستخدام **ECDHE**، والتوقيع باستخدام **ECDSA**، والتشفير باستخدام **AES**).
2. **Certificate:** يرسل الخادم **شهادته الرقمية**. يتحقق العميل من توقيع المرجع المصدِّق (CA) ومن الصلاحية ومن الاسم. إذا فشل ذلك، يتوقف عند هذه النقطة — ويعرض المتصفح تحذيرًا.
3. **Server Key Exchange:** يرسل الخادم **حصته من Diffie-Hellman** — و**يوقّعها** بمفتاحه الخاص. يتحقق العميل من التوقيع باستخدام المفتاح العام الموجود في الشهادة. وهكذا يعرف أن هذه الحصة صادرة فعلًا عن صاحب الشهادة، وليست من هجوم رجل في المنتصف (Man-in-the-Middle).
4. **Client Key Exchange:** يرسل العميل حصته من Diffie-Hellman. الآن يستطيع الطرفان حساب **مفتاح الجلسة** نفسه — من دون أن يُرسَل أبدًا عبر الشبكة.
5. **Change Cipher Spec:** «من الآن فصاعدًا سأقوم بالتشفير.»
6. **Encrypted Handshake Message (Finished):** يرسل الطرفان — وقد أصبحت الرسائل مشفَّرة — مجموعًا اختباريًا لجميع رسائل المصافحة السابقة. إذا غيّر مهاجم شيئًا في الطريق، فلن تتطابق المجاميع الاختبارية، ويُقطَع الاتصال.
7. **Application Data:** من هنا تنتقل بيانات HTTP — مشفَّرة تشفيرًا متماثلًا باستخدام AES.

:::quiz match
Certificate -> يُثبت الخادم هويته بشهادته الرقمية
Server Key Exchange -> حصة Diffie-Hellman الموقَّعة الخاصة بالخادم
Client Key Exchange -> حصة Diffie-Hellman الخاصة بالعميل
Change Cipher Spec -> من الآن فصاعدًا يتم التشفير
Application Data -> بيانات HTTP مشفَّرة
:::

:::note
في التتبع ترى اتصالَي TLS **اثنين** الواحد تلو الآخر: يجلب المتصفح الصفحة أولًا، ثم ينشئ اتصالًا جديدًا لملف التنسيق `style.css`. يحصل كل اتصال على مصافحة خاصة به ومفتاح جلسة خاص به. أما المتصفحات الحقيقية فتُبقي الاتصالات مفتوحة، فتوفّر بذلك جزءًا من هذا الجهد. كما أن الإصدار الأحدث **TLS 1.3** يكتفي برسائل أقل من TLS 1.2 المعروض هنا.
:::

:::tip تذكّر
في **مصافحة TLS** يُثبت الخادم هويته بـ**شهادته الرقمية**، ويتفق الطرفان على **مفتاح جلسة** عبر **Diffie-Hellman** (ويقوم الخادم بـ**توقيع** حصته)، وبواسطة **Finished** يتحقق الطرفان من أن أحدًا لم يغيّر المصافحة. بعد ذلك تُنقل البيانات كـ**Application Data** مشفَّرة تشفيرًا متماثلًا.
:::
