**Cieľ učenia:** Vieš v Tracer-i pozorovať a vysvetliť, ako TCP zistí stratené dáta, odošle ich znova a obnoví poradie.
:::

V tejto simulácii je kábel pripravený tak, že **druhý paket s dátami** od Client-PC k serveru sa stratí. (Nastavenie nájdeš, keď v režime spustenia klikneš na kábel: **Cielená strata paketov**.)

## Experiment

1. Prepni sa do režimu :fa-play: **Spustiť**, na **Client-PC** otvor **Jednoduchý TCP klient** a pripoj ho na `192.168.0.20`, port `5000`.
2. Odošli postupne tri správy: `Hallo`, potom `Welt`, potom `!`.
3. Sleduj okno četu: ozvena `Hallo` príde okamžite. A zvyšné dve?
4. Počkaj niekoľko sekúnd. Potom v režime :fa-magnifying-glass: **Stopa** otvor trace pre **Server** (príjemca), port `eth0`.

:::quiz mc
Čo sa stane s ozvenami `Welt` a `!`?
- [ ] Ozvena `!` príde okamžite, `Welt` chýba navždy
- [x] Obe prídu až po niekoľkých sekundách — spoločne a so správnym poradím
- [ ] Ani jedna z nich nikdy nepríde
:::

## Čo ukazuje Tracer

Na serveri chýba paket s `Welt` — veď sa stratil. Namiesto toho nájdeš v stĺpci **Info** tri upozornenia v hranatých zátvorkách:

| Upozornenie | Čo sa stalo |
|---|---|
| `[TCP Previous segment not captured]` | Paket s `!` dorazí, ale pred ním chýbajú bajty — **medzera**. |
| `[TCP Dup ACK …]` | Server znova potvrdí rovnaké číslo ako predtým (*duplicate ACK*): „Stále čakám na bajt 8.“ |
| `[TCP Retransmission]` | Klient pošle `Welt` **ešte raz**. |

:::quiz short
Aké poradové číslo (`Seq`) má paket označený `[TCP Retransmission]`?
= 8
:::

:::quiz short
Aké potvrdzovacie číslo (`Ack`) pošle server hneď po opakovanom prenesení?
= 17
:::

:::quiz mc
Prečo server po opakovanom prenesení potvrdí rovno po bajt 17 — a nie len po koniec `Welt`?
- [x] `!` už prijal a podržal — s `Welt` sa medzera zaplnila, teraz je tam všetko až po bajt 16
- [ ] Klient poslal `Welt` a `!` ešte raz spoločne
- [ ] Potvrdzovacie čísla sa vždy zaokrúhľujú
:::

:::evaluate
Skontrolovať odpovede
:::

V diagrame komunikácie to vyzerá takto — prerušovaná šípka s ✕ je stratený paket:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Čo za tým je

Klient si uchováva každý odoslaný paket, kým nie je potvrdený, a spustí na to **časovač**. Ak potvrdenie príliš dlho nepríde, odošle dáta znova — ide o **opakované prenesenie** (*retransmission*).

Server potvrdzuje vždy len po **prvú medzeru**. Dáta, ktoré dorazia po nej (tu `!`), podrží, kým sa medzera nezaplní. Až potom odovzdá všetko programu v správnom poradí — preto prišli ozveny `Welt` a `!` spoločne.

:::tip Zapamätaj si
TCP rozpoznáva straty podľa **chýbajúcich potvrdení**: príjemca potvrdzuje vždy len po prvú medzeru. Ak potvrdenie nepríde, odosielateľ po uplynutí časovača odošle dáta **znova** (*retransmission*). Čo dorazí po medzere, príjemca podrží — vďaka tomu sa dáta dostanú k programu **kompletné a v správnom poradí**.
:::

:::tip Rozšírenie: Fast Retransmit
Po `Hallo` pošli rýchlo za sebou štyri alebo viac správ. Po strate paketu dostane klient tri *Dup ACK* po sebe — a okamžite odošle znova, bez čakania na svoj časovač. Tento postup sa nazýva **Fast Retransmit**.
:::

:::note
Skutočné implementácie TCP navyše prispôsobujú svoje tempo odosielania: ak sa pakety strácajú, sieť je pravdepodobne preťažená a odosielateľ sa spomalí (*riadenie zahltenia*). To presahuje rámec tohto kurzu.
:::
