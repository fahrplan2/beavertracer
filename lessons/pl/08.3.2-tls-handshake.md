# Handshake TLS

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Zanim zostanie wysłane pierwsze zaszyfrowane zapytanie, klient i serwer muszą się dogadać: co do metody, co do klucza sesji — a klient musi sprawdzić, z kim właściwie rozmawia. To nawiązywanie połączenia nazywa się **handshake TLS**.

## Przebieg na diagramie

Bez potwierdzeń TCP (`ACK`) handshake wygląda tak:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Co się tu dzieje — i który element z rozdziału 8.1 za tym stoi:

1. **Client Hello / Server Hello:** klient i serwer witają się, wymieniają liczby losowe i uzgadniają metody (w BeaverTracer: wymiana kluczy za pomocą **ECDHE**, podpis za pomocą **ECDSA**, szyfrowanie za pomocą **AES**).
2. **Certificate:** serwer wysyła swój **certyfikat**. Klient sprawdza podpis urzędu certyfikacji (CA), ważność i nazwę. Jeśli się to nie powiedzie, klient w tym miejscu przerywa — a przeglądarka wyświetla ostrzeżenie.
3. **Server Key Exchange:** serwer wysyła swoją **część Diffiego-Hellmana** — i **podpisuje** ją swoim kluczem prywatnym. Klient sprawdza podpis kluczem publicznym z certyfikatu. Dzięki temu wie: ta część naprawdę pochodzi od właściciela certyfikatu, a nie od atakującego typu man-in-the-middle.
4. **Client Key Exchange:** klient wysyła swoją część Diffiego-Hellmana. Teraz obie strony mogą obliczyć ten sam **klucz sesji** — bez tego, by kiedykolwiek został przesłany.
5. **Change Cipher Spec:** „Od teraz szyfruję.”
6. **Encrypted Handshake Message (Finished):** obie strony wysyłają — już w postaci zaszyfrowanej — sumę kontrolną ze wszystkich dotychczasowych komunikatów handshake'u. Jeśli atakujący coś po drodze zmienił, sumy kontrolne się nie zgadzają, a połączenie zostaje przerwane.
7. **Application Data:** od tego momentu płyną dane HTTP — zaszyfrowane symetrycznie za pomocą AES.

:::quiz match
Certificate -> Serwer potwierdza swoją tożsamość certyfikatem
Server Key Exchange -> Podpisana część Diffiego-Hellmana serwera
Client Key Exchange -> Część Diffiego-Hellmana klienta
Change Cipher Spec -> Od teraz dane są szyfrowane
Application Data -> Zaszyfrowane dane HTTP
:::

:::note
W śladzie widzisz **dwa** połączenia TLS jedno po drugim: przeglądarka najpierw pobiera stronę, a potem nawiązuje nowe połączenie dla arkusza stylów `style.css`. Każde połączenie dostaje własny handshake i własny klucz sesji. Prawdziwe przeglądarki utrzymują połączenia otwarte i dzięki temu oszczędzają część tego nakładu pracy. Nowsza wersja **TLS 1.3** poza tym potrzebuje mniej komunikatów niż pokazany tutaj TLS 1.2.
:::

:::tip Zapamiętaj
Podczas **handshake'u TLS** serwer potwierdza swoją tożsamość **certyfikatem**, obie strony uzgadniają **klucz sesji** za pomocą **Diffiego-Hellmana** (serwer **podpisuje** swoją część), a dzięki komunikatowi **Finished** obie sprawdzają, że nikt nie zmienił handshake'u. Potem dane są przesyłane jako **Application Data**, zaszyfrowane symetrycznie.
:::
