# TLS handshake

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Преди да бъде изпратена първата криптирана заявка, клиентът и сървърът трябва да се споразумеят: за метод, за сесиен ключ — и клиентът трябва да провери с кого разговаря. Това установяване на връзка се нарича **TLS handshake**.

## Последователността в диаграма

Без TCP потвържденията (`ACK`) handshake изглежда така:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Какво се случва при това — и кой градивен елемент от раздел 8.1 стои зад него:

1. **Client Hello / Server Hello:** Клиентът и сървърът се поздравяват, обменят случайни числа и се договарят за методите (в BeaverTracer: обмен на ключове с **ECDHE**, подпис с **ECDSA**, криптиране с **AES**).
2. **Certificate:** Сървърът изпраща своя **сертификат**. Клиентът проверява подписа на CA, валидността и имената. Ако проверката не успее, той прекъсва тук — и браузърът показва предупреждение.
3. **Server Key Exchange:** Сървърът изпраща своя **дял на Diffie-Hellman** — и го **подписва** със своя личен ключ. Клиентът проверява подписа с публичния ключ от сертификата. Така той знае: този дял наистина идва от притежателя на сертификата, а не от Man-in-the-Middle.
4. **Client Key Exchange:** Клиентът изпраща своя дял на Diffie-Hellman. Сега и двамата могат да изчислят един и същ **сесиен ключ** — без той някога да е бил предаван.
5. **Change Cipher Spec:** „От сега нататък криптирам."
6. **Encrypted Handshake Message (Finished):** И двете страни изпращат — вече криптирана — контролна сума за всички досегашни съобщения от handshake. Ако нападател е променил нещо по пътя, контролните суми няма да съвпаднат и връзката се прекъсва.
7. **Application Data:** Оттук нататък текат HTTP данните — симетрично криптирани с AES.

:::quiz match
Certificate -> Сървърът се идентифицира със своя сертификат
Server Key Exchange -> Подписан дял на Diffie-Hellman на сървъра
Client Key Exchange -> Дял на Diffie-Hellman на клиента
Change Cipher Spec -> От сега нататък се криптира
Application Data -> Криптирани HTTP данни
:::

:::note
В Trace виждаш **две** TLS връзки една след друга: браузърът първо изтегля страницата и после установява нова връзка за стиловия файл `style.css`. Всяка връзка получава собствен handshake и собствен сесиен ключ. Истинските браузъри държат връзките отворени и така си спестяват част от тази работа. По-новата версия **TLS 1.3** освен това се справя с по-малко съобщения от показания тук TLS 1.2.
:::

:::tip Запомни
При **TLS handshake** сървърът се идентифицира със своя **сертификат**, двете страни договарят **сесиен ключ** чрез **Diffie-Hellman** (сървърът **подписва** своя дял), а с **Finished** и двете проверяват, че никой не е променил handshake. След това данните се предават като **Application Data**, симетрично криптирани.
:::
