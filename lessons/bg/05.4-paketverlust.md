# Когато пакетите се губят

:::goal
**Цел на обучението:** Можеш да наблюдаваш в Tracer и да обясниш как TCP забелязва изгубени данни, изпраща ги повторно и възстановява реда.
:::

В тази симулация кабелът е подготвен: **вторият пакет с данни** от Client-PC към сървъра се губи. (Настройката ще намериш, като в режим на изпълнение щракнеш върху кабела: **Целенасочена загуба на пакети**.)

## Експериментът

1. Премини в режим на изпълнение :fa-play: **Стартиране**, отвори на **Client-PC** **Прост TCP клиент** и го свържи с `192.168.0.20`, порт `5000`.
2. Изпрати последователно три съобщения: `Hallo`, после `Welt`, после `!`.
3. Наблюдавай прозореца на чата: ехото на `Hallo` идва веднага. А другите две?
4. Изчакай няколко секунди. След това в режим :fa-magnifying-glass: **Проследяване** отвори trace за **сървъра** (получателя), интерфейс `eth0`.

:::quiz mc
Какво се случва с ехото на `Welt` и `!`?
- [ ] Ехото на `!` идва веднага, а `Welt` липсва завинаги
- [x] И двете идват едва след няколко секунди — заедно и в правилния ред
- [ ] Нито едно от двете не пристига изобщо
:::

## Какво показва Tracer

При сървъра пакетът с `Welt` липсва — нали се е загубил. Затова в колоната **Info** ще намериш три означения в квадратни скоби:

| Означение | Какво се е случило |
|---|---|
| `[TCP Previous segment not captured]` | Пакетът с `!` пристига, но преди него липсват байтове — **празнина**. |
| `[TCP Dup ACK …]` | Сървърът потвърждава още веднъж същия номер като преди (*duplicate ACK*): „Все още чакам байт 8.“ |
| `[TCP Retransmission]` | Клиентът изпраща `Welt` **още веднъж**. |

:::quiz short
Какъв пореден номер (`Seq`) има пакетът, маркиран с `[TCP Retransmission]`?
= 8
:::

:::quiz short
Какъв номер за потвърждение (`Ack`) изпраща сървърът непосредствено след повторното предаване?
= 17
:::

:::quiz mc
Защо след повторното предаване сървърът потвърждава веднага до байт 17 — а не само до края на `Welt`?
- [x] Той вече е получил `!` и го е задържал — с `Welt` празнината е запълнена, сега всичко до байт 16 е налице
- [ ] Клиентът е изпратил `Welt` и `!` още веднъж заедно
- [ ] Номерата за потвърждение винаги се закръглят
:::

:::evaluate
Провери отговорите
:::

В диаграмата на комуникацията това изглежда така — прекъснатата стрелка с ✕ е изгубеният пакет:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Какво стои зад това

Клиентът пази всеки изпратен пакет, докато бъде потвърден, и за целта стартира **таймер**. Ако потвърждението закъснее твърде дълго, той изпраща данните отново — **повторно предаване** (*Retransmission*).

Сървърът потвърждава винаги само до **първата празнина**. Данните, които пристигат след нея (тук `!`), той задържа, докато празнината бъде запълнена. Едва тогава предава всичко на програмата в правилния ред — затова ехото на `Welt` и `!` дойде заедно.

:::tip Запомни
TCP разпознава загубите по **липсващите потвърждения**: получателят потвърждава винаги само до първата празнина. Ако потвърждението не дойде, подателят изпраща данните **отново** след изтичане на таймер (*Retransmission*). Всичко, което пристигне след празнина, получателят задържа — така данните стигат до програмата **пълни и в правилния ред**.
:::

:::tip Задълбочаване: Fast Retransmit
След `Hallo` изпрати бързо едно след друго четири или повече съобщения. След изгубения пакет клиентът получава три *Dup ACK* поредни — и изпраща веднага отново, без да чака своя таймер. Този метод се нарича **Fast Retransmit**.
:::

:::note
Реалните имплементации на TCP освен това нагаждат скоростта си на изпращане: ако пакети се губят, мрежата вероятно е претоварена и подателят забавя (*контрол на задръстването*). Това надхвърля рамките на този курс.
:::
