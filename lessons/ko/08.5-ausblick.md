# 요약과 전망

## 구성 요소 한눈에 보기

| 구성 요소 | 보안 목표 | 예시 |
|---|---|---|
| **대칭 암호화** | 기밀성 | AES가 HTTPS 연결의 데이터를 암호화한다 |
| **비대칭 암호화** | 기밀성, 키 교환 | Diffie-Hellman, RSA |
| **해시값** | 무결성 | 다운로드 파일의 SHA-256 체크섬 |
| **디지털 서명** | 인증성, 무결성 | 서버가 자신의 Diffie-Hellman 값에 서명한다 |
| **인증서** | 인증성 | 이 키가 `www.biberbank.de`의 것임을 확인해 준다 |

## 여러 곳에서 쓰이는 같은 원리

HTTPS에서 배운 내용은 다른 많은 기술에도 들어 있다.

- **WLAN (WPA2/WPA3):** 3.3.2장에서는 통신 범위 안의 모든 장치가 내용을 엿볼 수 있었다. WPA2나 WPA3를 사용하면 모든 무선 프레임이 AES로 암호화된다. 또한 WPA3는 키를 협상하는 방식 덕분에, 도청자가 WLAN 비밀번호를 알고 있어도 예전에 캡처한 통신 내용을 복호화할 수 없다.
- **SSH:** 6.6장에서 다룬 암호화된 원격 관리이다. 인증서 대신 클라이언트가 처음 연결할 때 서버 키의 **지문**을 저장해 두고, 나중에 그 지문이 바뀌면 경고한다.
- **VPN:** 인터넷을 통과하는 암호화된 터널로, 예를 들어 학교나 회사 네트워크에 접속할 때 쓴다. 이 내용은 10장에서 다룬다.
- **메신저:** Signal, WhatsApp 등은 **종단 간(End-to-End)** 암호화를 사용한다. 서비스 운영자조차 메시지를 읽을 수 없다.

:::note
대형 **양자 컴퓨터**는 언젠가 큰 수를 소인수분해하여 RSA와 Diffie-Hellman을 깨뜨릴 수 있다. 그래서 오늘날 이미 새로운 **양자 내성** 방식이 도입되고 있다. 긴 키를 사용하는 AES 같은 대칭 방식은 앞으로도 안전하다고 여겨진다.
:::

## 스스로 점검하기

:::quiz mc
HTTPS에서 실제 데이터는 … 로 암호화된다.
- [ ] RSA, 가장 안전하기 때문이다
- [x] AES 같은 대칭 방식과 협상된 세션 키
- [ ] 서버의 개인 키
:::

:::quiz mc
너는 `https://www.biberbank.de/`에 접속했는데 브라우저가 "이 인증서는 `www.gewinn-biber.de`에 대해 발급되었습니다"라고 알린다. 어떻게 해야 할까?
- [ ] "그래도 계속"을 클릭한다 — 어쨌든 연결은 암호화되어 있으니까
- [x] 중단한다 — 브라우저가 은행과 통신하고 있지 않을 수도 있다
- [ ] `http://`로 접속한다. 그러면 경고가 나오지 않는다
:::

:::quiz multi
다음 중 맞는 설명은 무엇일까?
- [x] 데이터가 아주 조금만 바뀌어도 해시값은 완전히 달라진다
- [x] 서명은 개인 키로 만들고 공개 키로 검증한다
- [x] 루트 CA는 브라우저 또는 운영체제에 미리 설치되어 있다
- [ ] HTTPS에서는 도청자가 서버의 IP 주소조차 볼 수 없다
- [ ] SMTPS는 메일 서버에 저장된 메일도 암호화한다
:::

:::quiz fill

:::
