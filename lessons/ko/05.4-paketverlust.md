# 패킷이 손실될 때

:::goal
**학습 목표:** 트레이서에서 TCP가 손실된 데이터를 어떻게 알아채고, 다시 전송하고, 순서를 복원하는지 관찰하고 설명할 수 있다.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

이 시뮬레이션에서는 케이블에 장난이 되어 있다. 클라이언트 PC에서 서버로 가는 **데이터가 담긴 두 번째 패킷**이 손실된다. (이 설정은 실행 모드에서 케이블을 클릭하면 찾을 수 있다: **대상 패킷 손실**.)

## 실험

1. :fa-play: **실행** 모드로 전환하고, **Client-PC**에서 **단순 TCP 클라이언트**를 열어 `192.168.0.20`, 포트 `5000`으로 연결한다.
2. 메시지 세 개를 차례로 보낸다: `Hallo`, 그다음 `Welt`, 그다음 `!`.
3. 채팅 창을 관찰한다: `Hallo`의 에코는 바로 도착한다. 나머지 두 개는 어떨까?
4. 몇 초 기다린다. 그런 다음 :fa-magnifying-glass: **추적** 모드에서 **서버**(수신자)의 인터페이스 `eth0`에 대한 트레이스를 연다.

:::quiz mc
`Welt`와 `!`의 에코는 어떻게 될까?
- [ ] `!`의 에코는 바로 도착하고, `Welt`는 영원히 오지 않는다
- [x] 둘 다 몇 초 뒤에야 도착한다 — 함께, 그리고 올바른 순서로
- [ ] 둘 다 끝내 도착하지 않는다
:::

## 트레이서가 보여주는 것

서버에는 `Welt`가 담긴 패킷이 없다 — 손실되었으니까. 대신 **Info** 열에서 대괄호로 된 힌트 세 가지를 찾을 수 있다:

| 힌트 | 일어난 일 |
|---|---|
| `[TCP Previous segment not captured]` | `!`가 담긴 패킷은 도착했지만, 그 앞의 바이트가 비어 있다 — **공백**이다. |
| `[TCP Dup ACK …]` | 서버가 이전과 같은 번호를 한 번 더 확인한다(*duplicate ACK*): "아직 바이트 8을 기다리고 있어." |
| `[TCP Retransmission]` | 클라이언트가 `Welt`를 **한 번 더** 보낸다. |

:::quiz short
`[TCP Retransmission]`으로 표시된 패킷의 순서 번호(`Seq`)는 얼마인가?
= 8
:::

:::quiz short
재전송 직후 서버가 보내는 확인 응답 번호(`Ack`)는 얼마인가?
= 17
:::

:::quiz mc
서버는 재전송 후 왜 `Welt`의 끝까지만이 아니라 바이트 17까지 한 번에 확인 응답을 보낼까?
- [x] 서버가 `!`를 이미 받아서 보관하고 있었고, `Welt`가 도착하면서 공백이 메워져 바이트 16까지 모두 갖춰졌기 때문이다
- [ ] 클라이언트가 `Welt`와 `!`를 함께 다시 보냈기 때문이다
- [ ] 확인 응답 번호는 항상 반올림되기 때문이다
:::

:::evaluate
답 확인
:::

시퀀스 다이어그램으로 보면 다음과 같다 — ✕가 있는 점선 화살표가 손실된 패킷이다:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## 배경 원리

클라이언트는 보낸 패킷을 확인 응답을 받을 때까지 보관하고, 이를 위해 **타이머**를 시작한다. 확인 응답이 너무 오래 오지 않으면 데이터를 다시 보낸다 — 이것이 **재전송**(*Retransmission*)이다.

서버는 항상 **첫 번째 공백**까지만 확인 응답을 보낸다. 그 뒤에 도착한 데이터(여기서는 `!`)는 공백이 채워질 때까지 보관한다. 공백이 채워진 뒤에야 모든 데이터를 올바른 순서로 프로그램에 넘긴다 — 그래서 `Welt`와 `!`의 에코가 함께 도착한 것이다.

:::tip 핵심 정리
TCP는 **빠진 확인 응답**으로 손실을 알아챈다: 수신자는 항상 첫 번째 공백까지만 확인 응답을 보낸다. 확인 응답이 오지 않으면 송신자는 타이머가 만료된 뒤 데이터를 **다시** 보낸다(*Retransmission*). 공백 뒤에 도착한 데이터는 수신자가 보관한다 — 그래서 데이터는 **빠짐없이, 올바른 순서로** 프로그램에 도달한다.
:::

:::tip 심화: Fast Retransmit
`Hallo` 다음에 메시지 네 개 이상을 빠르게 연달아 보내 보자. 패킷이 손실된 뒤 클라이언트는 *Dup ACK*를 연속으로 세 번 받고 — 타이머를 기다리지 않고 즉시 다시 보낸다. 이 방식을 **Fast Retransmit**이라고 한다.
:::

:::note
실제 TCP 구현은 전송 속도도 조절한다: 패킷이 손실되면 네트워크가 과부하 상태일 가능성이 크므로 송신자는 속도를 늦춘다(*혼잡 제어*). 이는 이 강의의 범위를 벗어난다.
:::
