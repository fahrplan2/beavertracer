# Der TLS-Handshake

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Bevor die erste verschlüsselte Anfrage verschickt wird, müssen sich Client und Server einigen: auf ein Verfahren, auf einen Sitzungsschlüssel — und der Client muss prüfen, mit wem er spricht. Dieser Verbindungsaufbau heißt **TLS-Handshake**.

## Beobachten

Rufe auf dem **Client-PC** `https://www.beaver-schule.de/` auf (falls noch nicht geschehen), öffne einen Trace für den **Client-PC** und filtere mit `tls`.

## Der Ablauf im Diagramm

Ohne die TCP-Bestätigungen (`ACK`) sieht der Handshake so aus:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Was dabei passiert — und welcher Baustein aus Abschnitt 8.1 dahintersteckt:

1. **Client Hello / Server Hello:** Client und Server begrüßen sich, tauschen Zufallszahlen aus und einigen sich auf die Verfahren (in BeaverTracer: Schlüsselaustausch mit **ECDHE**, Signatur mit **ECDSA**, Verschlüsselung mit **AES**).
2. **Certificate:** Der Server schickt sein **Zertifikat**. Der Client prüft Signatur der CA, Gültigkeit und Namen. Schlägt das fehl, bricht er hier ab — und der Browser zeigt eine Warnung.
3. **Server Key Exchange:** Der Server schickt seinen **Diffie-Hellman-Anteil** — und **signiert** ihn mit seinem privaten Schlüssel. Der Client prüft die Signatur mit dem öffentlichen Schlüssel aus dem Zertifikat. So weiß er: Dieser Anteil kommt wirklich vom Inhaber des Zertifikats, nicht von einem Man-in-the-Middle.
4. **Client Key Exchange:** Der Client schickt seinen Diffie-Hellman-Anteil. Jetzt können beide denselben **Sitzungsschlüssel** berechnen — ohne dass er je übertragen wurde.
5. **Change Cipher Spec:** „Ab jetzt verschlüssele ich.“
6. **Encrypted Handshake Message (Finished):** Beide Seiten schicken — schon verschlüsselt — eine Prüfsumme über alle bisherigen Handshake-Nachrichten. Hat ein Angreifer unterwegs etwas verändert, passen die Prüfsummen nicht, und die Verbindung wird abgebrochen.
7. **Application Data:** Ab hier fließen die HTTP-Daten — symmetrisch verschlüsselt mit AES.

:::quiz match
Certificate -> Der Server weist sich mit seinem Zertifikat aus
Server Key Exchange -> Signierter Diffie-Hellman-Anteil des Servers
Client Key Exchange -> Diffie-Hellman-Anteil des Clients
Change Cipher Spec -> Ab jetzt wird verschlüsselt
Application Data -> Verschlüsselte HTTP-Daten
:::

:::note
Im Trace siehst du **zwei** TLS-Verbindungen nacheinander: Der Browser holt erst die Seite und baut dann eine neue Verbindung für das Stylesheet `style.css` auf. Jede Verbindung bekommt einen eigenen Handshake und einen eigenen Sitzungsschlüssel. Echte Browser halten Verbindungen offen und sparen sich so einen Teil dieses Aufwands. Die neuere Version **TLS 1.3** kommt außerdem mit weniger Nachrichten aus als das hier gezeigte TLS 1.2.
:::

:::tip Merksatz
Beim **TLS-Handshake** weist sich der Server mit seinem **Zertifikat** aus, beide Seiten handeln per **Diffie-Hellman** einen **Sitzungsschlüssel** aus (der Server **signiert** seinen Anteil), und mit **Finished** prüfen beide, dass niemand den Handshake verändert hat. Danach werden die Daten als **Application Data** symmetrisch verschlüsselt übertragen.
:::
