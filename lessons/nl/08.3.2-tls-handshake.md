# De TLS-handshake

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Voordat het eerste versleutelde verzoek wordt verstuurd, moeten client en server het eens worden: over een methode, over een sessiesleutel — en de client moet controleren met wie hij praat. Deze verbindingsopbouw heet de **TLS-handshake**.

## Observeren

Open op de **Client-PC** `https://www.beaver-schule.de/` (als je dat nog niet hebt gedaan), open een trace voor de **Client-PC** en filter met `tls`.

## Het verloop in het diagram

Zonder de TCP-bevestigingen (`ACK`) ziet de handshake er zo uit:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Wat hierbij gebeurt — en welke bouwsteen uit paragraaf 8.1 erachter zit:

1. **Client Hello / Server Hello:** Client en server begroeten elkaar, wisselen willekeurige getallen uit en komen overeen welke methoden ze gebruiken (in BeaverTracer: sleuteluitwisseling met **ECDHE**, handtekening met **ECDSA**, versleuteling met **AES**).
2. **Certificate:** De server stuurt zijn **certificaat**. De client controleert de handtekening van de CA, de geldigheid en de namen. Als dat mislukt, stopt hij hier — en toont de browser een waarschuwing.
3. **Server Key Exchange:** De server stuurt zijn **Diffie-Hellman-deel** — en **ondertekent** dit met zijn privésleutel. De client controleert de handtekening met de publieke sleutel uit het certificaat. Zo weet hij: dit deel komt echt van de houder van het certificaat, niet van een man-in-the-middle.
4. **Client Key Exchange:** De client stuurt zijn Diffie-Hellman-deel. Nu kunnen beiden dezelfde **sessiesleutel** berekenen — zonder dat die ooit is verzonden.
5. **Change Cipher Spec:** "Vanaf nu versleutel ik."
6. **Encrypted Handshake Message (Finished):** Beide kanten sturen — al versleuteld — een controlesom over alle tot dan toe verstuurde handshakeberichten. Als een aanvaller onderweg iets heeft gewijzigd, komen de controlesommen niet overeen en wordt de verbinding verbroken.
7. **Application Data:** Vanaf hier stromen de HTTP-gegevens — symmetrisch versleuteld met AES.

:::quiz match
Certificate -> De server legitimeert zich met zijn certificaat
Server Key Exchange -> Ondertekend Diffie-Hellman-deel van de server
Client Key Exchange -> Diffie-Hellman-deel van de client
Change Cipher Spec -> Vanaf nu wordt er versleuteld
Application Data -> Versleutelde HTTP-gegevens
:::

:::note
In de trace zie je **twee** TLS-verbindingen na elkaar: de browser haalt eerst de pagina op en bouwt daarna een nieuwe verbinding op voor de stylesheet `style.css`. Elke verbinding krijgt een eigen handshake en een eigen sessiesleutel. Echte browsers houden verbindingen open en besparen zo een deel van deze inspanning. De nieuwere versie **TLS 1.3** komt bovendien met minder berichten toe dan het hier getoonde TLS 1.2.
:::

:::tip Onthoud
Bij de **TLS-handshake** legitimeert de server zich met zijn **certificaat**, onderhandelen beide kanten via **Diffie-Hellman** over een **sessiesleutel** (de server **ondertekent** zijn deel), en controleren beiden met **Finished** dat niemand de handshake heeft gewijzigd. Daarna worden de gegevens als **Application Data** symmetrisch versleuteld verzonden.
:::
