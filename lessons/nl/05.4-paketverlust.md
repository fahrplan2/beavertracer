# Wanneer pakketten verloren gaan

:::goal
**Leerdoel:** Je kunt in de tracer waarnemen en uitleggen hoe TCP verloren data opmerkt, opnieuw verzendt en de volgorde herstelt.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

In deze simulatie is de kabel voorbereid: het **tweede pakket met data** van de Client-PC naar de Server gaat verloren. (Je vindt de instelling als je in de Uitvoermodus op de kabel klikt: **Gerichte pakketverlies**.)

## Het experiment

1. Schakel over naar de :fa-play: **Uitvoeren**-modus, open op de **Client-PC** de **Eenvoudige TCP-client** en verbind deze met `192.168.0.20`, poort `5000`.
2. Stuur na elkaar drie berichten: `Hallo`, dan `Welt`, dan `!`.
3. Bekijk het chatvenster: het echo van `Hallo` komt meteen. En de andere twee?
4. Wacht een paar seconden. Open dan in de :fa-magnifying-glass: **Tracering**-modus een trace voor de **Server** (de ontvanger), aansluiting `eth0`.

:::quiz mc
Wat gebeurt er met de echo's van `Welt` en `!`?
- [ ] De echo van `!` komt meteen, `Welt` ontbreekt voorgoed
- [x] Beide komen pas na enkele seconden — samen en in de juiste volgorde
- [ ] Geen van beide komt ooit aan
:::

## Wat de tracer laat zien

Bij de server ontbreekt het pakket met `Welt` — het is immers verloren gegaan. In plaats daarvan vind je in de **Info**-kolom drie aanwijzingen tussen blokhaken:

| Aanwijzing | Wat er is gebeurd |
|---|---|
| `[TCP Previous segment not captured]` | Het pakket met `!` komt aan, maar daarvoor ontbreken bytes — een **gat**. |
| `[TCP Dup ACK …]` | De server bevestigt nogmaals hetzelfde nummer als daarvoor (*duplicate ACK*): „Ik wacht nog steeds op byte 8.” |
| `[TCP Retransmission]` | De client stuurt `Welt` **nog een keer**. |

:::quiz short
Welk volgnummer (`Seq`) heeft het pakket dat is gemarkeerd met `[TCP Retransmission]`?
= 8
:::

:::quiz short
Welk bevestigingsnummer (`Ack`) stuurt de server direct na de hertransmissie?
= 17
:::

:::quiz mc
Waarom bevestigt de server na de hertransmissie meteen tot en met byte 17 — en niet alleen tot het einde van `Welt`?
- [x] Hij had `!` al ontvangen en vastgehouden — met `Welt` is het gat gedicht, nu is alles tot en met byte 16 aanwezig
- [ ] De client heeft `Welt` en `!` nog een keer samen verstuurd
- [ ] Bevestigingsnummers worden altijd afgerond
:::

Antwoorden controleren
:::

In het sequentiediagram ziet het er zo uit — de gestippelde pijl met de ✕ is het verloren pakket:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Wat erachter zit

De client bewaart elk verzonden pakket totdat het bevestigd is, en start daarvoor een **timer**. Blijft de bevestiging te lang uit, dan verzendt hij de data opnieuw — een **hertransmissie** (*retransmission*).

De server bevestigt altijd alleen tot aan het **eerste gat**. Data die daarna aankomt (hier `!`), houdt hij vast totdat het gat is gevuld. Pas dan geeft hij alles in de juiste volgorde door aan het programma — daarom kwamen de echo's van `Welt` en `!` samen.

:::tip Onthoud
TCP herkent verlies aan **ontbrekende bevestigingen**: de ontvanger bevestigt altijd alleen tot aan het eerste gat. Blijft de bevestiging uit, dan verzendt de afzender de data na het verstrijken van een timer **opnieuw** (*retransmission*). Wat na een gat aankomt, houdt de ontvanger vast — zo bereikt de data het programma **volledig en in de juiste volgorde**.
:::

:::tip Verdieping: Fast Retransmit
Stuur na `Hallo` vier of meer berichten snel achter elkaar. Na het verloren pakket krijgt de client dan drie *Dup ACKs* achter elkaar — en verzendt meteen opnieuw, zonder op zijn timer te wachten. Dit mechanisme heet **Fast Retransmit**.
:::

:::note
Echte TCP-implementaties passen bovendien hun verzendtempo aan: gaan er pakketten verloren, dan is het netwerk waarschijnlijk overbelast en wordt de afzender langzamer (*congestiebeheersing*). Dat gaat verder dan deze cursus.
:::
