# The TLS Handshake

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Before the first encrypted request is sent, client and server have to agree: on a cipher, on a session key — and the client has to check who it's talking to. This connection setup is called the **TLS handshake**.

## The sequence in a diagram

Without the TCP acknowledgements (`ACK`), the handshake looks like this:

:::seq
mode: text
Client -> Server: Client Hello | random number, supported ciphers
Server -> Client: Server Hello | chosen cipher, random number
Server -> Client: Certificate | server certificate
Server -> Client: Server Key Exchange | DH share, signed
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | client's DH share
Client -> Server: Change Cipher Spec | encrypted from now on
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | encrypted from now on
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (encrypted)
Server -> Client: Application Data | web page (encrypted)
:::

What happens — and which building block from section 8.1 is behind it:

1. **Client Hello / Server Hello:** client and server greet each other, exchange random numbers and agree on the ciphers (in BeaverTracer: key exchange with **ECDHE**, signature with **ECDSA**, encryption with **AES**).
2. **Certificate:** the server sends its **certificate**. The client checks the CA's signature, validity and name. If that fails, it aborts here — and the browser shows a warning.
3. **Server Key Exchange:** the server sends its **Diffie-Hellman share** — and **signs** it with its private key. The client checks the signature with the public key from the certificate. So it knows: this share really comes from the certificate holder, not from a man-in-the-middle.
4. **Client Key Exchange:** the client sends its Diffie-Hellman share. Now both can calculate the same **session key** — without it ever being transmitted.
5. **Change Cipher Spec:** "From now on I encrypt."
6. **Encrypted Handshake Message (Finished):** both sides send — already encrypted — a checksum over all previous handshake messages. If an attacker changed anything on the way, the checksums don't match and the connection is aborted.
7. **Application Data:** from here on the HTTP data flows — symmetrically encrypted with AES.

:::quiz match

Server Key Exchange -> The server's signed Diffie-Hellman share
Client Key Exchange -> The client's Diffie-Hellman share
Change Cipher Spec -> Encryption starts now
Application Data -> Encrypted HTTP data
:::

:::note
In the trace you see **two** TLS connections in a row: the browser first fetches the page and then opens a new connection for the stylesheet `style.css`. Each connection gets its own handshake and its own session key. Real browsers keep connections open and save part of this effort. The newer version **TLS 1.3** also needs fewer messages than the TLS 1.2 shown here.
:::

:::tip Key point
In the **TLS handshake**, the server identifies itself with its **certificate**, both sides negotiate a **session key** via **Diffie-Hellman** (the server **signs** its share), and with **Finished** both check that nobody tampered with the handshake. After that, the data is transferred symmetrically encrypted as **Application Data**.
:::
