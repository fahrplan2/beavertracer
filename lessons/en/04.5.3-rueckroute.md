# Troubleshooting: the return route

:::sim
url=/sims/lesson-4.5.3.btsim
:::

The same setup as before: company A — router A — transit network — router B — company B. The administrator has entered the route to company B (`172.16.0.0/24` via `10.0.0.2`) on **Router A**. Still, Anna reports: Clara doesn't answer.

Find the fault and fix it.

<details>
<summary>Tip 1: Does Anna's ping arrive at all?</summary>

Ping Clara from Anna and open a trace for **Clara**. Does the ping arrive at her — and does she answer?
</details>

<details>
<summary>Tip 2: How far does traceroute get?</summary>

Enter `traceroute 172.16.0.10` on Anna. Up to which router do answers come back — and which router would have to forward Clara's replies to Anna?
</details>

<details>
<summary>Tip 3: Who knows which network?</summary>

Look at the routing table of **Router B**. Does it know where packets for `192.168.0.0/24` go?
</details>

:::task
title: Connection repaired?
Checks whether router B knows the way to company A and Anna reaches Clara. The simulation has to be running in Run mode for this.
check: hasRoute(5, "192.168.0.0/24")
check: pingOk(9, 11)
:::

## What was going on?

:::quiz multi
What did you observe while troubleshooting?
- [x] Anna's ping arrived at Clara, and Clara answered
- [x] The reply got stuck at router B because it didn't know company A
- [ ] Router A discarded Anna's ping
- [x] After router A, `traceroute` only showed `*`, even though the way there worked
:::

:::evaluate
Check answer
:::

:::tip Key point
Every connection needs a **way there and a way back**: every router on the path has to know *both* networks — the destination network and the sender's network. A missing **return route** is one of the most common routing faults. Careful: `traceroute` only shows from where on no answers come back — the fault can also be on the way back.
:::
