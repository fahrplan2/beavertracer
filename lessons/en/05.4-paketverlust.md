# When packets get lost

:::goal
**Learning goal:** You can observe in the tracer and explain how TCP notices lost data, sends it again and restores the order.
:::

:::sim

In this simulation the cable is prepared: the **second packet with data** from the Client-PC to the Server gets lost. (You find the setting when you click the cable in Run mode: **Targeted packet loss**.)

## The experiment

1. Switch to :fa-play: **Run** mode, open the **Simple TCP Client** on the **Client-PC** and connect it to `192.168.0.20`, port `5000`.
2. Send three messages one after the other: `Hallo`, then `Welt`, then `!`.
3. Watch the chat window: the echo of `Hallo` comes right away. And the other two?
4. Wait a few seconds. Then, in :fa-magnifying-glass: **Trace** mode, open a trace for the **Server** (the receiver), port `eth0`.

:::quiz mc
What happens to the echoes of `Welt` and `!`?
- [ ] The echo of `!` comes right away, `Welt` is missing forever
- [x] Both only come after a few seconds — together and in the right order
- [ ] Neither of them ever arrives
:::

## What the tracer shows

At the server, the packet with `Welt` is missing — it got lost, after all. Instead you find three hints in square brackets in the **Info** column:

| Hint | What happened |
|---|---|
| `[TCP Previous segment not captured]` | The packet with `!` arrives, but bytes before it are missing — a **gap**. |
| `[TCP Dup ACK …]` | The server confirms the same number as before once again (*duplicate ACK*): "I'm still waiting for byte 8." |
| `[TCP Retransmission]` | The client sends `Welt` **once more**. |

:::quiz short
Which sequence number (`Seq`) does the packet marked `[TCP Retransmission]` have?
= 8
:::

:::quiz short
Which acknowledgement number (`Ack`) does the server send directly after the retransmission?
= 17
:::

:::quiz mc
Why does the server confirm all the way to byte 17 after the retransmission — and not just to the end of `Welt`?
- [x] It had already received and held back `!` — with `Welt` the gap is closed, now everything up to byte 16 is there
- [ ] The client sent `Welt` and `!` together once more
- [ ] Acknowledgement numbers are always rounded
:::

Client-PC -> Server: ACK

## What's behind it

The client keeps every sent packet until it's confirmed, and starts a **timer** for it. If the acknowledgement takes too long, it sends the data again — a **retransmission**.

The server only ever confirms up to the **first gap**. Data that arrives after it (here `!`) is held back until the gap is filled. Only then does it pass everything to the program in the right order — that's why the echoes of `Welt` and `!` came together.

:::tip Key point
TCP recognises losses by **missing acknowledgements**: the receiver only ever confirms up to the first gap. If the acknowledgement doesn't come, the sender sends the data **again** after a timer runs out (*retransmission*). Whatever arrives after a gap is held back by the receiver — so the data reaches the program **completely and in the right order**.
:::

:::tip In depth: Fast Retransmit
After `Hallo`, send four or more messages quickly one after the other. After the lost packet, the client then gets three *Dup ACKs* in a row — and sends again immediately, without waiting for its timer. This procedure is called **Fast Retransmit**.
:::

:::note
Real TCP implementations also adapt their sending speed: if packets get lost, the network is probably overloaded and the sender slows down (*congestion control*). That goes beyond this course.
:::
