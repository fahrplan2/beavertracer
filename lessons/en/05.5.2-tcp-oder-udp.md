# TCP or UDP?

| | TCP | UDP |
|---|---|---|
| Connection | setup with three-way handshake, orderly teardown | none — every datagram stands on its own |
| Acknowledgements | yes (`ACK`) | no |
| Lost data | is sent again | stays lost |
| Order | is restored | not guaranteed |
| Header | at least 20 bytes | 8 bytes |
| Speed | somewhat slower, more packets | fast, little overhead |

When is less more?

- **Real time:** with video calls, internet telephony or online games every millisecond counts. A lost piece of sound that's delivered a second later is of no use to anyone — better a short crackle than a delay.
- **Short requests:** a **DNS** request ("Which IP address does `www.example.com` have?") fits into a single datagram, and so does the answer. A connection setup would triple the effort. If no answer comes, the program simply asks again.

Wherever every byte has to arrive — web pages, e-mails, downloads — TCP, on the other hand, is the right choice.

:::tip Key point
**TCP** is reliable, but more effort — for everything that has to arrive **completely** (web, e-mail, files). **UDP** is fast and lean, but without guarantees — for **real time** (telephony, video, games) and **short requests** like DNS.
:::
