# TLS handshake

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Než se odešle první šifrovaný požadavek, musí se klient a server dohodnout: na postupu, na klíči relace — a klient musí ověřit, s kým vlastně komunikuje. Toto navázání spojení se nazývá **TLS handshake**.

## Pozorování

Na **Client-PC** otevři `https://www.beaver-schule.de/` (pokud jsi to ještě neudělal), otevři trasování pro **Client-PC** a filtruj pomocí `tls`.

## Průběh v diagramu

Bez potvrzení TCP (`ACK`) vypadá handshake takto:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Co se přitom děje — a který stavební prvek z části 8.1 za tím stojí:

1. **Client Hello / Server Hello:** Klient a server se pozdraví, vymění si náhodná čísla a dohodnou se na postupech (v BeaverTraceru: výměna klíčů pomocí **ECDHE**, podpis pomocí **ECDSA**, šifrování pomocí **AES**).
2. **Certificate:** Server pošle svůj **certifikát**. Klient zkontroluje podpis certifikační autority, platnost a jméno. Pokud kontrola selže, klient zde spojení ukončí — a prohlížeč zobrazí varování.
3. **Server Key Exchange:** Server pošle svůj **podíl Diffie-Hellman** — a **podepíše** ho svým soukromým klíčem. Klient ověří podpis veřejným klíčem z certifikátu. Tak ví: Tento podíl skutečně pochází od držitele certifikátu, a ne od útočníka typu Man-in-the-Middle.
4. **Client Key Exchange:** Klient pošle svůj podíl Diffie-Hellman. Nyní mohou oba vypočítat stejný **klíč relace** — aniž by byl někdy přenesen.
5. **Change Cipher Spec:** „Od teď šifruji.“
6. **Encrypted Handshake Message (Finished):** Obě strany pošlou — již šifrovaně — kontrolní součet ze všech dosavadních zpráv handshaku. Pokud útočník cestou něco změnil, kontrolní součty nesouhlasí a spojení se přeruší.
7. **Application Data:** Od tohoto okamžiku proudí data HTTP — symetricky šifrovaná pomocí AES.

:::quiz match
Certificate -> Server se prokazuje svým certifikátem
Server Key Exchange -> Podepsaný podíl Diffie-Hellman serveru
Client Key Exchange -> Podíl Diffie-Hellman klienta
Change Cipher Spec -> Od teď se šifruje
Application Data -> Šifrovaná data HTTP
:::

:::note
V trasování uvidíš **dvě** spojení TLS za sebou: Prohlížeč nejprve načte stránku a potom naváže nové spojení pro stylopis `style.css`. Každé spojení má vlastní handshake a vlastní klíč relace. Skutečné prohlížeče udržují spojení otevřená a část této režie si tak ušetří. Novější verze **TLS 1.3** navíc vystačí s menším počtem zpráv než zde ukázané TLS 1.2.
:::

:::tip Zapamatuj si
Při **TLS handshaku** se server prokazuje svým **certifikátem**, obě strany si pomocí **Diffie-Hellmanu** dohodnou **klíč relace** (server svůj podíl **podepíše**) a pomocí **Finished** obě ověří, že nikdo handshake nezměnil. Poté se data přenášejí jako **Application Data** symetricky šifrovaná.
:::
