# Když se pakety ztrácejí

:::goal
**Cíl výuky:** Dokážeš v Traceru pozorovat a vysvětlit, jak TCP zjistí ztracená data, odešle je znovu a obnoví jejich pořadí.
:::

V této simulaci je kabel připravený: **druhý paket s daty** od Client-PC k serveru se ztratí. (Nastavení najdeš, když v režimu spuštění klikneš na kabel: **Cílená ztráta paketů**.)

## Experiment

1. Přepni do režimu :fa-play: **Spustit**, otevři na **Client-PC** **Jednoduchý TCP klient** a připoj ho k `192.168.0.20`, port `5000`.
2. Odešli postupně tři zprávy: `Hallo`, potom `Welt`, potom `!`.
3. Sleduj okno chatu: Echo zprávy `Hallo` přijde okamžitě. A ty další dvě?
4. Počkej pár sekund. Potom v režimu :fa-magnifying-glass: **Trasování** otevři trace pro **Server** (příjemce), rozhraní `eth0`.

:::quiz mc
Co se stane s echy zpráv `Welt` a `!`?
- [ ] Echo zprávy `!` přijde okamžitě, `Welt` chybí navždy
- [x] Obě přijdou až po několika sekundách — společně a ve správném pořadí
- [ ] Ani jedno z nich nikdy nedorazí
:::

## Co ukazuje Tracer

U serveru chybí paket se zprávou `Welt` — vždyť se ztratil. Místo toho najdeš ve sloupci **Info** tři poznámky v hranatých závorkách:

| Poznámka | Co se stalo |
|---|---|
| `[TCP Previous segment not captured]` | Paket se zprávou `!` dorazí, ale před ním chybí bajty — **mezera**. |
| `[TCP Dup ACK …]` | Server znovu potvrdí stejné číslo jako předtím (*duplicate ACK*): „Pořád čekám na bajt 8.“ |
| `[TCP Retransmission]` | Klient pošle `Welt` **ještě jednou**. |

:::quiz short
Jaké sekvenční číslo (`Seq`) má paket označený `[TCP Retransmission]`?
= 8
:::

:::quiz short
Jaké potvrzovací číslo (`Ack`) pošle server hned po opakovaném odeslání?
= 17
:::

:::quiz mc
Proč server po opakovaném odeslání potvrdí rovnou až po bajt 17 — a ne jen do konce zprávy `Welt`?
- [x] Zprávu `!` už přijal a zadržel — se zprávou `Welt` je mezera zaplněná, teď je tu všechno až po bajt 16
- [ ] Klient poslal `Welt` a `!` ještě jednou společně
- [ ] Potvrzovací čísla se vždy zaokrouhlují
:::

:::evaluate
Zkontrolovat odpovědi
:::

V sekvenčním diagramu to vypadá takto — přerušovaná šipka s ✕ je ztracený paket:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Co za tím stojí

Klient uchovává každý odeslaný paket, dokud není potvrzen, a pro každý spustí **časovač**. Pokud potvrzení nepřijde včas, odešle data znovu — **opakované odeslání** (*retransmission*).

Server potvrzuje vždy jen až po **první mezeru**. Data, která dorazí po ní (tady `!`), zadrží, dokud se mezera nezaplní. Teprve potom předá všechno programu ve správném pořadí — proto přišla echa zpráv `Welt` a `!` společně.

:::tip Zapamatuj si
TCP pozná ztráty podle **chybějících potvrzení**: příjemce potvrzuje vždy jen až po první mezeru. Pokud potvrzení nepřijde, odesílatel po uplynutí časovače data **odešle znovu** (*retransmission*). Co dorazí po mezeře, příjemce zadrží — díky tomu data dorazí k programu **kompletní a ve správném pořadí**.
:::

:::tip Rozšíření: Fast Retransmit
Pošli po zprávě `Hallo` rychle za sebou čtyři nebo více zpráv. Po ztraceném paketu pak klient dostane tři *Dup ACK* po sobě — a okamžitě odešle data znovu, aniž by čekal na svůj časovač. Tento postup se nazývá **Fast Retransmit**.
:::

:::note
Skutečné implementace TCP navíc přizpůsobují rychlost odesílání: Pokud se pakety ztrácejí, je síť pravděpodobně přetížená a odesílatel zpomalí (*řízení zahlcení*). To už přesahuje rámec tohoto kurzu.
:::
