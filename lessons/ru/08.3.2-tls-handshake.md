# TLS-рукопожатие

:::sim

Прежде чем будет отправлен первый зашифрованный запрос, клиент и сервер должны договориться: о методе, о сеансовом ключе — а клиент должен проверить, с кем он вообще общается. Это установление соединения называется **TLS-рукопожатием** (**TLS-Handshake**).

## Ход рукопожатия на диаграмме

Без подтверждений TCP (`ACK`) рукопожатие выглядит так:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Что при этом происходит — и какой строительный блок из раздела 8.1 за этим стоит:

1. **Client Hello / Server Hello:** клиент и сервер приветствуют друг друга, обмениваются случайными числами и договариваются о методах (в BeaverTracer: обмен ключами с помощью **ECDHE**, подпись с помощью **ECDSA**, шифрование с помощью **AES**).
2. **Certificate:** сервер отправляет свой **сертификат**. Клиент проверяет подпись удостоверяющего центра (CA), срок действия и имя. Если проверка не удалась, клиент прерывает соединение на этом шаге — и браузер показывает предупреждение.
3. **Server Key Exchange:** сервер отправляет свою **долю Диффи — Хеллмана** и **подписывает** её своим закрытым ключом. Клиент проверяет подпись с помощью открытого ключа из сертификата. Так он знает: эта доля действительно пришла от владельца сертификата, а не от злоумышленника, выполняющего атаку «человек посередине» (Man-in-the-Middle).
4. **Client Key Exchange:** клиент отправляет свою долю Диффи — Хеллмана. Теперь обе стороны могут вычислить один и тот же **сеансовый ключ** — при этом он ни разу не передавался.
5. **Change Cipher Spec:** «С этого момента я шифрую».
6. **Encrypted Handshake Message (Finished):** обе стороны отправляют — уже в зашифрованном виде — контрольную сумму всех предыдущих сообщений рукопожатия. Если злоумышленник что-то изменил по пути, контрольные суммы не совпадут, и соединение будет разорвано.
7. **Application Data:** отсюда начинают передаваться данные HTTP — с симметричным шифрованием AES.

:::quiz match
Certificate -> Сервер подтверждает свою подлинность сертификатом
Server Key Exchange -> Подписанная доля Диффи — Хеллмана сервера
Client Key Exchange -> Доля Диффи — Хеллмана клиента
Change Cipher Spec -> С этого момента данные шифруются
Application Data -> Зашифрованные данные HTTP
:::

:::note
В трассировке ты увидишь **два** TLS-соединения одно за другим: сначала браузер получает страницу, а затем устанавливает новое соединение для таблицы стилей `style.css`. Каждое соединение получает собственное рукопожатие и собственный сеансовый ключ. Настоящие браузеры оставляют соединения открытыми и тем самым экономят часть этих затрат. Более новая версия **TLS 1.3** к тому же обходится меньшим числом сообщений, чем показанный здесь TLS 1.2.
:::

:::tip Запомни
При **TLS-рукопожатии** сервер подтверждает свою подлинность **сертификатом**, обе стороны согласуют **сеансовый ключ** с помощью **Диффи — Хеллмана** (сервер **подписывает** свою долю), а с помощью **Finished** обе стороны проверяют, что никто не изменил рукопожатие. После этого данные передаются как **Application Data** с симметричным шифрованием.
:::
