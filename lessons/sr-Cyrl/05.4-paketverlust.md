# Када се пакети изгубе

:::goal
**Циљ учења:** Можеш да у Трагачу посматраш и објасниш како TCP примећује изгубљене податке, поново их шаље и успоставља редослед.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

У овој симулацији је кабл припремљен: **други пакет са подацима** од Client-PC до сервера се губи. (Подешавање налазиш ако у режиму извршавања кликнеш на кабл: **Циљана губитак пакета**.)

## Експеримент

1. Пређи у :fa-play: режим **Покрени**, отвори на **Client-PC** **Једноставан TCP клијент** и повежи га са `192.168.0.20`, порт `5000`.
2. Пошаљи једну за другом три поруке: `Hallo`, затим `Welt`, па `!`.
3. Посматрај прозор за ћаскање: ехо за `Hallo` стиже одмах. А остала два?
4. Сачекај неколико секунди. Затим у режиму :fa-magnifying-glass: **Трага** отвори снимак за **Server** (прималац), прикључак `eth0`.

:::quiz mc
Шта се дешава са ехом за `Welt` и `!`?
- [ ] Ехо за `!` стиже одмах, а `Welt` заувек изостаје
- [x] Оба стижу тек након неколико секунди — заједно и у исправном редоследу
- [ ] Ниједан од та два никада не стигне
:::

## Шта приказује Трагач

Код сервера недостаје пакет са `Welt` — он се ипак изгубио. Зато у колони **Info** налазиш три напомене у угластим заградама:

| Напомена | Шта се догодило |
|---|---|
| `[TCP Previous segment not captured]` | Пакет са `!` стиже, али пре њега недостају бајтови — **празнина**. |
| `[TCP Dup ACK …]` | Сервер поново потврђује исти број као и раније (*duplicate ACK*): „И даље чекам бајт 8.“ |
| `[TCP Retransmission]` | Клијент шаље `Welt` **још једном**. |

:::quiz short
Који редни број секвенце (`Seq`) има пакет означен са `[TCP Retransmission]`?
= 8
:::

:::quiz short
Који број потврде (`Ack`) сервер шаље непосредно после поновног слања?
= 17
:::

:::quiz mc
Зашто сервер после поновног слања потврђује све до бајта 17 — а не само до краја `Welt`?
- [x] `!` је већ примио и задржао — са `Welt` је празнина затворена, сада је све до бајта 16 ту
- [ ] Клијент је `Welt` и `!` поново послао заједно
- [ ] Бројеви потврде се увек заокружују
:::

:::evaluate
Провери одговоре
:::

У дијаграму комуникације то изгледа овако — испрекидана стрелица са ✕ је изгубљени пакет:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Шта стоји иза тога

Клијент чува сваки послати пакет док се не потврди и за њега покреће **тајмер**. Ако потврда предуго изостане, он поново шаље податке — **поновно слање** (*Retransmission*).

Сервер увек потврђује само до **прве празнине**. Податке који стигну после ње (овде `!`) задржава док се празнина не попуни. Тек тада све у исправном редоследу прослеђује програму — зато су ехои за `Welt` и `!` стигли заједно.

:::tip Запамти
TCP препознаје губитке по **недостајућим потврдама**: прималац увек потврђује само до прве празнине. Ако потврда изостане, пошиљалац након истека тајмера податке шаље **поново** (*Retransmission*). Оно што стигне после празнине прималац задржава — тако подаци стижу до програма **потпуно и у исправном редоследу**.
:::

:::tip Продубљивање: Fast Retransmit
Пошаљи после `Hallo` четири или више порука брзо једну за другом. После изгубљеног пакета клијент тада добија три *Dup ACK*-а заредом — и одмах поново шаље, не чекајући свој тајмер. Овај поступак се зове **Fast Retransmit**.
:::

:::note
Прави TCP имплементације поред тога прилагођавају и своју брзину слања: ако се пакети губе, мрежа је вероватно преоптерећена и пошиљалац успорава (*контрола загушења*). То превазилази оквире овог курса.
:::
