# Quando os pacotes se perdem

:::goal
**Objetivo de aprendizagem:** Consegues observar no Tracer e explicar como o TCP deteta dados perdidos, os volta a enviar e restabelece a ordem.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

Nesta simulação, o cabo está preparado: o **segundo pacote com dados** do Client-PC para o Server perde-se. (Encontras a definição quando clicas no cabo no modo de execução: **Perda de pacotes direcionada**.)

## A experiência

1. Muda para o modo :fa-play: **Executar**, abre no **Client-PC** o **Cliente TCP Simples** e liga-o a `192.168.0.20`, porta `5000`.
2. Envia três mensagens, uma a seguir à outra: `Hallo`, depois `Welt` e por fim `!`.
3. Observa a janela de chat: o eco de `Hallo` chega logo. E os outros dois?
4. Espera alguns segundos. Depois, no modo :fa-magnifying-glass: **Rastreamento**, abre um trace para o **Server** (o destinatário), interface `eth0`.

:::quiz mc
O que acontece com os ecos de `Welt` e `!`?
- [ ] O eco de `!` chega logo, `Welt` falta para sempre
- [x] Ambos só chegam passados alguns segundos — juntos e na ordem correta
- [ ] Nenhum dos dois chega alguma vez
:::

## O que o Tracer mostra

No servidor falta o pacote com `Welt` — afinal, perdeu-se. Em compensação, na coluna **Info** encontras três indicações entre parênteses retos:

| Indicação | O que aconteceu |
|---|---|
| `[TCP Previous segment not captured]` | O pacote com `!` chega, mas antes dele faltam bytes — uma **lacuna**. |
| `[TCP Dup ACK …]` | O servidor confirma outra vez o mesmo número que antes (*duplicate ACK*): «Continuo à espera do byte 8.» |
| `[TCP Retransmission]` | O cliente envia `Welt` **mais uma vez**. |

:::quiz short
Que número de sequência (`Seq`) tem o pacote marcado com `[TCP Retransmission]`?
= 8
:::

:::quiz short
Que número de confirmação (`Ack`) envia o servidor logo a seguir à retransmissão?
= 17
:::

:::quiz mc
Porque é que o servidor, depois da retransmissão, confirma logo até ao byte 17 — e não apenas até ao fim de `Welt`?
- [x] Já tinha recebido `!` e tinha-o retido — com `Welt` a lacuna fica fechada e agora está tudo até ao byte 16
- [ ] O cliente enviou `Welt` e `!` novamente em conjunto
- [ ] Os números de confirmação são sempre arredondados
:::

## O que está por trás

O cliente guarda cada pacote enviado até ele ser confirmado e, para isso, inicia um **temporizador**. Se a confirmação demorar demasiado, envia os dados outra vez — uma **retransmissão** (*Retransmission*).

O servidor confirma sempre apenas até à **primeira lacuna**. Os dados que chegam depois dela (aqui `!`) são retidos até a lacuna ser preenchida. Só então os entrega todos ao programa, na ordem correta — por isso os ecos de `Welt` e `!` chegaram juntos.

:::tip Ponto-chave
O TCP deteta perdas através da **falta de confirmações**: o destinatário confirma sempre apenas até à primeira lacuna. Se a confirmação não chegar, o remetente envia os dados **novamente** quando um temporizador expira (*Retransmission*). O que chega depois de uma lacuna é retido pelo destinatário — assim, os dados chegam ao programa **completos e na ordem correta**.
:::

:::tip Aprofundamento: Fast Retransmit
Depois de `Hallo`, envia quatro ou mais mensagens rapidamente, umas a seguir às outras. Depois do pacote perdido, o cliente recebe então três *Dup ACKs* seguidos — e volta a enviar de imediato, sem esperar pelo seu temporizador. Este procedimento chama-se **Fast Retransmit**.
:::

:::note
As implementações reais de TCP também ajustam o seu ritmo de envio: se se perdem pacotes, a rede está provavelmente congestionada e o remetente abranda (*controlo de congestionamento*). Isto vai além deste curso.
:::
