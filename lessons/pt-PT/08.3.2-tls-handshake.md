# O handshake TLS

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Antes de ser enviado o primeiro pedido cifrado, o cliente e o servidor têm de chegar a acordo: sobre um método, sobre uma chave de sessão — e o cliente tem de verificar com quem está a comunicar. Este estabelecimento de ligação chama-se **handshake TLS**.

No **Client-PC**, abre `https://www.beaver-schule.de/` (se ainda não o fizeste), abre um rastreio para o **Client-PC** e filtra com `tls`.

## O fluxo no diagrama

Sem as confirmações TCP (`ACK`), o handshake é assim:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

O que acontece e qual o componente da secção 8.1 que está por trás:

1. **Client Hello / Server Hello:** o cliente e o servidor cumprimentam-se, trocam números aleatórios e acordam os métodos a utilizar (no BeaverTracer: troca de chaves com **ECDHE**, assinatura com **ECDSA**, cifragem com **AES**).
2. **Certificate:** o servidor envia o seu **certificado**. O cliente verifica a assinatura da CA, a validade e os nomes. Se isto falhar, o cliente interrompe aqui — e o navegador mostra um aviso.
3. **Server Key Exchange:** o servidor envia a sua **parte de Diffie-Hellman** — e **assina-a** com a sua chave privada. O cliente verifica a assinatura com a chave pública do certificado. Assim, fica a saber que esta parte provém realmente do titular do certificado e não de um man-in-the-middle.
4. **Client Key Exchange:** o cliente envia a sua parte de Diffie-Hellman. Agora ambos podem calcular a mesma **chave de sessão** — sem que ela tenha alguma vez sido transmitida.
5. **Change Cipher Spec:** «A partir de agora, cifro.»
6. **Encrypted Handshake Message (Finished):** ambos os lados enviam — já cifrada — uma soma de verificação de todas as mensagens de handshake anteriores. Se um atacante tiver alterado algo pelo caminho, as somas de verificação não coincidem e a ligação é interrompida.
7. **Application Data:** a partir daqui circulam os dados HTTP — cifrados de forma simétrica com AES.

:::quiz match
Certificate -> O servidor identifica-se com o seu certificado
Server Key Exchange -> Parte de Diffie-Hellman do servidor, assinada
Client Key Exchange -> Parte de Diffie-Hellman do cliente
Change Cipher Spec -> A partir de agora, a comunicação é cifrada
Application Data -> Dados HTTP cifrados
:::

:::note
No rastreio vês **duas** ligações TLS consecutivas: o navegador obtém primeiro a página e depois estabelece uma nova ligação para a folha de estilos `style.css`. Cada ligação tem o seu próprio handshake e a sua própria chave de sessão. Os navegadores reais mantêm as ligações abertas e poupam assim parte deste esforço. A versão mais recente, **TLS 1.3**, necessita ainda de menos mensagens do que o TLS 1.2 aqui apresentado.
:::

:::tip Ponto-chave
No **handshake TLS**, o servidor identifica-se com o seu **certificado**, ambos os lados negoceiam uma **chave de sessão** através de **Diffie-Hellman** (o servidor **assina** a sua parte) e, com **Finished**, ambos verificam que ninguém alterou o handshake. Depois disso, os dados são transmitidos como **Application Data**, cifrados de forma simétrica.
:::
