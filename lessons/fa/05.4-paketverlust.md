# وقتی بسته‌ها گم می‌شوند

:::goal
**هدف یادگیری:** تو می‌توانی در Tracer مشاهده کنی و توضیح بدهی که TCP چگونه از گم شدن داده‌ها باخبر می‌شود، آن‌ها را دوباره می‌فرستد و ترتیب را بازمی‌گرداند.
:::

در این شبیه‌سازی کابل دستکاری شده است: **دومین بسته حاوی داده** از Client-PC به سمت Server گم می‌شود. (این تنظیم را وقتی در حالت اجرا روی کابل کلیک کنی پیدا می‌کنی: **تلفات بسته هدفمند**.)

## آزمایش

1. به حالت :fa-play: **اجرا** برو، روی **Client-PC** برنامه‌ی **کلاینت TCP ساده** را باز کن و آن را به `192.168.0.20` و پورت `5000` وصل کن.
2. سه پیام را پشت سر هم بفرست: `Hallo`، سپس `Welt` و بعد `!`.
3. پنجره‌ی چت را نگاه کن: بازتاب `Hallo` بلافاصله می‌رسد. اما دوتای دیگر چه؟
4. چند ثانیه صبر کن. سپس در حالت :fa-magnifying-glass: **ردیابی** یک trace برای **Server** (گیرنده) روی درگاه `eth0` باز کن.

:::quiz mc
چه اتفاقی برای بازتاب‌های `Welt` و `!` می‌افتد؟
- [ ] بازتاب `!` بلافاصله می‌رسد، اما `Welt` برای همیشه گم می‌شود
- [x] هر دو بعد از چند ثانیه می‌رسند — با هم و به ترتیب درست
- [ ] هیچ‌کدام از این دو هرگز نمی‌رسند
:::

## Tracer چه چیزی نشان می‌دهد

در Server بسته‌ی حاوی `Welt` وجود ندارد — چون گم شده است. در عوض در ستون **Info** سه نشانه در کروشه می‌یابی:

| نشانه | چه اتفاقی افتاده است |
|---|---|
| `[TCP Previous segment not captured]` | بسته‌ی حاوی `!` می‌رسد، اما بایت‌های قبل از آن کم هستند — یک **شکاف**. |
| `[TCP Dup ACK …]` | سرور دوباره همان شماره‌ی قبلی را تصدیق می‌کند (*duplicate ACK*): «من هنوز منتظر بایت ۸ هستم.» |
| `[TCP Retransmission]` | کلاینت `Welt` را **یک بار دیگر** می‌فرستد. |

:::quiz short
بسته‌ای که با `[TCP Retransmission]` علامت‌گذاری شده، چه شماره توالی (`Seq`) دارد؟
= 8
:::

:::quiz short
سرور بلافاصله پس از ارسال مجدد، چه شماره تصدیقی (`Ack`) می‌فرستد؟
= 17
:::

:::quiz mc
چرا سرور بعد از ارسال مجدد یکباره تا بایت ۱۷ تصدیق می‌کند — و نه فقط تا انتهای `Welt`؟
- [x] سرور `!` را قبلاً دریافت و نگه داشته بود — با رسیدن `Welt` شکاف بسته می‌شود و حالا همه‌چیز تا بایت ۱۶ رسیده است
- [ ] کلاینت `Welt` و `!` را یک بار دیگر با هم فرستاد
- [ ] شماره‌های تصدیق همیشه گرد می‌شوند
:::

:::evaluate
بررسی پاسخ‌ها
:::

در نمودار ارتباط این‌طور دیده می‌شود — فلش خط‌چین با ✕ همان بسته‌ی گم‌شده است:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## پشت صحنه چه می‌گذرد

کلاینت هر بسته‌ی ارسال‌شده را تا زمان تصدیق نگه می‌دارد و برای آن یک **تایمر** راه می‌اندازد. اگر تصدیق بیش از حد طول بکشد، داده‌ها را دوباره می‌فرستد — یک **ارسال مجدد** (*Retransmission*).

سرور همیشه فقط تا **اولین شکاف** تصدیق می‌کند. داده‌هایی که بعد از آن می‌رسند (اینجا `!`) را نگه می‌دارد تا شکاف پر شود. فقط آن‌وقت همه‌چیز را به ترتیب درست به برنامه تحویل می‌دهد — به همین دلیل بازتاب‌های `Welt` و `!` با هم رسیدند.

:::tip نکته کلیدی
TCP گم شدن داده را از **تصدیق‌های ناپدید** تشخیص می‌دهد: گیرنده همیشه فقط تا اولین شکاف تصدیق می‌کند. اگر تصدیق نیاید، فرستنده پس از اتمام یک تایمر داده‌ها را **دوباره** می‌فرستد (*Retransmission*). آنچه بعد از یک شکاف برسد را گیرنده نگه می‌دارد — به این ترتیب داده‌ها **کامل و به ترتیب درست** به برنامه می‌رسند.
:::

:::tip تعمیق: Fast Retransmit
بعد از `Hallo` چهار پیام یا بیشتر را سریع پشت سر هم بفرست. پس از بسته‌ی گم‌شده، کلاینت سه *Dup ACK* پشت سر هم دریافت می‌کند — و بدون صبر برای تایمر خودش، بلافاصله دوباره می‌فرستد. این روش **Fast Retransmit** نام دارد.
:::

:::note
پیاده‌سازی‌های واقعی TCP علاوه بر این سرعت ارسال خود را هم تنظیم می‌کنند: اگر بسته‌ها گم شوند، احتمالاً شبکه شلوغ و پرترافیک است و فرستنده کندتر می‌شود (*کنترل ازدحام*). این موضوع فراتر از این دوره است.
:::
