پیش از آنکه نخستین درخواست رمزنگاری‌شده فرستاده شود، کلاینت و سرور باید بر سر چند چیز به توافق برسند: بر سر یک روش، بر سر یک کلید نشست — و کلاینت باید بررسی کند که با چه کسی صحبت می‌کند. این برقراری اتصال **دست‌دهی TLS** (TLS-Handshake) نام دارد.

## مشاهده

## روند کار در نمودار

بدون تصدیق‌های TCP (`ACK`)، دست‌دهی به این شکل است:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

در اینجا چه اتفاقی می‌افتد — و کدام عنصر از بخش ۸.۱ پشت آن است:

1. **Client Hello / Server Hello:** کلاینت و سرور به هم سلام می‌کنند، اعداد تصادفی رد و بدل می‌کنند و بر سر روش‌ها به توافق می‌رسند (در BeaverTracer: تبادل کلید با **ECDHE**، امضا با **ECDSA**، رمزنگاری با **AES**).
2. **Certificate:** سرور **گواهی** خود را می‌فرستد. کلاینت امضای CA، اعتبار زمانی و نام را بررسی می‌کند. اگر این بررسی شکست بخورد، همین‌جا متوقف می‌شود — و مرورگر یک هشدار نشان می‌دهد.
3. **Server Key Exchange:** سرور **سهم Diffie-Hellman** خود را می‌فرستد — و آن را با کلید خصوصی‌اش **امضا** می‌کند. کلاینت امضا را با کلید عمومی موجود در گواهی بررسی می‌کند. به این ترتیب می‌داند: این سهم واقعاً از صاحب گواهی آمده است، نه از یک Man-in-the-Middle.
4. **Client Key Exchange:** کلاینت سهم Diffie-Hellman خود را می‌فرستد. اکنون هر دو می‌توانند **کلید نشست** یکسانی را محاسبه کنند — بی‌آنکه هرگز منتقل شده باشد.
5. **Change Cipher Spec:** «از این لحظه به بعد رمزنگاری می‌کنم.»
6. **Encrypted Handshake Message (Finished):** هر دو طرف — این بار رمزنگاری‌شده — یک مقدار کنترلی (checksum) از همه پیام‌های دست‌دهی تا این لحظه می‌فرستند. اگر مهاجمی در مسیر چیزی را تغییر داده باشد، مقادیر کنترلی با هم نمی‌خوانند و اتصال قطع می‌شود.
7. **Application Data:** از اینجا به بعد داده‌های HTTP جریان می‌یابند — با AES به‌صورت متقارن رمزنگاری‌شده.

:::quiz match
Certificate -> سرور با گواهی خود هویتش را اثبات می‌کند
Server Key Exchange -> سهم Diffie-Hellman امضاشده‌ی سرور
Client Key Exchange -> سهم Diffie-Hellman کلاینت
Change Cipher Spec -> از این لحظه به بعد رمزنگاری می‌شود
Application Data -> داده‌های HTTP رمزنگاری‌شده
:::

:::note
در ردیابی **دو** اتصال TLS را پشت سر هم می‌بینی: مرورگر ابتدا صفحه را دریافت می‌کند و سپس برای شیوه‌نامه `style.css` یک اتصال جدید برقرار می‌کند. هر اتصال دست‌دهی و کلید نشست مخصوص به خود را دارد. مرورگرهای واقعی اتصال‌ها را باز نگه می‌دارند و به این ترتیب بخشی از این هزینه را صرفه‌جویی می‌کنند. نسخه جدیدتر یعنی **TLS 1.3** افزون بر این با پیام‌های کمتری نسبت به TLS 1.2 که اینجا نشان داده شده کار را پیش می‌برد.
:::

:::tip نکته کلیدی
در **دست‌دهی TLS** سرور با **گواهی** خود هویتش را اثبات می‌کند، هر دو طرف با **Diffie-Hellman** یک **کلید نشست** را توافق می‌کنند (سرور سهم خود را **امضا** می‌کند)، و با **Finished** هر دو بررسی می‌کنند که کسی دست‌دهی را تغییر نداده است. پس از آن داده‌ها به‌صورت **Application Data** و با رمزنگاری متقارن منتقل می‌شوند.
:::
