# Kada se paketi izgube

:::goal
**Ishod učenja:** U alatu Trag možeš posmatrati i objasniti kako TCP primjećuje izgubljene podatke, ponovo ih šalje i uspostavlja redoslijed.
:::

U ovoj simulaciji kabl je pripremljen: **drugi paket s podacima** od Client-PC prema serveru se gubi. (Postavku nalaziš kada u načinu rada Pokretanje klikneš na kabl: **Ciljani gubitak paketa**.)

## Eksperiment

1. Pređi u način rada :fa-play: **Pokreni**, otvori na **Client-PC** **Jednostavni TCP klijent** i poveži ga na `192.168.0.20`, port `5000`.
2. Pošalji redom tri poruke: `Hallo`, zatim `Welt`, pa `!`.
3. Posmatraj prozor za chat: odjek poruke `Hallo` stiže odmah. A druge dvije?
4. Sačekaj nekoliko sekundi. Zatim u načinu rada :fa-magnifying-glass: **Trag** otvori trag za **Server** (primalac), priključak `eth0`.

:::quiz mc
Šta se dešava s odjecima poruka `Welt` i `!`?
- [ ] Odjek poruke `!` stiže odmah, a `Welt` zauvijek izostaje
- [x] Oba stižu tek nakon nekoliko sekundi — zajedno i ispravnim redoslijedom
- [ ] Nijedan od ta dva nikada ne stigne
:::

## Šta Tracer prikazuje

Na serveru nedostaje paket s porukom `Welt` — on se ipak izgubio. Umjesto toga u koloni **Info** nalaziš tri napomene u uglastim zagradama:

| Napomena | Šta se desilo |
|---|---|
| `[TCP Previous segment not captured]` | Paket s `!` stiže, ali prije njega nedostaju bajtovi — **praznina**. |
| `[TCP Dup ACK …]` | Server ponovo potvrđuje isti broj kao i ranije (*duplicate ACK*): „Još uvijek čekam bajt 8.“ |
| `[TCP Retransmission]` | Klijent šalje `Welt` **još jednom**. |

:::quiz short
Koji sekvencijski broj (`Seq`) ima paket koji je označen sa `[TCP Retransmission]`?
= 8
:::

:::quiz short
Koji broj potvrde (`Ack`) server šalje neposredno nakon ponovnog slanja?
= 17
:::

:::quiz mc
Zašto server nakon ponovnog slanja odmah potvrđuje sve do bajta 17 — a ne samo do kraja poruke `Welt`?
- [x] Već je primio i zadržao `!` — s porukom `Welt` praznina je zatvorena, sada je sve do bajta 16 stiglo
- [ ] Klijent je `Welt` i `!` poslao još jednom zajedno
- [ ] Brojevi potvrde se uvijek zaokružuju
:::

Provjeri odgovore
:::

:::seq

Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Šta se krije iza toga

Klijent čuva svaki poslani paket dok ne bude potvrđen i za to pokreće **tajmer**. Ako potvrda predugo izostane, ponovo šalje podatke — **ponovno slanje** (*retransmission*).

Server uvijek potvrđuje samo do **prve praznine**. Podatke koji stignu poslije nje (ovdje `!`) zadržava dok se praznina ne popuni. Tek tada sve prosljeđuje programu ispravnim redoslijedom — zato su odjeci poruka `Welt` i `!` stigli zajedno.

:::tip Zapamti
TCP prepoznaje gubitke po **izostanku potvrda**: primalac uvijek potvrđuje samo do prve praznine. Ako potvrda izostane, pošiljalac nakon isteka tajmera **ponovo** šalje podatke (*retransmission*). Ono što stigne poslije praznine primalac zadržava — tako podaci do programa stižu **potpuni i ispravnim redoslijedom**.
:::

:::tip Produbljivanje: Fast Retransmit
Nakon poruke `Hallo` pošalji četiri ili više poruka brzo jednu za drugom. Nakon izgubljenog paketa klijent tada dobije tri *Dup ACK-a* zaredom — i odmah ponovo šalje, ne čekajući svoj tajmer. Ovaj postupak se zove **Fast Retransmit**.
:::

:::note
Stvarne TCP implementacije osim toga prilagođavaju i svoju brzinu slanja: ako se paketi gube, mreža je vjerovatno preopterećena i pošiljalac usporava (*kontrola zagušenja*). To prelazi okvire ovog kursa.
:::
