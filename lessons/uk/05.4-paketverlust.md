## Експеримент

1. Перейди в режим :fa-play: **Запустити**, відкрий на **Client-PC** **Простий TCP-клієнт** і підключи його до `192.168.0.20`, порт `5000`.
2. Надішли послідовно три повідомлення: `Hallo`, потім `Welt`, потім `!`.
3. Спостерігай за вікном чату: відлуння `Hallo` приходить одразу. А інші два?
4. Зачекай кілька секунд. Потім у режимі :fa-magnifying-glass: **Трасування** відкрий трасування для **Server** (одержувач), інтерфейс `eth0`.

- [x] Обидва приходять лише через кілька секунд — разом і в правильному порядку

## Що показує Tracer

На сервері пакета з `Welt` немає — адже він загубився. Натомість у стовпці **Info** ти знайдеш три позначки у квадратних дужках:

| Позначка | Що сталося |
|---|---|
| `[TCP Previous segment not captured]` | Пакет з `!` доходить, але перед ним бракує байтів — **прогалина**. |
| `[TCP Dup ACK …]` | Сервер ще раз підтверджує той самий номер, що й раніше (*duplicate ACK*): «Я все ще чекаю на байт 8». |
| `[TCP Retransmission]` | Клієнт надсилає `Welt` **ще раз**. |

:::quiz short
Який порядковий номер (`Seq`) має пакет, позначений `[TCP Retransmission]`?
= 8
:::

:::quiz short
Який номер підтвердження (`Ack`) надсилає сервер одразу після повторного передавання?
= 17
:::

:::quiz mc
Чому після повторного передавання сервер одразу підтверджує до байта 17, а не лише до кінця `Welt`?
- [x] Він уже отримав `!` і притримав його — із `Welt` прогалину закрито, тепер усе до байта 16 є
- [ ] Клієнт ще раз надіслав `Welt` і `!` разом
- [ ] Номери підтвердження завжди округлюються
:::

:::evaluate
Перевірити відповіді
:::

На діаграмі послідовності це виглядає так — пунктирна стрілка з ✕ позначає втрачений пакет:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Що за цим стоїть

Клієнт зберігає кожен надісланий пакет, доки його не підтвердять, і запускає для цього **таймер**. Якщо підтвердження надходить надто довго, він надсилає дані знову — це **повторне передавання** (*Retransmission*).

Сервер підтверджує завжди лише до **першої прогалини**. Дані, що надходять після неї (тут `!`), він притримує, доки прогалину не буде заповнено. Лише тоді він передає все програмі в правильному порядку — тому відлуння `Welt` і `!` прийшли разом.

:::tip Запам'ятай
TCP виявляє втрати за **відсутніми підтвердженнями**: одержувач підтверджує завжди лише до першої прогалини. Якщо підтвердження немає, відправник після спливу таймера надсилає дані **повторно** (*Retransmission*). Те, що надходить після прогалини, одержувач притримує — так дані потрапляють до програми **повністю й у правильному порядку**.
:::

:::tip Поглиблення: Fast Retransmit
Після `Hallo` надішли швидко одне за одним чотири або більше повідомлень. Після втраченого пакета клієнт отримає три *Dup ACK* поспіль — і негайно надішле дані знову, не чекаючи свого таймера. Цей метод називається **Fast Retransmit**.
:::

:::note
Реальні реалізації TCP також підлаштовують швидкість надсилання: якщо пакети губляться, мережа, імовірно, перевантажена, і відправник сповільнюється (*контроль перевантаження*). Це виходить за межі цього курсу.
:::
