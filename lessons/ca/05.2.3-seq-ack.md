# Números de seqüència i de confirmació

:::sim
url=/sims/lesson-5.1.btsim
:::

Com sap TCP si tot ha arribat — i en quin ordre? Cada part **numera els bytes** que envia:

- El **número de seqüència** (`SEQ`) és el número del primer byte que va en aquest paquet.
- El **número de confirmació** (`ACK`) diu: «Fins aquí ho he rebut tot — el següent que espero és el byte núm. …»

A més, dues regles: `SYN` i `FIN` compten com un byte, tot i que no porten dades. I cada part compta per si mateixa — per això hi ha dos intervals de numeració, en vermell (client) i en blau (servidor) al diagrama.

## Comprovació amb càlculs

Aquí tens una altra vegada la teva connexió. Els números de les línies mostren el comptador de l'ordinador en aquell punt:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hello World" len=13
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=13
Client-PC -> Server: ACK
Client-PC -> Server: FIN, ACK
Server -> Client-PC: ACK
Server -> Client-PC: FIN, ACK
Client-PC -> Server: ACK
:::

Repassa la sèrie de números vermells:

1. El client comença a `SEQ=0`. El seu `SYN` consumeix un número — el servidor el confirma amb `ACK=1`.
2. El missatge comença a `SEQ=1` i fa 13 bytes (bytes de l'1 al 13). El servidor el confirma amb `ACK=14`: «El següent que espero és el byte 14.»
3. Per tant, el `FIN` del client té `SEQ=14` i es confirma amb `ACK=15`.

La sèrie blava del servidor funciona exactament igual.

:::tip Idea clau
El **número de seqüència** (`SEQ`) és el número del primer byte del paquet. El **número de confirmació** (`ACK`) és el número del següent byte que espera el receptor — tot el que hi ha abans ha arribat. Val la regla: **ACK = SEQ + longitud** de les dades rebudes; `SYN` i `FIN` compten com un byte. Cada part compta els seus propis bytes.
:::

:::tip Prova-ho
Torna a establir la connexió amb el **Client TCP simple** i envia dos missatges seguits. Digues abans quins valors de `Seq` i `Ack` apareixeran a la columna **Info** — i comprova-ho a la traça.
:::

## Practica

:::quiz short
El client envia un paquet amb `Seq=1` i `Len=13`. Quin número de confirmació li retorna el servidor?
= 14
:::

:::quiz short
Després, el client envia el seu següent missatge. Amb quin número de seqüència comença?
= 14
:::

:::quiz short
Arriba un paquet amb `Seq=40` i `Len=25`. Quin número de confirmació envia el receptor?
= 65
:::

:::evaluate
Comprova les respostes
:::

Introdueix els números que falten. El client envia `Hallo` i després `Tschau` (cadascun amb final de línia):

:::quiz seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK ack=?
Client-PC -> Server: ACK seq=? ack=?

Server -> Client-PC: ACK ack=?
Client-PC -> Server: PSH, ACK "Tschau" len=8 seq=?
Server -> Client-PC: ACK ack=?
:::

:::note
A les xarxes reals el recompte no comença a 0: cada part tria un **número inicial aleatori** (*Initial Sequence Number*, ISN) entre 0 i uns 4.300 milions. Quan s'arriba al número més alt, es torna a continuar des de 0. El Tracer resta el número inicial i mostra números **relatius** — igual que Wireshark. Per això veus `Seq=0` i `Seq=1`.

A més, cada paquet inclou `Win=` — la **mida de finestra**: és la quantitat de bytes que el receptor pot admetre en aquell moment. Amb això frena un emissor massa ràpid (*control de flux*). A BeaverTracer la finestra sempre té la mateixa mida.
:::
