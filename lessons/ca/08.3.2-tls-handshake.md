# L'handshake TLS

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Abans d'enviar la primera petició xifrada, el client i el servidor s'han de posar d'acord: en un mètode, en una clau de sessió, i el client ha de comprovar amb qui parla. Aquest establiment de la connexió s'anomena **handshake TLS**.

## Observar

Obre `https://www.beaver-schule.de/` des del **Client-PC** (si encara no ho has fet), obre una traça per al **Client-PC** i filtra amb `tls`.

## El procés en el diagrama

Sense les confirmacions TCP (`ACK`), l'handshake té aquest aspecte:

:::seq
mode: text
Client -> Server: Client Hello | Nombre aleatori, mètodes possibles
Server -> Client: Server Hello | Mètode triat, nombre aleatori
Server -> Client: Certificate | Certificat del servidor
Server -> Client: Server Key Exchange | Part DH, signada
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | Part DH del client
Client -> Server: Change Cipher Spec | A partir d'ara, xifrat
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | A partir d'ara, xifrat
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (xifrat)
Server -> Client: Application Data | Pàgina web (xifrada)
:::

Què passa en cada pas, i quin component de la secció 8.1 hi ha al darrere:

1. **Client Hello / Server Hello:** el client i el servidor se saluden, intercanvien nombres aleatoris i es posen d'acord en els mètodes (a BeaverTracer: intercanvi de claus amb **ECDHE**, signatura amb **ECDSA**, xifratge amb **AES**).
2. **Certificate:** el servidor envia el seu **certificat**. El client en comprova la signatura de la CA, la validesa i el nom. Si falla, el client s'atura aquí i el navegador mostra un avís.
3. **Server Key Exchange:** el servidor envia la seva **part de Diffie-Hellman** i la **signa** amb la seva clau privada. El client comprova la signatura amb la clau pública del certificat. Així sap que aquesta part ve realment del titular del certificat i no d'un atacant man-in-the-middle.
4. **Client Key Exchange:** el client envia la seva part de Diffie-Hellman. Ara tots dos poden calcular la mateixa **clau de sessió**, sense que aquesta s'hagi transmès mai.
5. **Change Cipher Spec:** «A partir d'ara xifro.»
6. **Encrypted Handshake Message (Finished):** les dues parts envien, ja xifrada, una suma de verificació de tots els missatges d'handshake anteriors. Si un atacant ha modificat alguna cosa pel camí, les sumes de verificació no coincideixen i la connexió s'interromp.
7. **Application Data:** a partir d'aquí circulen les dades HTTP, xifrades simètricament amb AES.

:::quiz match
Certificate -> El servidor s'identifica amb el seu certificat
Server Key Exchange -> Part de Diffie-Hellman signada del servidor
Client Key Exchange -> Part de Diffie-Hellman del client
Change Cipher Spec -> A partir d'ara es xifra
Application Data -> Dades HTTP xifrades
:::

:::note
A la traça veus **dues** connexions TLS successives: el navegador obté primer la pàgina i després estableix una connexió nova per al full d'estil `style.css`. Cada connexió té el seu propi handshake i la seva pròpia clau de sessió. Els navegadors reals mantenen les connexions obertes i s'estalvien així una part d'aquest esforç. A més, la versió més recent, **TLS 1.3**, necessita menys missatges que el TLS 1.2 mostrat aquí.
:::

:::tip Idea clau
Durant l'**handshake TLS**, el servidor s'identifica amb el seu **certificat**, les dues parts negocien una **clau de sessió** mitjançant **Diffie-Hellman** (el servidor **signa** la seva part) i, amb **Finished**, tots dos comproven que ningú no ha modificat l'handshake. Després, les dades es transmeten xifrades simètricament com a **Application Data**.
:::
