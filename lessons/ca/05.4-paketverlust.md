# Quan es perden paquets

:::goal
**Objectiu d'aprenentatge:** Pots observar al Tracer i explicar com TCP s'adona que s'han perdut dades, les torna a enviar i restableix l'ordre.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

En aquesta simulació el cable està preparat: el **segon paquet amb dades** del Client-PC cap al servidor es perd. (Trobaràs aquesta opció si, en el mode d'execució, fas clic al cable: **Pèrdua de paquets dirigida**.)

## L'experiment

1. Canvia al mode :fa-play: **Executar**, obre el **Client TCP simple** al **Client-PC** i connecta'l a `192.168.0.20`, port `5000`.
2. Envia tres missatges un darrere l'altre: `Hallo`, després `Welt` i després `!`.
3. Observa la finestra de xat: l'eco de `Hallo` arriba de seguida. I els altres dos?
4. Espera uns quants segons. Després, en el mode :fa-magnifying-glass: **Traça**, obre una traça per al **servidor** (el receptor), interfície `eth0`.

:::quiz mc
Què passa amb els ecos de `Welt` i `!`?
- [ ] L'eco de `!` arriba de seguida, `Welt` no arriba mai
- [x] Tots dos arriben només al cap d'uns segons — junts i en l'ordre correcte
- [ ] Cap dels dos no arriba mai
:::

## Què mostra el Tracer

Al servidor falta el paquet amb `Welt` — s'ha perdut, és clar. En canvi, a la columna **Info** hi trobaràs tres indicacions entre claudàtors:

| Indicació | Què ha passat |
|---|---|
| `[TCP Previous segment not captured]` | El paquet amb `!` arriba, però abans falten bytes — un **buit**. |
| `[TCP Dup ACK …]` | El servidor confirma una altra vegada el mateix número que abans (*duplicate ACK*): «Encara estic esperant el byte 8.» |
| `[TCP Retransmission]` | El client envia `Welt` **una altra vegada**. |

:::quiz short
Quin número de seqüència (`Seq`) té el paquet marcat amb `[TCP Retransmission]`?
= 8
:::

:::quiz short
Quin número de confirmació (`Ack`) envia el servidor just després de la retransmissió?
= 17
:::

:::quiz mc
Per què el servidor confirma fins al byte 17 just després de la retransmissió — i no només fins al final de `Welt`?
- [x] Ja havia rebut `!` i l'havia retingut — amb `Welt` el buit es tanca i ara ja hi ha tot fins al byte 16
- [ ] El client ha tornat a enviar `Welt` i `!` junts
- [ ] Els números de confirmació sempre s'arrodoneixen
:::

:::evaluate
Comprova les respostes
:::

Al diagrama de seqüència es veu així — la fletxa discontínua amb la ✕ és el paquet perdut:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK

## Què hi ha al darrere

El client guarda cada paquet enviat fins que es confirma i, per a això, inicia un **temporitzador**. Si la confirmació triga massa, torna a enviar les dades — una **retransmissió** (*retransmission*).

El servidor només confirma sempre fins al **primer buit**. Les dades que arriben després (aquí `!`) les reté fins que el buit s'ompli. Només llavors les passa totes al programa en l'ordre correcte — per això els ecos de `Welt` i `!` van arribar junts.

:::tip Idea clau
TCP detecta les pèrdues per les **confirmacions que falten**: el receptor només confirma sempre fins al primer buit. Si la confirmació no arriba, el remitent **torna a enviar** les dades quan s'esgota un temporitzador (*retransmission*). El que arriba després d'un buit, el receptor ho reté — així les dades arriben al programa **completes i en l'ordre correcte**.
:::

:::tip Per aprofundir: Fast Retransmit
Després de `Hallo`, envia quatre missatges o més ràpidament un darrere l'altre. Després del paquet perdut, el client rep tres *Dup ACK* seguits — i reenvia immediatament, sense esperar el seu temporitzador. Aquest procediment s'anomena **Fast Retransmit**.
:::

:::note
Les implementacions reals de TCP, a més, adapten el seu ritme d'enviament: si es perden paquets, probablement la xarxa està sobrecarregada i el remitent va més lent (*control de congestió*). Això va més enllà d'aquest curs.
:::
