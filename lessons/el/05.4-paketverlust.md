# Όταν χάνονται πακέτα

:::goal
**Μαθησιακός στόχος:** Μπορείς να παρατηρήσεις στον tracer και να εξηγήσεις πώς το TCP αντιλαμβάνεται τα χαμένα δεδομένα, τα στέλνει ξανά και αποκαθιστά τη σειρά τους.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

Σε αυτή την προσομοίωση το καλώδιο έχει ρυθμιστεί ειδικά: το **δεύτερο πακέτο με δεδομένα** από τον Client-PC προς τον Server χάνεται. (Θα βρεις τη ρύθμιση αν κάνεις κλικ στο καλώδιο στη Λειτουργία εκτέλεσης: **Στοχευμένη απώλεια πακέτων**.)

## Το πείραμα

1. Πέρασε στη λειτουργία :fa-play: **Εκτέλεση**, άνοιξε στον **Client-PC** το **Απλό TCP Client** και σύνδεσέ το με τη `192.168.0.20`, θύρα `5000`.
2. Στείλε τρία μηνύματα το ένα μετά το άλλο: `Hallo`, μετά `Welt`, μετά `!`.
3. Παρατήρησε το παράθυρο συνομιλίας: η ηχώ του `Hallo` έρχεται αμέσως. Και των άλλων δύο;
4. Περίμενε λίγα δευτερόλεπτα. Μετά, στη λειτουργία :fa-magnifying-glass: **Ίχνος**, άνοιξε ένα trace για τον **Server** (τον παραλήπτη), διεπαφή `eth0`.

:::quiz mc
Τι συμβαίνει με την ηχώ του `Welt` και του `!`;
- [ ] Η ηχώ του `!` έρχεται αμέσως, το `Welt` λείπει για πάντα
- [x] Και οι δύο έρχονται μόνο μετά από μερικά δευτερόλεπτα — μαζί και με τη σωστή σειρά
- [ ] Καμία από τις δύο δεν φτάνει ποτέ
:::

## Τι δείχνει ο tracer

Στον Server λείπει το πακέτο με το `Welt` — άλλωστε χάθηκε. Αντί γι' αυτό, βρίσκεις στη στήλη **Info** τρεις ενδείξεις μέσα σε αγκύλες:

| Ένδειξη | Τι συνέβη |
|---|---|
| `[TCP Previous segment not captured]` | Το πακέτο με το `!` φτάνει, αλλά πριν από αυτό λείπουν bytes — ένα **κενό**. |
| `[TCP Dup ACK …]` | Ο server επιβεβαιώνει ξανά τον ίδιο αριθμό με πριν (*duplicate ACK*): «Περιμένω ακόμα το byte 8.» |
| `[TCP Retransmission]` | Ο client στέλνει το `Welt` **ξανά**. |

:::quiz short
Ποιον αριθμό ακολουθίας (`Seq`) έχει το πακέτο που είναι επισημασμένο με `[TCP Retransmission]`;
= 8
:::

:::quiz short
Ποιον αριθμό επιβεβαίωσης (`Ack`) στέλνει ο server αμέσως μετά την επαναμετάδοση;
= 17
:::

:::quiz mc
Γιατί ο server μετά την επαναμετάδοση επιβεβαιώνει κατευθείαν μέχρι το byte 17 — και όχι μόνο μέχρι το τέλος του `Welt`;
- [x] Είχε ήδη λάβει και κρατήσει σε αναμονή το `!` — με το `Welt` το κενό κλείνει, τώρα έχουν φτάσει όλα μέχρι το byte 16
- [ ] Ο client έστειλε ξανά το `Welt` και το `!` μαζί
- [ ] Οι αριθμοί επιβεβαίωσης στρογγυλοποιούνται πάντα
:::

:::evaluate
Έλεγχος απαντήσεων
:::

Στο διάγραμμα ακολουθίας φαίνεται έτσι — το διακεκομμένο βέλος με το ✕ είναι το χαμένο πακέτο:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Τι κρύβεται από πίσω

Ο client κρατά κάθε πακέτο που έχει στείλει μέχρι να επιβεβαιωθεί και ξεκινά γι' αυτό ένα **χρονόμετρο** (*timer*). Αν η επιβεβαίωση αργήσει πολύ, στέλνει τα δεδομένα ξανά — μια **επαναμετάδοση** (*Retransmission*).

Ο server επιβεβαιώνει πάντα μόνο μέχρι το **πρώτο κενό**. Τα δεδομένα που φτάνουν μετά από αυτό (εδώ το `!`) τα κρατά σε αναμονή μέχρι να καλυφθεί το κενό. Μόνο τότε τα παραδίδει όλα με τη σωστή σειρά στο πρόγραμμα — γι' αυτό η ηχώ του `Welt` και του `!` ήρθαν μαζί.

:::tip Βασικό σημείο
Το TCP αναγνωρίζει τις απώλειες από τις **επιβεβαιώσεις που λείπουν**: ο παραλήπτης επιβεβαιώνει πάντα μόνο μέχρι το πρώτο κενό. Αν η επιβεβαίωση δεν έρθει, ο αποστολέας στέλνει τα δεδομένα **ξανά** μόλις λήξει ένα χρονόμετρο (*Retransmission*). Ό,τι φτάνει μετά από ένα κενό, ο παραλήπτης το κρατά σε αναμονή — έτσι τα δεδομένα φτάνουν στο πρόγραμμα **πλήρη και με τη σωστή σειρά**.
:::

:::tip Εμβάθυνση: Fast Retransmit
Μετά το `Hallo`, στείλε τέσσερα ή περισσότερα μηνύματα γρήγορα το ένα μετά το άλλο. Μετά το χαμένο πακέτο, ο client λαμβάνει τότε τρία *Dup ACKs* στη σειρά — και στέλνει ξανά αμέσως, χωρίς να περιμένει το χρονόμετρό του. Αυτή η διαδικασία ονομάζεται **Fast Retransmit**.
:::

:::note
Οι πραγματικές υλοποιήσεις του TCP προσαρμόζουν επιπλέον τον ρυθμό αποστολής τους: αν χάνονται πακέτα, το δίκτυο είναι πιθανότατα υπερφορτωμένο και ο αποστολέας επιβραδύνει (*έλεγχος συμφόρησης*). Αυτό ξεφεύγει από τα όρια αυτού του μαθήματος.
:::
