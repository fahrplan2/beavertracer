# TLS-rokovanje

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Preden je poslana prva šifrirana zahteva, se morata odjemalec in strežnik dogovoriti: o postopku, o ključu seje — in odjemalec mora preveriti, s kom komunicira. Ta vzpostavitev povezave se imenuje **TLS-rokovanje** (TLS handshake).

## Potek v diagramu

Brez potrditev TCP (`ACK`) rokovanje izgleda takole:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Kaj se pri tem dogaja — in kateri gradnik iz razdelka 8.1 stoji za tem:

1. **Client Hello / Server Hello:** Odjemalec in strežnik se pozdravita, izmenjata naključni števili in se dogovorita o postopkih (v BeaverTracer: izmenjava ključev z **ECDHE**, podpis z **ECDSA**, šifriranje z **AES**).
2. **Certificate:** Strežnik pošlje svoje **digitalno potrdilo**. Odjemalec preveri podpis CA, veljavnost in imena. Če to spodleti, se tu prekine — in brskalnik prikaže opozorilo.
3. **Server Key Exchange:** Strežnik pošlje svoj **delež Diffie-Hellman** — in ga **podpiše** s svojim zasebnim ključem. Odjemalec preveri podpis z javnim ključem iz digitalnega potrdila. Tako ve: ta delež res prihaja od lastnika digitalnega potrdila in ne od napadalca man-in-the-middle.
4. **Client Key Exchange:** Odjemalec pošlje svoj delež Diffie-Hellman. Zdaj lahko oba izračunata isti **ključ seje** — ne da bi bil kdaj prenesen.
5. **Change Cipher Spec:** „Od zdaj naprej šifriram.“
6. **Encrypted Handshake Message (Finished):** Obe strani pošljeta — že šifrirano — kontrolno vsoto vseh dotedanjih sporočil rokovanja. Če je napadalec med potjo kaj spremenil, se kontrolni vsoti ne ujemata in povezava se prekine.
7. **Application Data:** Od tu naprej tečejo podatki HTTP — simetrično šifrirani z AES.

:::quiz match
Certificate -> Strežnik se izkaže s svojim digitalnim potrdilom
Server Key Exchange -> Podpisan delež Diffie-Hellman strežnika
Client Key Exchange -> Delež Diffie-Hellman odjemalca
Change Cipher Spec -> Od zdaj naprej se šifrira
Application Data -> Šifrirani podatki HTTP
:::

:::note
V sledi vidiš **dve** povezavi TLS ena za drugo: brskalnik najprej prenese stran in nato vzpostavi novo povezavo za slogovno datoteko `style.css`. Vsaka povezava dobi svoje rokovanje in svoj ključ seje. Pravi brskalniki povezave puščajo odprte in si tako prihranijo del tega napora. Novejša različica **TLS 1.3** poleg tega potrebuje manj sporočil kot tukaj prikazani TLS 1.2.
:::

:::tip Zapomni si
Pri **TLS-rokovanju** se strežnik izkaže s svojim **digitalnim potrdilom**, obe strani se prek **Diffie-Hellmana** dogovorita o **ključu seje** (strežnik svoj delež **podpiše**), s sporočilom **Finished** pa obe preverita, da nihče ni spremenil rokovanja. Nato se podatki prenašajo kot **Application Data**, simetrično šifrirani.
:::
