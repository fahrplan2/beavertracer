# Ko se paketi izgubijo

:::goal
**Učni cilj:** V orodju Tracer znaš opazovati in razložiti, kako TCP opazi izgubljene podatke, jih ponovno pošlje in obnovi vrstni red.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

V tej simulaciji je kabel pripravljen: **drugi paket s podatki** od Client-PC do strežnika se izgubi. (Nastavitev najdeš, ko v načinu izvajanja klikneš na kabel: **Ciljna izpustitev paketov**.)

## Eksperiment

1. Preklopi v način :fa-play: **Zagon**, na računalniku **Client-PC** odpri **Enostaven odjemalec TCP** in ga poveži z `192.168.0.20`, vrata `5000`.
2. Zaporedoma pošlji tri sporočila: `Hallo`, nato `Welt`, nato `!`.
3. Opazuj okno za klepet: odmev sporočila `Hallo` pride takoj. In ostala dva?
4. Počakaj nekaj sekund. Nato v načinu :fa-magnifying-glass: **Sled** odpri sled za **strežnik** (prejemnik), priključek `eth0`.

:::quiz mc
Kaj se zgodi z odmevoma sporočil `Welt` in `!`?
- [ ] Odmev sporočila `!` pride takoj, `Welt` manjka za vedno
- [x] Oba prideta šele po nekaj sekundah — skupaj in v pravilnem vrstnem redu
- [ ] Nobeden od obeh ne pride nikoli
:::

## Kaj prikaže Tracer

Pri strežniku paket z `Welt` manjka — saj se je izgubil. Namesto tega v stolpcu **Info** najdeš tri opombe v oglatih oklepajih:

| Opomba | Kaj se je zgodilo |
|---|---|
| `[TCP Previous segment not captured]` | Paket z `!` prispe, vendar pred njim manjkajo bajti — **vrzel**. |
| `[TCP Dup ACK …]` | Strežnik še enkrat potrdi isto številko kot prej (*duplicate ACK*): »Še vedno čakam na bajt 8.« |
| `[TCP Retransmission]` | Odjemalec pošlje `Welt` **še enkrat**. |

:::quiz short
Katero zaporedno številko (`Seq`) ima paket, označen z `[TCP Retransmission]`?
= 8
:::

:::quiz short
Katero potrditveno številko (`Ack`) pošlje strežnik neposredno po ponovnem prenosu?
= 17
:::

:::quiz mc
Zakaj strežnik po ponovnem prenosu potrdi kar do bajta 17 — in ne samo do konca sporočila `Welt`?
- [x] `!` je že prejel in ga zadržal — z `Welt` je vrzel zapolnjena, zdaj je vse do bajta 16 na voljo
- [ ] Odjemalec je `Welt` in `!` ponovno poslal skupaj
- [ ] Potrditvene številke se vedno zaokrožijo
:::

:::evaluate
Preveri odgovore
:::

V komunikacijskem diagramu to izgleda takole — črtkana puščica s ✕ je izgubljeni paket:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Kaj je v ozadju

Odjemalec hrani vsak poslani paket, dokler ni potrjen, in za to zažene **časovnik**. Če potrditev predolgo izostane, podatke pošlje ponovno — **ponovni prenos** (*retransmission*).

Strežnik vedno potrdi samo do **prve vrzeli**. Podatke, ki prispejo za njo (tu `!`), zadrži, dokler vrzel ni zapolnjena. Šele nato vse v pravilnem vrstnem redu preda programu — zato sta odmeva sporočil `Welt` in `!` prišla skupaj.

:::tip Zapomni si
TCP izgube prepozna po **manjkajočih potrditvah**: prejemnik vedno potrdi samo do prve vrzeli. Če potrditev izostane, pošiljatelj po izteku časovnika podatke pošlje **ponovno** (*retransmission*). Kar prispe za vrzeljo, prejemnik zadrži — tako podatki dosežejo program **popolni in v pravilnem vrstnem redu**.
:::

:::tip Poglobitev: Fast Retransmit
Po sporočilu `Hallo` hitro zaporedoma pošlji štiri ali več sporočil. Po izgubljenem paketu odjemalec nato prejme tri *Dup ACK* zapored — in takoj ponovno pošlje, ne da bi čakal na svoj časovnik. Ta postopek se imenuje **Fast Retransmit**.
:::

:::note
Pravi izvedbi TCP svojo hitrost pošiljanja tudi prilagajata: če se paketi izgubljajo, je omrežje verjetno preobremenjeno in pošiljatelj upočasni (*nadzor zasičenosti*). To presega okvir tega tečaja.
:::
