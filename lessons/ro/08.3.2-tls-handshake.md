# Handshake-ul TLS

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Înainte de a fi trimisă prima cerere criptată, clientul și serverul trebuie să se pună de acord: asupra unei metode, asupra unei chei de sesiune — iar clientul trebuie să verifice cu cine comunică. Această stabilire a conexiunii se numește **handshake TLS**.

## Observă

Accesează pe **Client-PC** adresa `https://www.beaver-schule.de/` (dacă nu ai făcut-o deja), deschide o urmărire pentru **Client-PC** și filtrează cu `tls`.

## Desfășurarea în diagramă

Fără confirmările TCP (`ACK`), handshake-ul arată astfel:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Ce se întâmplă aici — și ce element din secțiunea 8.1 se află în spate:

1. **Client Hello / Server Hello:** Clientul și serverul se salută, schimbă numere aleatorii și cad de acord asupra metodelor (în BeaverTracer: schimb de chei cu **ECDHE**, semnătură cu **ECDSA**, criptare cu **AES**).
2. **Certificate:** Serverul trimite **certificatul** său. Clientul verifică semnătura CA, valabilitatea și numele. Dacă verificarea eșuează, clientul întrerupe aici — iar browserul afișează un avertisment.
3. **Server Key Exchange:** Serverul trimite **contribuția sa Diffie-Hellman** — și o **semnează** cu cheia sa privată. Clientul verifică semnătura cu cheia publică din certificat. Astfel știe: această contribuție provine într-adevăr de la deținătorul certificatului, nu de la un atacator de tip Man-in-the-Middle.
4. **Client Key Exchange:** Clientul trimite contribuția sa Diffie-Hellman. Acum amândoi pot calcula aceeași **cheie de sesiune** — fără ca ea să fi fost vreodată transmisă.
5. **Change Cipher Spec:** „De acum încep să criptez.”
6. **Encrypted Handshake Message (Finished):** Ambele părți trimit — deja criptat — o sumă de control peste toate mesajele de handshake de până atunci. Dacă un atacator a modificat ceva pe parcurs, sumele de control nu se potrivesc, iar conexiunea este întreruptă.
7. **Application Data:** De aici încep să circule datele HTTP — criptate simetric cu AES.

:::quiz match
Certificate -> Serverul se identifică cu certificatul său
Server Key Exchange -> Contribuția Diffie-Hellman semnată a serverului
Client Key Exchange -> Contribuția Diffie-Hellman a clientului
Change Cipher Spec -> De acum se criptează
Application Data -> Date HTTP criptate
:::

:::note
În trace vezi **două** conexiuni TLS una după alta: browserul preia mai întâi pagina și apoi stabilește o conexiune nouă pentru foaia de stil `style.css`. Fiecare conexiune primește propriul handshake și propria cheie de sesiune. Browserele reale țin conexiunile deschise și economisesc astfel o parte din acest efort. Versiunea mai nouă, **TLS 1.3**, se descurcă în plus cu mai puține mesaje decât TLS 1.2 prezentat aici.
:::

:::tip De reținut
La **handshake-ul TLS**, serverul se identifică cu **certificatul** său, ambele părți stabilesc prin **Diffie-Hellman** o **cheie de sesiune** (serverul își **semnează** contribuția), iar prin **Finished** ambele verifică faptul că nimeni nu a modificat handshake-ul. După aceea, datele sunt transmise ca **Application Data**, criptate simetric.
:::
