Mielőtt elküldenék az első titkosított kérést, a kliensnek és a szervernek meg kell állapodnia: egy eljárásban, egy munkamenetkulcsban — és a kliensnek ellenőriznie kell, kivel beszél. Ezt a kapcsolatfelépítést nevezzük **TLS-kézfogásnak**.

## A lefolyás diagramon

A TCP-nyugták (`ACK`) nélkül a kézfogás így néz ki:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Mi történik eközben — és melyik, a 8.1 szakaszból ismert építőelem áll mögötte:

1. **Client Hello / Server Hello:** A kliens és a szerver üdvözli egymást, véletlen számokat cserélnek, és megegyeznek az eljárásokban (a BeaverTracerben: kulcscsere **ECDHE**-vel, aláírás **ECDSA**-val, titkosítás **AES**-szel).
2. **Certificate:** A szerver elküldi a **tanúsítványát**. A kliens ellenőrzi a CA aláírását, az érvényességet és a nevet. Ha ez nem sikerül, itt megszakítja a kapcsolatot — és a böngésző figyelmeztetést jelenít meg.
3. **Server Key Exchange:** A szerver elküldi a **Diffie–Hellman-részét** — és **aláírja** a privát kulcsával. A kliens a tanúsítványban található nyilvános kulccsal ellenőrzi az aláírást. Így tudja: ez a rész valóban a tanúsítvány birtokosától származik, nem egy man-in-the-middle támadótól.
4. **Client Key Exchange:** A kliens elküldi a saját Diffie–Hellman-részét. Most már mindketten kiszámíthatják ugyanazt a **munkamenetkulcsot** — anélkül, hogy azt valaha is átvitték volna.
5. **Change Cipher Spec:** „Mostantól titkosítok.”
6. **Encrypted Handshake Message (Finished):** Mindkét fél — már titkosítva — elküld egy ellenőrző összeget az eddigi összes kézfogás-üzenetről. Ha egy támadó menet közben módosított valamit, az ellenőrző összegek nem egyeznek, és a kapcsolat megszakad.
7. **Application Data:** Innentől áramlanak a HTTP-adatok — AES-szel szimmetrikusan titkosítva.

:::quiz match
Certificate -> A szerver a tanúsítványával igazolja magát
Server Key Exchange -> A szerver aláírt Diffie–Hellman-része
Client Key Exchange -> A kliens Diffie–Hellman-része
Change Cipher Spec -> Mostantól titkosítva megy az adatforgalom
Application Data -> Titkosított HTTP-adatok
:::

:::note
A nyomkövetésben **két** TLS-kapcsolatot látsz egymás után: a böngésző először letölti az oldalt, majd új kapcsolatot épít fel a `style.css` stíluslaphoz. Minden kapcsolat saját kézfogást és saját munkamenetkulcsot kap. A valódi böngészők nyitva tartják a kapcsolatokat, így megspórolják ennek a költségnek egy részét. Az újabb **TLS 1.3** ráadásul kevesebb üzenettel is beéri, mint az itt bemutatott TLS 1.2.
:::

:::tip Jegyezd meg!
A **TLS-kézfogás** során a szerver a **tanúsítványával** igazolja magát, mindkét fél **Diffie–Hellman** segítségével állapodik meg egy **munkamenetkulcsban** (a szerver **aláírja** a saját részét), a **Finished** üzenettel pedig mindketten ellenőrzik, hogy senki sem módosította a kézfogást. Ezután az adatok **Application Data** formájában, szimmetrikusan titkosítva kerülnek átvitelre.
:::
