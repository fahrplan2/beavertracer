# Quand des paquets se perdent

:::goal
**Objectif d'apprentissage :** Tu sais observer dans le traceur et expliquer comment TCP remarque des données perdues, les renvoie et rétablit l'ordre.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

Dans cette simulation, le câble a été préparé : le **deuxième paquet contenant des données** envoyé du Client-PC au Server se perd. (Tu trouves ce réglage en cliquant sur le câble en mode Exécution : **Perte de paquets ciblée**.)

## L'expérience

1. Passe en mode :fa-play: **Exécuter**, ouvre le **Client TCP simple** sur le **Client-PC** et connecte-le à `192.168.0.20`, port `5000`.
2. Envoie trois messages l'un après l'autre : `Hallo`, puis `Welt`, puis `!`.
3. Observe la fenêtre de discussion : l'écho de `Hallo` arrive tout de suite. Et les deux autres ?
4. Attends quelques secondes. Ouvre ensuite, en mode :fa-magnifying-glass: **Trace**, une trace pour le **Server** (le destinataire), interface `eth0`.

:::quiz mc
Que se passe-t-il avec les échos de `Welt` et `!` ?
- [ ] L'écho de `!` arrive tout de suite, `Welt` manque pour toujours
- [x] Les deux n'arrivent qu'après quelques secondes — ensemble et dans le bon ordre
- [ ] Aucun des deux n'arrive jamais
:::

## Ce que montre le traceur

Côté serveur, le paquet contenant `Welt` manque — il s'est bien perdu. En revanche, tu trouves dans la colonne **Info** trois indications entre crochets :

| Indication | Ce qui s'est passé |
|---|---|
| `[TCP Previous segment not captured]` | Le paquet contenant `!` arrive, mais des octets manquent avant lui — un **trou**. |
| `[TCP Dup ACK …]` | Le serveur acquitte une nouvelle fois le même numéro qu'avant (*duplicate ACK*) : « J'attends toujours l'octet 8. » |
| `[TCP Retransmission]` | Le client envoie `Welt` **encore une fois**. |

:::quiz short
Quel numéro de séquence (`Seq`) porte le paquet marqué `[TCP Retransmission]` ?
= 8
:::

:::quiz short
Quel numéro d'acquittement (`Ack`) le serveur envoie-t-il juste après la retransmission ?
= 17
:::

:::quiz mc
Pourquoi le serveur acquitte-t-il directement jusqu'à l'octet 17 après la retransmission — et pas seulement jusqu'à la fin de `Welt` ?
- [x] Il avait déjà reçu et mis de côté `!` — avec `Welt`, le trou est comblé, maintenant tout est là jusqu'à l'octet 16
- [ ] Le client a renvoyé `Welt` et `!` ensemble une nouvelle fois
- [ ] Les numéros d'acquittement sont toujours arrondis
:::

Vérifier les réponses

Server -> Client-PC: ACK

Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK

Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK

## Ce qui se cache derrière

Le client conserve chaque paquet envoyé jusqu'à ce qu'il soit acquitté et démarre pour cela un **minuteur** (*timer*). Si l'acquittement tarde trop, il renvoie les données — c'est une **retransmission** (*Retransmission*).

Le serveur n'acquitte toujours que jusqu'au **premier trou**. Les données qui arrivent après (ici `!`), il les met de côté jusqu'à ce que le trou soit comblé. Ce n'est qu'alors qu'il transmet tout au programme dans le bon ordre — c'est pourquoi les échos de `Welt` et `!` sont arrivés ensemble.

:::tip À retenir
TCP détecte les pertes grâce aux **acquittements manquants** : le destinataire n'acquitte toujours que jusqu'au premier trou. Si l'acquittement ne vient pas, l'expéditeur renvoie les données **une nouvelle fois** après l'expiration d'un minuteur (*retransmission*). Ce qui arrive après un trou est mis de côté par le destinataire — ainsi, les données parviennent au programme **complètes et dans le bon ordre**.
:::

:::tip Pour aller plus loin : Fast Retransmit
Après `Hallo`, envoie rapidement quatre messages ou plus à la suite. Après le paquet perdu, le client reçoit alors trois *Dup ACKs* consécutifs — et renvoie immédiatement, sans attendre son minuteur. Ce procédé s'appelle **Fast Retransmit** (retransmission rapide).
:::

:::note
Les vraies implémentations de TCP adaptent en outre leur rythme d'envoi : si des paquets se perdent, le réseau est probablement surchargé, et l'expéditeur ralentit (*contrôle de congestion*). Cela dépasse le cadre de ce cours.
:::
