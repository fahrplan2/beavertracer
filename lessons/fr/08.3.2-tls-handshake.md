# Le handshake TLS

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Avant d'envoyer la première requête chiffrée, le client et le serveur doivent se mettre d'accord sur un procédé et sur une clé de session. Le client doit aussi vérifier à qui il parle. Cet établissement de la connexion s'appelle le **handshake TLS**.

## Le déroulement dans le diagramme

Sans les acquittements TCP (`ACK`), le handshake se présente ainsi :

:::seq
mode: text
Client -> Serveur: Client Hello | nombre aléatoire, procédés possibles
Serveur -> Client: Server Hello | procédé choisi, nombre aléatoire
Serveur -> Client: Certificate | certificat du serveur
Serveur -> Client: Server Key Exchange | part DH, signée
Serveur -> Client: Server Hello Done
Client -> Serveur: Client Key Exchange | part DH du client
Client -> Serveur: Change Cipher Spec | chiffré à partir de maintenant
Client -> Serveur: Encrypted Handshake Message | Finished
Serveur -> Client: Change Cipher Spec | chiffré à partir de maintenant
Serveur -> Client: Encrypted Handshake Message | Finished
Client -> Serveur: Application Data | GET / (chiffré)
Serveur -> Client: Application Data | page web (chiffrée)
:::

Voici ce qui se passe à chaque étape et quelle brique de la section 8.1 se cache derrière :

1. **Client Hello / Server Hello :** le client et le serveur se saluent, échangent des nombres aléatoires et se mettent d'accord sur les procédés (dans BeaverTracer : échange de clés avec **ECDHE**, signature avec **ECDSA**, chiffrement avec **AES**).
2. **Certificate :** le serveur envoie son **certificat**. Le client vérifie la signature de l'autorité de certification (CA), la validité et le nom. Si la vérification échoue, il interrompt la connexion ici et le navigateur affiche un avertissement.
3. **Server Key Exchange :** le serveur envoie sa **part Diffie-Hellman** et la **signe** avec sa clé privée. Le client vérifie la signature avec la clé publique contenue dans le certificat. Il sait ainsi que cette part provient vraiment du titulaire du certificat et non d'un attaquant de type « man-in-the-middle ».
4. **Client Key Exchange :** le client envoie sa part Diffie-Hellman. Les deux côtés peuvent maintenant calculer la même **clé de session**, sans qu'elle ait jamais été transmise.
5. **Change Cipher Spec :** « À partir de maintenant, je chiffre. »
6. **Encrypted Handshake Message (Finished) :** les deux côtés envoient, déjà chiffrée, une somme de contrôle calculée sur tous les messages du handshake échangés jusqu'ici. Si un attaquant a modifié quelque chose en route, les sommes de contrôle ne correspondent pas et la connexion est interrompue.
7. **Application Data :** à partir d'ici, les données HTTP circulent, chiffrées de manière symétrique avec AES.

:::quiz match
Certificate -> Le serveur s'identifie avec son certificat
Server Key Exchange -> Part Diffie-Hellman signée du serveur
Client Key Exchange -> Part Diffie-Hellman du client
Change Cipher Spec -> À partir de maintenant, tout est chiffré
Application Data -> Données HTTP chiffrées
:::

:::note
Dans la trace, tu vois **deux** connexions TLS l'une après l'autre : le navigateur récupère d'abord la page, puis établit une nouvelle connexion pour la feuille de style `style.css`. Chaque connexion a son propre handshake et sa propre clé de session. Les vrais navigateurs gardent les connexions ouvertes et s'épargnent ainsi une partie de ce travail. De plus, la version plus récente **TLS 1.3** nécessite moins de messages que la version TLS 1.2 présentée ici.
:::

:::tip À retenir
Lors du **handshake TLS**, le serveur s'identifie avec son **certificat**. Les deux côtés négocient une **clé de session** grâce à **Diffie-Hellman** (le serveur **signe** sa part). Avec **Finished**, chacun vérifie que personne n'a modifié le handshake. Ensuite, les données sont transmises sous forme d'**Application Data**, chiffrées de manière symétrique.
:::
