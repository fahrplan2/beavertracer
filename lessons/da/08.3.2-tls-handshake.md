# TLS-handshaket

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Før den første krypterede forespørgsel sendes, skal klient og server blive enige: om en metode, om en sessionsnøgle — og klienten skal tjekke, hvem den egentlig taler med. Denne opbygning af forbindelse hedder **TLS-handshake**.

## Observer

Åbn `https://www.beaver-schule.de/` på **Client-PC** (hvis du ikke allerede har gjort det), åbn et trace for **Client-PC** og filtrer med `tls`.

## Forløbet i diagrammet

Uden TCP-kvitteringerne (`ACK`) ser handshaket sådan ud:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Hvad der sker undervejs — og hvilken byggesten fra afsnit 8.1 der ligger bag:

1. **Client Hello / Server Hello:** Klient og server hilser på hinanden, udveksler tilfældige tal og bliver enige om metoderne (i BeaverTracer: nøgleudveksling med **ECDHE**, signatur med **ECDSA**, kryptering med **AES**).
2. **Certificate:** Serveren sender sit **certifikat**. Klienten tjekker CA'ens signatur, gyldighed og navne. Hvis det mislykkes, afbryder klienten her — og browseren viser en advarsel.
3. **Server Key Exchange:** Serveren sender sin **Diffie-Hellman-andel** — og **signerer** den med sin private nøgle. Klienten tjekker signaturen med den offentlige nøgle fra certifikatet. Dermed ved den: Denne andel kommer virkelig fra indehaveren af certifikatet og ikke fra en man-in-the-middle.
4. **Client Key Exchange:** Klienten sender sin Diffie-Hellman-andel. Nu kan begge parter beregne den samme **sessionsnøgle** — uden at den nogensinde er blevet overført.
5. **Change Cipher Spec:** "Fra nu af krypterer jeg."
6. **Encrypted Handshake Message (Finished):** Begge sider sender — allerede krypteret — en kontrolsum over alle hidtidige handshake-beskeder. Hvis en angriber har ændret noget undervejs, passer kontrolsummerne ikke, og forbindelsen afbrydes.
7. **Application Data:** Herfra flyder HTTP-dataene — symmetrisk krypteret med AES.

:::quiz match
Certificate -> Serveren legitimerer sig med sit certifikat
Server Key Exchange -> Serverens signerede Diffie-Hellman-andel
Client Key Exchange -> Klientens Diffie-Hellman-andel
Change Cipher Spec -> Fra nu af krypteres der
Application Data -> Krypterede HTTP-data
:::

:::note
I trace ser du **to** TLS-forbindelser efter hinanden: Browseren henter først siden og opbygger derefter en ny forbindelse til stylesheetet `style.css`. Hver forbindelse får sit eget handshake og sin egen sessionsnøgle. Rigtige browsere holder forbindelser åbne og sparer på den måde en del af dette arbejde. Den nyere version **TLS 1.3** klarer sig desuden med færre beskeder end det TLS 1.2, der vises her.
:::

:::tip Husk
Ved **TLS-handshaket** legitimerer serveren sig med sit **certifikat**, begge sider forhandler en **sessionsnøgle** på plads med **Diffie-Hellman** (serveren **signerer** sin andel), og med **Finished** tjekker begge, at ingen har ændret handshaket. Derefter overføres dataene som **Application Data**, symmetrisk krypteret.
:::
