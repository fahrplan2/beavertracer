# Når pakker går tabt

:::goal
**Læringsmål:** Du kan i tracer'en observere og forklare, hvordan TCP opdager tabte data, sender dem igen og genopretter rækkefølgen.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

I denne simulation er kablet præpareret: Den **anden pakke med data** fra Client-PC til serveren går tabt. (Du finder indstillingen, når du klikker på kablet i Kør-tilstand: **Målrettet pakkeforsinkelse**.)

## Eksperimentet

1. Skift til :fa-play: **Kør**-tilstand, åbn **Simpel TCP-klient** på **Client-PC** og forbind den til `192.168.0.20`, port `5000`.
2. Send tre beskeder efter hinanden: `Hallo`, derefter `Welt`, derefter `!`.
3. Se på chatvinduet: Ekkoet af `Hallo` kommer med det samme. Og de to andre?
4. Vent et par sekunder. Åbn derefter i :fa-magnifying-glass: **Spor**-tilstand et trace for **serveren** (modtageren), port `eth0`.

:::quiz mc
Hvad sker der med ekkoerne af `Welt` og `!`?
- [ ] Ekkoet af `!` kommer med det samme, `Welt` mangler for altid
- [x] Begge kommer først efter nogle sekunder — sammen og i den rigtige rækkefølge
- [ ] Ingen af dem kommer nogensinde frem
:::

## Hvad tracer'en viser

Hos serveren mangler pakken med `Welt` — den er jo gået tabt. Til gengæld finder du i **Info**-kolonnen tre henvisninger i kantede parenteser:

| Henvisning | Hvad der skete |
|---|---|
| `[TCP Previous segment not captured]` | Pakken med `!` kommer frem, men der mangler bytes før den — et **hul**. |
| `[TCP Dup ACK …]` | Serveren kvitterer endnu en gang for det samme nummer som før (*duplicate ACK*): "Jeg venter stadig på byte 8." |
| `[TCP Retransmission]` | Klienten sender `Welt` **endnu en gang**. |

:::quiz short
Hvilket sekvensnummer (`Seq`) har den pakke, der er markeret med `[TCP Retransmission]`?
= 8
:::

:::quiz short
Hvilket kvitteringsnummer (`Ack`) sender serveren direkte efter gensendelsen?
= 17
:::

:::quiz mc
Hvorfor kvitterer serveren efter gensendelsen med det samme op til byte 17 — og ikke bare til slutningen af `Welt`?
- [x] Den havde allerede modtaget `!` og holdt det tilbage — med `Welt` er hullet lukket, nu er alt til og med byte 16 der
- [ ] Klienten har sendt `Welt` og `!` endnu en gang samlet
- [ ] Kvitteringsnumre bliver altid rundet op
:::

:::evaluate
Tjek svar
:::

I sekvensdiagrammet ser det sådan ud — den stiplede pil med ✕ er den tabte pakke:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Hvad der ligger bag

Klienten gemmer hver afsendt pakke, indtil den er kvitteret, og starter en **timer** til formålet. Hvis kvitteringen udebliver for længe, sender den dataene igen — en **gensendelse** (*retransmission*).

Serveren kvitterer altid kun op til det **første hul**. Data, der kommer frem efter det (her `!`), holder den tilbage, indtil hullet er fyldt. Først da giver den alt videre til programmet i den rigtige rækkefølge — derfor kom ekkoerne af `Welt` og `!` sammen.

:::tip Husk
TCP opdager tab på **manglende kvitteringer**: Modtageren kvitterer altid kun op til det første hul. Udebliver kvitteringen, sender afsenderen dataene **igen**, når en timer er udløbet (*retransmission*). Det, der kommer frem efter et hul, holder modtageren tilbage — så dataene når programmet **fuldstændigt og i den rigtige rækkefølge**.
:::

:::tip Fordybelse: Fast Retransmit
Send fire eller flere beskeder hurtigt efter hinanden efter `Hallo`. Efter den tabte pakke får klienten så tre *Dup ACK'er* i træk — og sender straks igen uden at vente på sin timer. Denne fremgangsmåde hedder **Fast Retransmit**.
:::

:::note
Rigtige TCP-implementeringer tilpasser desuden deres sendetempo: Hvis pakker går tabt, er netværket sandsynligvis overbelastet, og afsenderen bliver langsommere (*congestion control*). Det går ud over dette kursus.
:::
