## Der Ablauf im Diagramm

Ohne die TCP-Bestätigunge (`ACK`) guggt der Handshake so aus:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Was dabei passiert — un welcher Baustein aus Abschnitt 8.1 dahinnerstecke duht:

1. **Client Hello / Server Hello:** Client un Server begrüße sich, tausche Zufallszahle aus un einische sich uff die Verfahre (in BeaverTracer: Schlüsselaustausch mit **ECDHE**, Signatur mit **ECDSA**, Verschlüsselung mit **AES**).
2. **Certificate:** Der Server schickt sei **Zertifikat**. Der Client prüft die Signatur von de CA, die Gültischkeit un de Name. Schlächt des fehl, bricht er hier ab — un der Browser zeigt e Warnung.
3. **Server Key Exchange:** Der Server schickt sein **Diffie-Hellman-Anteil** — un **signiert** ihn mit seim private Schlüssel. Der Client prüft die Signatur mit em öffentliche Schlüssel aus em Zertifikat. So weiß er: Dieser Anteil kimmt wirklisch vom Inhaber vom Zertifikat, net von eme Man-in-the-Middle.
4. **Client Key Exchange:** Der Client schickt sein Diffie-Hellman-Anteil. Jetzt kenne alle zwaa de gleiche **Sitzungsschlüssel** ausrechne — ohne dass er jemals übertrage worde is.
5. **Change Cipher Spec:** „Ab jetzt verschlüssel isch.“
6. **Encrypted Handshake Message (Finished):** Beide Seite schicke — schon verschlüsselt — e Prüfsumm über alle bisherische Handshake-Nachrichte. Hat en Angreifer unnerwegs ebbes verännert, passe die Prüfsumme net, un die Verbindung werd abgebroche.
7. **Application Data:** Ab hier fließe die HTTP-Date — symmetrisch verschlüsselt mit AES.

:::quiz match
Certificate -> Der Server weist sich mit seinem Zertifikat aus
Server Key Exchange -> Signierter Diffie-Hellman-Anteil des Servers
Client Key Exchange -> Diffie-Hellman-Anteil des Clients
Change Cipher Spec -> Ab jetzt wird verschlüsselt
Application Data -> Verschlüsselte HTTP-Daten
:::

:::note
Im Trace siehst du **zwei** TLS-Verbindunge nacheinanner: Der Browser holt erscht die Seit un baut dann e neue Verbindung für des Stylesheet `style.css` uff. Jede Verbindung kriegt en eigene Handshake un en eigene Sitzungsschlüssel. Echte Browser halte Verbindunge offe un spare sich so en Teil von dem Aufwand. Die neuere Version **TLS 1.3** kimmt außerdem mit wenischer Nachrichte aus als des hier gezeischte TLS 1.2.
:::

:::tip Merksatz
Beim **TLS-Handshake** weist sich der Server mit seim **Zertifikat** aus, beide Seite handele per **Diffie-Hellman** en **Sitzungsschlüssel** aus (der Server **signiert** sein Anteil), un mit **Finished** prüfe beide, dass niemand de Handshake verännert hat. Danach werre die Date als **Application Data** symmetrisch verschlüsselt übertrage. Ei gude, so einfach isses!
:::
