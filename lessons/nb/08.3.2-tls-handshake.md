# TLS-handshaken

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Før den første krypterte forespørselen sendes, må klient og server bli enige: om en metode, om en øktnøkkel — og klienten må kontrollere hvem den snakker med. Denne oppkoblingen heter **TLS-handshake**.

## Observer

Åpne `https://www.beaver-schule.de/` på **Client-PC** (hvis du ikke har gjort det allerede), åpne en trace for **Client-PC** og filtrer med `tls`.

## Forløpet i diagrammet

Uten TCP-bekreftelsene (`ACK`) ser handshaken slik ut:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Dette skjer underveis — og hvilken byggestein fra avsnitt 8.1 som ligger bak:

1. **Client Hello / Server Hello:** Klient og server hilser på hverandre, utveksler tilfeldige tall og blir enige om metodene (i BeaverTracer: nøkkelutveksling med **ECDHE**, signatur med **ECDSA**, kryptering med **AES**).
2. **Certificate:** Serveren sender **sertifikatet** sitt. Klienten kontrollerer signaturen fra CA-en, gyldigheten og navnet. Hvis dette mislykkes, avbryter klienten her — og nettleseren viser en advarsel.
3. **Server Key Exchange:** Serveren sender sin **Diffie-Hellman-andel** — og **signerer** den med sin private nøkkel. Klienten kontrollerer signaturen med den offentlige nøkkelen fra sertifikatet. Slik vet klienten at denne andelen virkelig kommer fra innehaveren av sertifikatet, og ikke fra en man-in-the-middle.
4. **Client Key Exchange:** Klienten sender sin Diffie-Hellman-andel. Nå kan begge beregne den samme **øktnøkkelen** — uten at den noen gang er blitt overført.
5. **Change Cipher Spec:** «Fra nå av krypterer jeg.»
6. **Encrypted Handshake Message (Finished):** Begge sider sender — allerede kryptert — en kontrollsum over alle hittil sendte handshake-meldinger. Hvis en angriper har endret noe underveis, stemmer ikke kontrollsummene, og forbindelsen avbrytes.
7. **Application Data:** Herfra flyter HTTP-dataene — symmetrisk kryptert med AES.

:::quiz match
Certificate -> Serveren legitimerer seg med sertifikatet sitt
Server Key Exchange -> Serverens signerte Diffie-Hellman-andel
Client Key Exchange -> Klientens Diffie-Hellman-andel
Change Cipher Spec -> Fra nå av krypteres det
Application Data -> Krypterte HTTP-data
:::

:::note
I tracen ser du **to** TLS-forbindelser etter hverandre: Nettleseren henter først siden og setter deretter opp en ny forbindelse for stilarket `style.css`. Hver forbindelse får sin egen handshake og sin egen øktnøkkel. Ekte nettlesere holder forbindelser åpne og sparer dermed noe av denne jobben. Den nyere versjonen **TLS 1.3** klarer seg dessuten med færre meldinger enn TLS 1.2, som vises her.
:::

:::tip Husk dette
I **TLS-handshaken** legitimerer serveren seg med **sertifikatet** sitt, begge sider blir enige om en **øktnøkkel** via **Diffie-Hellman** (serveren **signerer** sin andel), og med **Finished** kontrollerer begge at ingen har endret handshaken. Deretter overføres dataene som **Application Data**, symmetrisk kryptert.
:::
