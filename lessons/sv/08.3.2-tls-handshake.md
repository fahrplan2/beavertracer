# TLS-handskakningen

:::sim
url=/sims/lesson-8.2.1.btsim
:::

Innan den första krypterade förfrågan skickas måste klient och server komma överens: om ett förfarande, om en sessionsnyckel — och klienten måste kontrollera vem den pratar med. Denna uppkoppling kallas **TLS-handskakning** (TLS-handshake).

## Observera

Öppna `https://www.beaver-schule.de/` på **Client-PC** (om du inte redan har gjort det), öppna en trace för **Client-PC** och filtrera med `tls`.

## Förloppet i diagrammet

Utan TCP-bekräftelserna (`ACK`) ser handskakningen ut så här:

:::seq
mode: text
Client -> Server: Client Hello | Zufallszahl, mögliche Verfahren
Server -> Client: Server Hello | gewähltes Verfahren, Zufallszahl
Server -> Client: Certificate | Zertifikat des Servers
Server -> Client: Server Key Exchange | DH-Anteil, signiert
Server -> Client: Server Hello Done
Client -> Server: Client Key Exchange | DH-Anteil des Clients
Client -> Server: Change Cipher Spec | ab jetzt verschlüsselt
Client -> Server: Encrypted Handshake Message | Finished
Server -> Client: Change Cipher Spec | ab jetzt verschlüsselt
Server -> Client: Encrypted Handshake Message | Finished
Client -> Server: Application Data | GET / (verschlüsselt)
Server -> Client: Application Data | Webseite (verschlüsselt)
:::

Vad som händer här — och vilken byggsten från avsnitt 8.1 som ligger bakom:

1. **Client Hello / Server Hello:** Klient och server hälsar på varandra, utbyter slumptal och kommer överens om förfarandena (i BeaverTracer: nyckelutbyte med **ECDHE**, signatur med **ECDSA**, kryptering med **AES**).
2. **Certificate:** Servern skickar sitt **certifikat**. Klienten kontrollerar CA:ns signatur, giltighet och namn. Om det misslyckas avbryter klienten här — och webbläsaren visar en varning.
3. **Server Key Exchange:** Servern skickar sin **Diffie-Hellman-andel** — och **signerar** den med sin privata nyckel. Klienten kontrollerar signaturen med den publika nyckeln från certifikatet. Så vet klienten: den här andelen kommer verkligen från certifikatets innehavare, inte från en man-in-the-middle.
4. **Client Key Exchange:** Klienten skickar sin Diffie-Hellman-andel. Nu kan båda beräkna samma **sessionsnyckel** — utan att den någonsin har överförts.
5. **Change Cipher Spec:** ”Från och med nu krypterar jag.”
6. **Encrypted Handshake Message (Finished):** Båda sidor skickar — redan krypterad — en kontrollsumma över alla hittillsvarande handskakningsmeddelanden. Om en angripare har ändrat något på vägen stämmer inte kontrollsummorna, och anslutningen avbryts.
7. **Application Data:** Härifrån flödar HTTP-data — symmetriskt krypterad med AES.

:::quiz match
Certificate -> Servern legitimerar sig med sitt certifikat
Server Key Exchange -> Serverns signerade Diffie-Hellman-andel
Client Key Exchange -> Klientens Diffie-Hellman-andel
Change Cipher Spec -> Från och med nu krypteras det
Application Data -> Krypterad HTTP-data
:::

:::note
I tracen ser du **två** TLS-anslutningar efter varandra: Webbläsaren hämtar först sidan och kopplar sedan upp en ny anslutning för stilmallen `style.css`. Varje anslutning får en egen handskakning och en egen sessionsnyckel. Riktiga webbläsare håller anslutningar öppna och sparar därmed en del av detta arbete. Den nyare versionen **TLS 1.3** klarar dessutom sig med färre meddelanden än TLS 1.2 som visas här.
:::

:::tip Att komma ihåg
Vid **TLS-handskakningen** legitimerar sig servern med sitt **certifikat**, båda sidor förhandlar fram en **sessionsnyckel** via **Diffie-Hellman** (servern **signerar** sin andel), och med **Finished** kontrollerar båda att ingen har ändrat handskakningen. Därefter överförs data som **Application Data**, symmetriskt krypterad.
:::
