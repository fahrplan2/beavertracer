# Kada se paketi izgube

:::goal
**Cilj učenja:** Možeš da u Tracer-u posmatraš i objasniš kako TCP primećuje izgubljene podatke, ponovo ih šalje i vraća redosled.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

U ovoj simulaciji je kabl pripremljen: **drugi paket sa podacima** od Client-PC do servera se gubi. (Podešavanje pronalaziš kada u :fa-play: Režimu izvršavanja klikneš na kabl: **Ciljna gubitak paketa**.)

## Eksperiment

1. Pređi u :fa-play: **Izvršavanje** režim, otvori na **Client-PC** program **Jednostavni TCP klijent** i poveži ga sa `192.168.0.20`, port `5000`.
2. Pošalji redom tri poruke: `Hallo`, zatim `Welt`, pa `!`.
3. Posmatraj prozor za ćaskanje: Eho poruke `Hallo` stiže odmah. A druge dve?
4. Sačekaj nekoliko sekundi. Zatim u režimu :fa-magnifying-glass: **Praćenje** otvori trace za **Server** (primalac), priključak `eth0`.

:::quiz mc
Šta se dešava sa ehom poruka `Welt` i `!`?
- [ ] Eho poruke `!` stiže odmah, `Welt` nedostaje zauvek
- [x] Oba stižu tek posle nekoliko sekundi — zajedno i u ispravnom redosledu
- [ ] Nijedan od ova dva ne stiže nikada
:::

## Šta prikazuje Tracer

Kod servera nedostaje paket sa `Welt` — jer se izgubio. Umesto toga u koloni **Info** pronalaziš tri napomene u uglastim zagradama:

| Napomena | Šta se desilo |
|---|---|
| `[TCP Previous segment not captured]` | Paket sa `!` stiže, ali pre njega nedostaju bajtovi — **praznina**. |
| `[TCP Dup ACK …]` | Server ponovo potvrđuje isti broj kao ranije (*duplicate ACK*): „I dalje čekam bajt 8.“ |
| `[TCP Retransmission]` | Klijent šalje `Welt` **još jednom**. |

:::quiz short
Koji redni broj (`Seq`) ima paket označen sa `[TCP Retransmission]`?
= 8
:::

:::quiz short
Koji broj potvrde (`Ack`) server šalje neposredno posle ponovnog slanja?
= 17
:::

:::quiz mc
Zašto server posle ponovnog slanja odmah potvrđuje do bajta 17 — a ne samo do kraja poruke `Welt`?
- [x] Već je primio `!` i zadržao ga — sa `Welt` je praznina zatvorena, sada je sve do bajta 16 stiglo
- [ ] Klijent je ponovo poslao `Welt` i `!` zajedno
- [ ] Brojevi potvrde se uvek zaokružuju
:::

:::evaluate
Proveri odgovore
:::

U dijagramu komunikacije to izgleda ovako — isprekidana strelica sa ✕ je izgubljeni paket:

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## Šta stoji iza toga

Klijent čuva svaki poslati paket dok ne bude potvrđen i za to pokreće **tajmer**. Ako potvrda predugo izostane, ponovo šalje podatke — **ponovno slanje** (*Retransmission*).

Server uvek potvrđuje samo do **prve praznine**. Podatke koji stignu posle nje (ovde `!`) zadržava dok se praznina ne popuni. Tek tada sve prosleđuje programu u ispravnom redosledu — zato su eha poruka `Welt` i `!` stigla zajedno.

:::tip Zapamti
TCP prepoznaje gubitke po **nedostajućim potvrdama**: primalac uvek potvrđuje samo do prve praznine. Ako potvrda izostane, pošiljalac po isteku tajmera podatke šalje **ponovo** (*Retransmission*). Ono što stigne posle praznine primalac zadržava — tako podaci stižu do programa **potpuni i u ispravnom redosledu**.
:::

:::tip Produbljivanje: Fast Retransmit
Pošalji posle `Hallo` četiri ili više poruka brzo jednu za drugom. Posle izgubljenog paketa klijent tada dobija tri *Dup ACK*-a zaredom — i odmah ponovo šalje, ne čekajući svoj tajmer. Ovaj postupak se zove **Fast Retransmit**.
:::

:::note
Pravne TCP implementacije osim toga prilagođavaju brzinu slanja: ako se paketi gube, mreža je verovatno preopterećena i pošiljalac usporava (*kontrola zagušenja*). To prevazilazi okvire ovog kursa.
:::
