# Wenn Pakete verloren gehen

:::goal
**Lernziel:** Du kannst im Tracer beobachten und erklären, wie TCP verlorene Daten bemerkt, erneut sendet und die Reihenfolge wiederherstellt.
:::

:::sim
url=/sims/lesson-5.4.btsim
:::

In dieser Simulation ist das Kabel präpariert: Das **zweite Paket mit Daten** vom Client-PC zum Server geht verloren. (Du findest die Einstellung, wenn du im Ausführen-Modus auf das Kabel klickst: **Gezielter Paketverlust**.)

## Das Experiment

1. Wechsle in den :fa-play: **Ausführen**-Modus, öffne auf dem **Client-PC** den **Einfachen TCP-Client** und verbinde ihn mit `192.168.0.20`, Port `5000`.
2. Schicke nacheinander drei Nachrichten: `Hallo`, dann `Welt`, dann `!`.
3. Beobachte das Chat-Fenster: Das Echo von `Hallo` kommt sofort. Und die anderen beiden?
4. Warte ein paar Sekunden. Öffne dann im :fa-magnifying-glass: **Verfolgung**-Modus einen Trace für den **Server** (der Empfänger), Anschluss `eth0`.

:::quiz mc
Was passiert mit den Echos von `Welt` und `!`?
- [ ] Das Echo von `!` kommt sofort, `Welt` fehlt für immer
- [x] Beide kommen erst nach einigen Sekunden — gemeinsam und in der richtigen Reihenfolge
- [ ] Keines der beiden kommt jemals an
:::

## Was der Tracer zeigt

Beim Server fehlt das Paket mit `Welt` — es ist ja verloren gegangen. Dafür findest du in der **Info**-Spalte drei Hinweise in eckigen Klammern:

| Hinweis | Was passiert ist |
|---|---|
| `[TCP Previous segment not captured]` | Das Paket mit `!` kommt an, aber davor fehlen Bytes — eine **Lücke**. |
| `[TCP Dup ACK …]` | Der Server bestätigt noch einmal dieselbe Nummer wie vorher (*duplicate ACK*): „Ich warte immer noch auf Byte 8.“ |
| `[TCP Retransmission]` | Der Client schickt `Welt` **noch einmal**. |

:::quiz short
Welche Sequenznummer (`Seq`) hat das Paket, das mit `[TCP Retransmission]` markiert ist?
= 8
:::

:::quiz short
Welche Bestätigungsnummer (`Ack`) schickt der Server direkt nach der Neuübertragung?
= 17
:::

:::quiz mc
Warum bestätigt der Server nach der Neuübertragung gleich bis Byte 17 — und nicht nur bis zum Ende von `Welt`?
- [x] Er hatte `!` schon empfangen und zurückgehalten — mit `Welt` ist die Lücke geschlossen, jetzt ist alles bis Byte 16 da
- [ ] Der Client hat `Welt` und `!` noch einmal gemeinsam geschickt
- [ ] Bestätigungsnummern werden immer gerundet
:::

Client-PC -> Server: ACK

## Was dahintersteckt

Der Client bewahrt jedes gesendete Paket auf, bis es bestätigt ist, und startet dafür einen **Timer**. Bleibt die Bestätigung zu lange aus, sendet er die Daten erneut — eine **Neuübertragung** (*Retransmission*).

Der Server bestätigt immer nur bis zur **ersten Lücke**. Daten, die danach ankommen (hier `!`), hält er zurück, bis die Lücke gefüllt ist. Erst dann gibt er alles in der richtigen Reihenfolge an das Programm weiter — deshalb kamen die Echos von `Welt` und `!` gemeinsam.

:::tip Merksatz
TCP erkennt Verluste an **fehlenden Bestätigungen**: Der Empfänger bestätigt immer nur bis zur ersten Lücke. Bleibt die Bestätigung aus, sendet der Sender die Daten nach Ablauf eines Timers **erneut** (*Retransmission*). Was nach einer Lücke ankommt, hält der Empfänger zurück — so erreichen die Daten das Programm **vollständig und in der richtigen Reihenfolge**.
:::

:::tip Vertiefung: Fast Retransmit
Schick nach `Hallo` vier oder mehr Nachrichten schnell hintereinander. Nach dem verlorenen Paket bekommt der Client dann drei *Dup ACKs* in Folge — und sendet sofort neu, ohne auf seinen Timer zu warten. Dieses Verfahren heißt **Fast Retransmit**.
:::

:::note
Echte TCP-Implementierungen passen außerdem ihr Sendetempo an: Gehen Pakete verloren, ist das Netz vermutlich überlastet, und der Sender wird langsamer (*Staukontrolle*). Das geht über diesen Kurs hinaus.
:::
