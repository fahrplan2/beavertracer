:::goal

在這個模擬中，纜線被動了手腳：從 Client-PC 傳往 Server 的**第二個含資料的封包**會遺失。（在 執行模式 中點選纜線，就能找到這項設定：**目標封包遺失**。）

## 實驗

1. 切換到 :fa-play: **執行**模式，在 **Client-PC** 上開啟**簡單 TCP 用戶端**，並連線到 `192.168.0.20`，連接埠 `5000`。
2. 依序傳送三則訊息：`Hallo`、`Welt`，然後是 `!`。
3. 觀察聊天視窗：`Hallo` 的回顯會立刻出現。那另外兩則呢？
4. 等待幾秒鐘。然後在 :fa-magnifying-glass: **追蹤**模式中，為 **Server**（接收端）的連接埠 `eth0` 開啟一個追蹤。

:::quiz mc
`Welt` 和 `!` 的回顯會發生什麼事？
- [ ] `!` 的回顯立刻出現，`Welt` 永遠不會出現
- [x] 兩者都要等幾秒鐘後才出現 — 一起出現，而且順序正確
- [ ] 兩者都永遠不會到達
:::

## 追蹤工具顯示了什麼

在 Server 端缺少含有 `Welt` 的封包 — 因為它遺失了。不過，你可以在 **Info** 欄中找到三個放在方括號裡的提示：

| 提示 | 發生了什麼事 |
|---|---|
| `[TCP Previous segment not captured]` | 含有 `!` 的封包到達了，但在它之前缺少了一些位元組 — 出現了一個**缺口**。 |
| `[TCP Dup ACK …]` | 伺服器再次確認與先前相同的號碼（*duplicate ACK*，重複確認）：「我還在等第 8 個位元組。」 |
| `[TCP Retransmission]` | 用戶端**再一次**傳送 `Welt`。 |

:::quiz short
標示為 `[TCP Retransmission]` 的封包，其序號（`Seq`）是多少？
= 8
:::

:::quiz short
伺服器在重傳之後，緊接著傳送的確認號碼（`Ack`）是多少？
= 17
:::

:::quiz mc
為什麼伺服器在重傳之後會直接確認到第 17 個位元組 — 而不是只確認到 `Welt` 的結尾？
- [x] 它先前已經收到 `!` 並暫時保留 — 有了 `Welt` 之後缺口就補上了，現在直到第 16 個位元組的資料都齊全了
- [ ] 用戶端把 `Welt` 和 `!` 一起再傳送了一次
- [ ] 確認號碼一律會進位
:::

:::evaluate
檢查答案
:::

在序列圖中看起來是這樣 — 帶有 ✕ 的虛線箭頭就是遺失的封包：

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hallo" len=7
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=7
Client-PC -> Server: ACK
Client-PC -x Server: PSH, ACK "Welt" len=6
Client-PC -> Server: PSH, ACK "!" len=3
Server -> Client-PC: ACK
Client-PC -> Server: PSH, ACK "Welt" len=6 seq=8
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=9
Client-PC -> Server: ACK
:::

## 背後的原理

用戶端會保留每個已傳送的封包，直到它被確認為止，並為此啟動一個**計時器**。如果確認等太久還沒來，它就會重新傳送資料 — 這就是**重傳**（*Retransmission*）。

伺服器永遠只確認到**第一個缺口**為止。缺口之後到達的資料（這裡是 `!`），它會先保留，直到缺口被補上。接著它才會把所有資料依正確的順序交給應用程式 — 所以 `Welt` 和 `!` 的回顯才會一起出現。

:::tip 重點整理
TCP 透過**缺少確認**來發現資料遺失：接收端永遠只確認到第一個缺口為止。如果確認沒有出現，發送端會在計時器逾時後**再次**傳送資料（*Retransmission*）。缺口之後到達的資料，接收端會先保留 — 這樣資料就能**完整且依正確順序**送達應用程式。
:::

:::tip 進階：Fast Retransmit
在 `Hallo` 之後，快速連續傳送四則或更多訊息。在封包遺失之後，用戶端會連續收到三個 *Dup ACK* — 並且立即重傳，不必等待它的計時器。這種方式稱為 **Fast Retransmit**（快速重傳）。
:::

:::note
真實的 TCP 實作還會調整自己的傳送速度：如果封包遺失，網路很可能已經壅塞，發送端就會放慢速度（*壅塞控制*）。這已超出本課程的範圍。
:::
