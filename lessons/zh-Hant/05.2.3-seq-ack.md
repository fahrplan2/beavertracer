# 序號與確認號碼

:::sim
url=/sims/lesson-5.1.btsim
:::

TCP 怎麼知道所有資料是否都已送達，而且順序是否正確？雙方都會為自己傳送的**位元組編號**：

- **序號**（`SEQ`）是這個封包中第一個位元組的編號。
- **確認號碼**（`ACK`）表示：「到這裡為止我都收到了——接下來我期待收到第 … 號位元組。」

另外有兩條規則：`SYN` 和 `FIN` 雖然不攜帶資料，但各算作一個位元組。而且雙方各自計數——因此圖中有兩組編號，紅色（用戶端）和藍色（伺服器）。

## 動手計算

這裡再看一次你的連線。線條上的數字顯示該電腦在這一點的計數值：

:::seq
Client-PC -> Server: SYN
Server -> Client-PC: SYN, ACK
Client-PC -> Server: ACK
Client-PC -> Server: PSH, ACK "Hello World" len=13
Server -> Client-PC: ACK
Server -> Client-PC: PSH, ACK len=13
Client-PC -> Server: ACK
Client-PC -> Server: FIN, ACK
Server -> Client-PC: ACK
Server -> Client-PC: FIN, ACK
Client-PC -> Server: ACK
:::

一起看看紅色的數字序列：

1. 用戶端從 `SEQ=0` 開始。它的 `SYN` 用掉一個編號——伺服器以 `ACK=1` 確認。
2. 訊息從 `SEQ=1` 開始，長度為 13 位元組（第 1 到第 13 號位元組）。伺服器以 `ACK=14` 確認：「接下來我期待第 14 號位元組。」
3. 因此用戶端的 `FIN` 帶有 `SEQ=14`，並以 `ACK=15` 確認。

伺服器的藍色序列運作方式完全相同。

:::tip 重點整理
**序號**（`SEQ`）是封包中第一個位元組的編號。**確認號碼**（`ACK`）是接收端期待的下一個位元組的編號——在它之前的資料都已送達。規則是：**ACK = SEQ + 所收到資料的長度**；`SYN` 和 `FIN` 各算作一個位元組。雙方各自計算自己的位元組。
:::

:::tip 試試看
在**簡單 TCP 用戶端**中再建立一次連線，並連續傳送兩則訊息。先預測 **Info** 欄中會出現哪些 `Seq` 和 `Ack`——然後在追蹤中驗證。
:::

## 練習

:::quiz short
用戶端傳送一個 `Seq=1`、`Len=13` 的封包。伺服器會回傳哪個確認號碼？
= 14
:::

:::quiz short
接著用戶端傳送下一則訊息。它從哪個序號開始？
= 14
:::

:::note
在真實的網路中，計數並不是從 0 開始：雙方各自選擇一個**隨機的起始編號**（*Initial Sequence Number*，ISN），範圍在 0 到約 43 億之間。達到最大編號後，會再從 0 繼續。追蹤工具會減去起始編號，顯示**相對**編號——和 Wireshark 一樣。所以你看到的是 `Seq=0` 和 `Seq=1`。

此外，每個封包中都有 `Win=`——即**視窗大小**：表示接收端目前能接收多少位元組。接收端藉此讓過快的發送端慢下來（*流量控制*）。在 BeaverTracer 中，視窗大小始終固定不變。
:::
