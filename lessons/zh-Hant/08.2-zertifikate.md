# 憑證：這把金鑰屬於誰？

有了非對稱式加密和數位簽章，一切似乎都解決了：你銀行的網頁伺服器把它的公開金鑰傳給你，然後就可以開始了。但你怎麼知道這把公開金鑰**真的屬於銀行**？

攻擊者如果把你的連線轉向，就可以直接傳給你**他自己的**公開金鑰，並謊稱自己是銀行。這樣你的瀏覽器就會乖乖地用攻擊者的金鑰加密，而攻擊者可以讀取所有內容。這種處於中間的攻擊者稱為**中間人**（*Man-in-the-Middle*）。

## 憑證：金鑰的身分證

在現實生活中，你會出示**身分證**來證明自己是誰。人們相信身分證，是因為它由**值得信賴的機構**核發——也就是市政府——而且不容易偽造。

在網路上，這項工作由**憑證**來負責。它包含以下內容：

| 欄位 | 意義 | 對應身分證上的 |
|---|---|---|
| **主體**（*Subject*，常寫作 `CN=…`） | 這張憑證是為誰核發的？對網頁伺服器而言：就是名稱，例如 `CN=www.biberbank.de` | 持有人姓名 |
| **公開金鑰** | 持有人的金鑰 | 照片 |
| **簽發者**（*Issuer*） | 是誰簽發了這張憑證？ | 核發機關 |
| **有效期限** | 從……到…… | 有效期限 |
| 簽發者的**簽章** | 證明簽發者確實以這樣的內容簽發了這張憑證 | 防偽印章、全像圖 |

`CN` 是 *Common Name*（通用名稱）的縮寫。

負責簽發憑證的機構稱為**憑證授權機構**（*Certificate Authority*，簡稱 **CA**）。在它為 `www.biberbank.de` 簽署憑證之前，會先確認申請者確實擁有這個網域。

## 瀏覽器信任誰？

你的瀏覽器會對每張憑證檢查：

1. CA 的**簽章**是否真實？（為此它需要 CA 的公開金鑰。）
2. 憑證是否仍然**有效**？
3. 憑證中的**名稱**是否與所開啟的網址相符？

但瀏覽器怎麼認識這個 CA 呢？每個作業系統和瀏覽器中都**預先安裝**了一份約 150 個**根 CA**（*Root-CA*）的清單。它們的憑證是**自我簽署**的——也就是自己為自己背書；人們信任它們，是因為它們隨軟體一起提供。

根 CA 通常不會直接簽署，而是透過**中繼 CA** 來簽署。這樣就形成了一條**信任鏈**：

```
Root-CA (vorinstalliert, vertraut)
  └─ signiert → Zwischen-CA
                  └─ signiert → www.biberbank.de
```

瀏覽器會沿著這條鏈由下往上檢查，直到抵達一個它信任的根 CA。如果做不到，或是有效期限或名稱不符，它就會顯示**警告**。

:::quiz match
主體（CN） -> 憑證適用於哪個名稱
簽發者 -> 是哪個 CA 簽署了這張憑證
公開金鑰 -> 用來驗證伺服器的簽章
根 CA -> 預先安裝在瀏覽器中，是信任鏈的起點
:::

:::tip 重點整理
**憑證**用來確認某把**公開金鑰**屬於某個特定的**名稱**。它由**憑證授權機構（CA）**簽署。如果瀏覽器能透過**信任鏈**抵達一個預先安裝的**根 CA**、憑證**有效**，而且**名稱**與網址相符，瀏覽器就會信任這張憑證。
:::
